# 群聊适宜性发送与未发草稿最小结算修复

## 结论与版本

本次故障是“旧输入账本 × 发送前程序门槛 × 共享历史草稿”的组合问题，不是QQ网络发送失败。

修改基线：`e539e0914cca82166c9d0a77f1d6eb18dd6b0a57`。首个修复提交：`3a72ca403e71425defc0dead5bca21d7a590df90`；随后根据用户纠正撤回表情回应过滤，最终实现以本报告所在提交为准。本次仅本地实施、提交与隔离验证，**未部署生产**，未重发QQ消息、改变登录状态或修改生产数据库。

现场业务源码目录版本为`8b582b61ec9a69f044bceb298a1f59448757f9ff`；监控覆盖层不改变本次涉及的业务Python模块。只读检查确认现场具有戳一戳原有专门处理及聊天队列排除逻辑，仍有`unhandled_inputs`拦截且没有本次请求输入快照。因此不能解释为“此前修复根本没有应用”；是后续组合逻辑仍有缺陷。群消息表情回应有交流意义，**不能因为本次阻塞就认定应该整体过滤**。

## 真实证据与根因

用户在22:45–22:46私聊追问的原群消息实际发生于22:23:14。证据来自同一Bot的SQLite Work/input账本、持久化Journal及有界诊断记录，均为只读查询。

1. 当次模型生成了45字符的回复草稿，Journal中有其assistant原稿。
2. 发送前日志为`output_review: keep / unchanged`、`checked=false`、`unseen=26`。这里的keep是“没有新的适宜性变化”的快捷结果，**没有额外调用复核模型**。
3. 随后的硬编码条件只要看到未处理数量非零，就将回复改为`superseded`、返回续轮。它推翻了keep，并未证明草稿不合适。
4. 那26条按原Work owner及seen=0回查，恰好是：23条09:40–13:06遗留聊天输入，以及3条`notice_type=group_msg_emoji_like`通知；23条聊天在当前Journal中不可见，3条通知也不是可提交的原生聊天消息。不是26条新问题，也没有证据表明本次包含戳一戳。
5. 后续三个主模型请求均返回`[NO_REPLY]`，其中后两个只见时间与空只读变更，没有新增真实对话输入。最终达到4次激活上限，账本`silent / model_no_reply_marker`，协议尝试0、确认0。
6. 私聊请求里既有历史草稿，也有`delivery=not_sent`，模型仍说自己“回过”。它把生成经历与真实发言混淆了；有not_sent字段不等于模型必然正确理解。

此前规则对poke、输入状态和撤回采用专门路径，但这不应机械扩展到所有通知。历史pending/deferred条目会被新Work认领，即使本次请求根本无法收纳它们，旧代码仍把它们当作应继续调用模型的理由；错误在无进展续轮与队列否决，不在“通知有交流意义就不该进入”。

## 实际改动

### 发送决定与队列责任分离

`adapters/astrbot/behavior.py`发送链移除“keep且队列非空就拒发”的门槛。模型复核keep时允许发送当前合适回复；独立问题保留自己的处理责任，不能因此伪造已读或已完成。drop、实际dispatch前的目的会话cursor、StopFence、权限、generation/revision、回执和unknown保护保持原样。

原`group_freshness.py`提示本来就要求判断“合时宜”，并明确无关插话不使原回复过时。本次没有将责任推给提示词，而是先移除相冲突的代码门槛，再补清“另有独立问题不自动否定当前回复；只因实际适宜性改变才replace/drop”。不新增辅助调用，不用关键词替模型决定是否说话。

同函数的一个相邻缺陷也已修正：只有启用共享上下文、确有主Work续轮执行器时，replace才交回主Work；非共享模式继续走既有受控替换渲染。此前非共享模式也交回续轮，实际无人执行，较宽回归首先暴露此问题。

### 保留表情回应与阻止无进展续轮

第一版曾将`group_msg_emoji_like`加入排除列表。用户指出表情回应不应排除，这个纠正成立：最终撤回该过滤，也撤回相伴的通知退休扩展。表情回应保留既有persist/join/观察路径，不伪造已处理或直接删除；poke、撤回等既有专门规则不扩大。回归明确断言表情回应不被判为transport noise，blocked_recovery与unknown原状态保留。

在Journal候选成功持久化之后，暂存本次请求仍未收纳的输入ID集合到当前Work。这个集合是**临时请求边界快照**，不是新账本、不是完成状态，也不复制正文。模型返回后：

- 没有未处理输入：正常结束。
- 未处理项均已在本次请求边界被确认无法收纳：记录`inputs_not_adopted`，结束无进展激活，原记录保留待恢复。
- 请求边界后真的出现新输入：允许现有主Work继续处理；后续仍受原激活上限及unknown保护约束。

不把老记录伪装成已处理，也不因为一次clock-only变化反复调用模型。重启丢失临时集合后，下次真实请求重新建立即可；不会因此获得重放外部副作用的许可。

### 草稿结算与最小上下文

`shared_context.py`复用既有`memory_message_sources`精确输出归属，且核验绑定的原稿摘要。对已经结算、确定没有发送的非空草稿，原有delivery项只增加：

```json
{"source_scope":"group:fixture","source_event":"event","recipient_id":"peer","delivery":"not_sent","draft_only":true}
```

不再次复制草稿正文，不创建新的用户业务消息，不增加业务轮。共同阅读说明明确“只生成过、未发送”不能说成“已经回复”，也不能归因于网络发送失败。

已证明只有`[NO_REPLY]`的纯静默事件不逐条列入投递视图；辅助recent视图也不重复抄写该标记。有真实反馈时保留必要反馈。旧数据缺输出归属时保留原not_sent，既不猜测关联，也不把证据不足当作成功。unknown/partial、协议确认正文及迟到回执的解释保持原合同。

投递视图继续使用原有数量/字符预算；状态相同不额外制造一份草稿叙述。旧Journal内容、角色、顺序和序列化均不改写，只在合法新输入里提供结算变化。合法检查点仍按原机制退休，不新增草稿永久池。
