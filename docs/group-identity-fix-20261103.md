# 群聊认主串用修复：2026-11-03

用户反馈 20:28—20:30 群聊中，小双白把普通群友叫作主人，真正主人询问后又否认叫错。

## 实际证据与范围

仅查询当前机器人既有 SQLite 真实入站及回复记录，没有重放生产消息或给关系数据加分。主人配置仍为原绑定 QQ；20:28、20:29 的两次实际回复对象均为另一 QQ，但输出用了“主人”。不能仅凭这段记录认定之前有人成功用昵称或自称冒认。事实是自然语言称呼串用，历史输出随后被模型维护为一致说法。

代码核对发现当前 identity.owner 只提供布尔值，缺少绑定主人的明确 ID；dialogue.feedback 读取历史回复时丢弃了数据库已有的 subject/event/at，使模型看到旧称呼却缺少回复对象。原生 AstrBot 的当前 User ID 提示不能替代各历史反馈的对象归属。

## 修改

- `behavior.py`：真实消息与自主服务上下文均携带配置来源的 identity.owner_id。当前 sender/owner 布尔值仍按协议 ID 计算；服务身份仍为 0，不冒充主人。通用认主规则区分当前作者、第三人及真实主人，历史模型称呼不能证明身份，允许承认旧输出错误。
- `participation.py`：feedback 同时提供原数据库 recipient_id/event_id/at，不新增存储，不改历史数据，不以模型文本推导身份。
- `group-participation-runtime.test.ts`：真实 AstrBot 请求中验证主人与另一发送者交替接话；另一人自称“双白”仍为 owner=false，owner_id 不变，历史反馈保留实际对象。未改变参与白名单、跟聊、疲劳或消息分条策略。

QQ 资料、签名、空间和群工具已核对的主人入口仍按真实发送者 ID 校验；称呼错不能直接改变这些权限。本次不宣称对全部工具完成新一轮安全审计。

## 20:54 再次误称：补齐原生历史来源（21:14 已部署）

前一版没有彻底解决。真实数据库对应显示，20:54 两条回复实际回应的是另一群友 20:52 的“瞎说”，不是用户截图中紧邻它的 20:53 @；后者当时因 foreground_capacity 被跳过。未发现绑定主人被改写，缺陷仍发生在自然语言对象归属。

根因补充：原生 ToolLoop 持久聊天历史保留了消息文本和旧模型称呼，却没有逐条保存 FishBot 已核实的作者身份。仅补当前 identity 和 dialogue.feedback 不能完整修复历史归属。现在由公共管线在真实消息对应的原生 user prompt 前附 sender/owner/scope/event 来源；原始协议消息、记忆原文不改，服务任务不冒充 QQ 用户。系统上下文末尾再次明确当前回复对象与绑定主人的关系。旧无标记历史不能证明身份，不删除已有聊天记忆。

并发已满的前台消息改为最多 8 条、等待最多 15 秒的短队列，检查运行代次/会话有效性；完成与取消均释放等待计数并通知空槽。自主任务在前台队列等待时让位。不宣称可无界接收或绝不超时；模型或上游长时阻塞仍会明确记录容量超时。
