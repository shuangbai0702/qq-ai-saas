## 1. 执行摘要：在线可用，但尚不能判定全系统健康

当前API、Agent、Postgres容器均running/healthy；真实模型调用持续成功。19:34容量热修释放了原本尚可用的绝对容量，且四个热修文件与生产磁盘逐字节一致。但“所有私聊恢复”“35轮检查点全面恢复”“所有图片理解正常”“所有调用观察完全闭环”，证据均不足。

本次最重要的新发现：

1. **提交边界尚未完全覆盖“请求已发但结果未知”**：异常统一abort候选，只保护此前成功提交的Journal；离线证明失败候选的新尾部可以在下一请求消失。代码风险已证实，尚未证明某笔生产请求实际因此违反历史连续性。应先于其他优化解决。
2. **正常工具轮会成为无法靠重复摘要释放的Hold**：`supported_block`不支持tool_calls/tool；生产大肥鱼1条、小双白3条私聊Hold逐一命中这一机制。19:40修复了pending登记，却没有补齐工具整轮证据合同。
3. **Hold恢复还需另攒35个新轮**；容量不足时可能再也等不到恢复任务。真正lost与“材料合同不支持／暂时不完整”必须区分，不能删Hold、伪造coverage或借新epoch逃逸。
4. **旧报告几项重大因果判断错误**：把采集次数当表情发送次数；把SDK群历史清空等同最终请求无历史前缀；把几天写成一两个月；把缓存unknown直接归因解析漏字段。
5. **记忆还有实际接线缺陷**：多份大摘要时选最旧一份；已解决话题可在Claims中保持永久保护；自动正则Facts写入仍与摘要模型并存。

因此，推荐收敛为“提交证据与合法恢复→保护状态和记忆接线→观察与辅助预算→行为小改→条件优化及约定业务复核”，保留单内层、现有任务账本、800/1500字摘要限制。不要以再加容量、改缓存布局或新建第二套约定/记忆系统代替这些修复。

## 4. 新发现的根因链与影响

### 4.1 已发送未知请求与Journal成功提交边界不一致（P0）

链路：`behavior.text_chat/text_stream → prepare_chat_payload → Journal.prepare → HTTP hook → 异常/取消 → settle_journal(False) → abort_candidate`。

`behavior.py:1182–1211,1360–1386`未将“确定未发出”和“已发/已开流/提交未知”传入Journal处置；`readonly_journal.py:539–543`只撤销候选，不持久保留它的新尾部。`offline-repro.json`证明：旧成功前缀保留=true、失败候选尾部保留=false、下一prepare可成功。复现没有网络，**不声称某笔生产请求已发生违规**；但它证明“诊断分型已足以保证未知结果阻断”的旧验收表述不成立。

用户护栏是“已提交给模型”，不能缩成“成功返回且本地commit”。重试、流取消、worker崩溃、许可重构请求成功送达但结果未知，都必须在同一合同下考虑。保存提交证据不意味着该轮成功、消息已发送或可计入35轮。

这也是原《全系统健康与上下文长期记忆最终整改执行计划》第7节C包已经明确要求的“仅可证明未提交wire才释放reservation”。本次属于发现**原计划要求未完整落实**，不是追加一个无关的新机制。

### 4.2 工具整轮被材料合同永久判不完整（P0）

链路：已成功工具轮→`summary_material.snapshots`→`context_protocol.supported_block`拒绝tool/tool_calls→complete=false→摘要不写coverage→Hold保留→pending不能晋升→wire不能退休。

生产逐事件只读重放（不写库、不摘要、不执行工具）：大肥鱼1条、小双白3条私聊Hold，在现有Journal中找到同digest原始输入；整轮角色为user→assistant→tool→assistant等，均带tool_calls、无图片，按当前合同重抓仍complete=false。故至少这4条不是“多跑一次摘要就能修好”的暂时漏抓；另两条群Hold在当前Journal中未找到，原因保持未查明，不能直接标lost。

这是目前“增强信息保真反而造成容量死锁”的明确实例。未知内容诚实阻塞是正确安全默认；但系统自身支持的常见工具轮，需要有可信、受限、完整的覆盖表达。

### 4.3 恢复调度依赖新的35轮（P0）

`memory_reflection.retry:655–661`仅在new batch达到summary_rounds时把held加入。现有进度：99私聊8个新轮；735私聊6、群14；d18群2。单纯登记pending没有独立补证机会。

即使已有足够恢复材料，只要剩余上下文容不下再35轮，也会停在“需要新对话才能恢复，但新对话已被容量拒绝”。工具证据合同必须先修，随后复用现有后台摘要/退避做补coverage任务；两个问题不可互相代替。

### 4.4 记忆接线与保护退役（P1，属于P0容量的必要前置时提前）

- `memory_reflection.rolling:458,482`按id倒序查，却`bigs[-1:]`选最旧可见big。多big并存时会注入旧背景；应选最新且继续沿用受众门，不扩大召回范围。
- `companion_insights`可将motive写为resolved/abandoned，但`summary_material:338–350`仅把open接入Claims；previous_commitments和settle又仅处理agreement。已解决话题仍可能永久protected，挤占8000字符保护预算并阻断Big Merge。不是所有open都错，问题是缺少可信后续退役接线。
- `hosted_memory.self_report:21–37 → observe:124`仍按词面写人物Facts；与已有摘要模型重复，且语义能力有限。显式记住/忘记/更正命令是操作接口，不能一并删除。自然纠错现有启发式门仍可能漏报，应以明确反例决定替换，不能盲目删去所有来源/否定/引述保护。

## 6. 必须维持的不变量与合法恢复边界

1. 已提交给模型的消息内容、role、顺序、媒体表示和序列化不可在合法35轮许可前改变；System、配置保存、SDK截窗、重启、epoch切换均不能提供逃生许可。
2. HTTP失败/未知请求的提交保全与业务完成轮计数分离；失败不能赚轮次，取消不能当成功，未知副作用不能自动重发。
3. 许可必须对应同tenant/bot/scope/epoch、真实完整35个新轮；pending仅等待，available/reserved/consumed保持原子合法转移；consumed不复活。Big Merge携带scope/epoch/request/状态，不重签重复许可。
4. 模型负责语义选择与状态关系判断；代码验证真实来源、发言者、被展示的旧Claim、时序、版本、权限、预算和事务。主人、引用、模型自述和工具回执不能互相冒充。
5. 群/私聊/跨群召回继续走既有受众校验。隐私撤回后若旧wire禁止使用、又无许可重建，应诚实阻断，不能向更小受众悄悄重投敏感历史，也不能先删再声称连续。
6. **有限容量不可能无条件容纳35个任意大的新轮。**设剩余容量R、新增合法不可变量为a_i，若到许可前sum(a_i)>R，且无真实可用许可，则“继续普通调用、保持旧历史、容量不变”不可兼得。可以约束尚未提交的新材料、消除无价值重复、修正常合法许可供给；不能承诺绝对不再阻塞。
7. 无完整可验证历史时：只读封存、说明缺什么证据；优先恢复原Journal/工具源材料。若确实无法恢复，只能请求**具体且知情的例外授权**，说明要放弃何段历史、保留什么审计、是否新会话；用户本轮绝对约束下不能自行实施任何丢弃/重建。笼统“管理员修复”不等于授权。

**当前能证实的能力**：`summary_material`已有agreement Claims，包含id、speaker、scope/sourceRefs、stage/status、可选due及supersedes；accepted映射open，proposed/unknown独立，executed/canceled可退役，跨摘要/merge有保护和召回机制。另一方面，`pipeline_handoffs`、PG `acceptHandoff/planHandoff`、goals/wakes、实际工具回执已提供结构化任务与执行基础。**两条链都存在，不等于二者已可靠互通**；当前accepted是来源说话人语义标签，不是程序已经验证双向确认。当前due只是原话子串，不是已验证可调度时间。

**后续核验清单及具体交付**：

| 业务环节 | 要取得的证据/边界 | 最小改进决策 |

| 更新/取消/过期/冲突 | 同人跨事件、双方不同意、后改时间/条件、相同主题多约定；谁能取消；过期≠履行成功 | 语义由模型判断，程序验证版本/来源/权限与合法转移；不靠相似文本合并不同约定，不自动给proposed永久保护 |

**验收**：一组少量、可重复的离线完整案例覆盖“提议→双方确认→改期→取消”“到期提醒→unknown ACK→重启”“两个人同主题”“跨群/私聊与不同bot隔离”“跨两代大压缩后准确召回且不重复执行”“未确认/不具备执行能力不自动履约”。对每例分别给记忆PASS和业务履约PASS/BLOCKED；只有结构化状态、调度、执行证据闭环才可声称可靠履约。自然到期端到端验收另授权，不在本轮制造约定或QQ消息。

**交付/风险/收益**：先出“现有状态→缺口→是否改→最小补丁”的小矩阵；已具备的不重复开发。修正错误成功或丢取消有明确可靠性收益，其它无法量化时说明不确定性。若需要大量新状态/双向协商引擎才能支持低频社交约定，暂缓该高级能力，明确“记忆而非自动履约”的产品边界。预计复杂度取决于核验结果，不能预报为一行修复。涉及schema、生产任务回填、取消存量任务、付费模型/真实履约均需额外授权，回滚保留已发生副作用和不可重复执行证据。

## 10. 发送、任务与故障污染的保持性回归

- `group_actions.owns_reply`以同attempt_key+scope接管final；同事件同群confirmed/unknown/partial/取消不二发；工具调用确定在发送前被拒绝时正常final仍可用。
