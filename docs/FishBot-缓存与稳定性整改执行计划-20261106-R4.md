# FishBot 缓存与稳定性整改执行计划

2026-11-06，配套依据：[独立复核报告](FishBot-缓存与历史重建独立复核报告-20261106-R4.md)。**本文仅为下一轮实施设计，本轮未执行任何整改。** 后续真实模型验证、生产变更和部署需下一轮明确授权，本计划不视为本轮授权。

## 1. 最高合同、范围与实施准入

用户最终明确的最高代码护栏：

> 系统提示词只有在35轮摘要时候能变；35轮上下文重构是最高级护栏，除非用户直接网页修改了。

该合同优先于旧计划中“17–19次后台调用触边就重建”“摘要表变化就重建”“空闲后重建”以及追求命中率的方案。**不得增加隐藏例外，不得把任意summary_changed、自动刷新revision、模型失败或进程重启伪装成用户网页修改。** 普通消息、不同发言者、图片、工具调用、事件类型和工具可用性变化都不是重构许可。

固定35轮指业务真实已完成对话轮次，与同一轮里的ToolLoop消息数、后台orientation/planning模型调用次数无关。准确来源沿用`Reflection.maybe_start`的`memory_rounds`与`memory_reflection_progress`，不要新建独立消息计数器。大摘要合并不是新完成35轮。35轮是允许边界，摘要生成失败不构成成功边界。

本计划范围：现有ContextBuilder、decision/readonly journal、摘要事务与投影、请求装配和诊断、输出到OutputPlan/ACK接线；精简必要信息的表达与重复传输。保留35轮业务覆盖、群轮次13条默认、人物事实、跨群私约定、真实回执、未完成Work、后端授权及副作用幂等体系。

不做：换模型/代理、乱加prompt_cache_key、缩短记忆窗口、按行数删资料、冻结身份/权限、把动态可信身份整体降为user、延迟遗忘、自动重发外部动作、另建一套记忆/授权/调度系统。历史原生档案和数据库正文不批量改写。已有大量本地修改不能整体打包上线。

**必须承认的可行性边界：** “任意大流量、始终回复、35轮前绝不改写前缀、内存/请求有上界”不能无条件同时保证。完全相同的已提交前缀不能在第17轮原地压缩后仍声称相同。容量不足时只能明确阻止模型请求并保留有效基线，不能偷偷重建、裁必要信息或无界增长；这属于故障状态，不能作为正常验收通过。只有在真实35轮轨迹及压力测试中证明无需这种阻塞，才允许上线新护栏。若压缩不足以满足条件，标记暂缓，不自行放宽35轮。

同样，用户护栏不意味着沿用旧权限。权限/遗忘立即生效；没有合法的新可信承载或重构许可时，拒绝使用旧资料发起请求，不复活已失效内容。下一轮必须把这一冲突以客观测试收口，不能写成“默认合理例外”。

## 3. 重大方案比较与选择

| 项目 | 保持现状 | 最小修复（首选） | 深入优化（有条件） |
|---|---|---|---|
| decision journal | 提前重建，违背新合同；实现简单但费用/体积继续增长 | 统一许可、失败保基线、可逆压缩，获准边界重建完整当前状态 | 对仍合法active记录分块，跨获准重构保持相同连续前部；须证明实际HTTP而非对象复用 |
| 前台system | 已有独立system快照，但首部数据和工具仍动态 | 固定全部system模板/记忆语义，动态可信内容改经验证可信角色；格式指南恒定 | 统一角色协议/多模型适配；不支持的模型路径暂缓，禁止user降级 |
| 摘要生命周期 | 哈希整表，所有变化退休两阶段 | 35轮事务许可；big合并更新当前记忆数据、不中途重构；候选提交复核 | 按实际依赖证明减少传播，但遗忘必须从请求中消失，不能仅移除引用 |
| 输出过滤 | 无新误删但既有分析可能泄露 | 结构化reasoning分离、确定标记清洗、终态观测；撤回通用英文分类器 | 内容启发式只作观测，除非独立质量集证明可接受，否则不启用拦截 |

复杂度：现状最低，最小修复中等但可信角色/35轮护栏有硬兼容门槛；深入方案最高。最小方案不承诺40%或50%的节省，收益先由实际轨迹度量。深入方案可能增加代码维护、格式版本、资源和回退复杂度，不能自动列为必做。

**否决旧方案：** 保留首份contextState、旧摘要或旧Work并用新尾巴覆盖来凑缓存；将identity/owner权限移user；固定工具总集以绕过按事件授权；大小触发后在17轮静默重建；空回复/500自动重发QQ；只看缓存命中而忽略总体积；以gen/resp选择通道；先部署有已知误删的过滤器再观察。

## 4. 精确实施设计：唯一的35轮/网页重构许可

### 4.1 当前执行与需要改变的点

`AppendHistory.prepare`用`self.turns<MAX_TURNS`和history_boundary决定reuse；`ReadonlyJournal.prepare`另检查native前缀、摘要、stamp、idle；`commit`可因大小clear。`invoke_decision`按摘要整表stamp失效，`behavior.prepare_chat_payload`按模型/工具stamp和原生base失效；二者都没有业务35轮成功事务的许可。旧journal未持久化，进程重启无法还原相同transport前缀。

修改文件与职责：

| 文件/函数 | 具体任务 |
|---|---|
| `memory_reflection.py: Reflection.maybe_start/run`的成功summary事务 | 普通35轮成功事务生成checkpoint证明；big合并不生成；证明与摘要、水位、coverage同事务 |
| `decision_history.py: Prepared/SnapshotPrepared/AppendPrepared, AppendHistory.prepare/commit/clear` | 携带许可、依赖版本与候选usage；移除以调用次数冒充业务35轮的正常重建；未经许可不得assemble(False)替换已存在基线 |
| `readonly_journal.py: Prepared, prepare/commit/abort_candidate/retire_committed` | 同一许可合同；native变更不自动当重构许可；保留候选serial栅栏 |
| `autonomous_runtime.py: invoke_decision/valid/cancel` | 同步准备当前输入、许可和摘要依赖；await后复核；两个阶段同一checkpoint、独立候选与成功基线 |
| `behavior.py: prepare_chat_payload/settle_journal/text_chat/text_chat_stream` | 在最终装配与HTTP边界检查system/许可；与Work、租户、epoch及工具邻接共同验证 |
| `model_cache.py: begin_attempt/observe_payload/observe_wire_request/record_diagnostic` | 记录许可来源与system护栏结果；禁止仅记录warning后继续发送非法请求 |
| `apps/control-api/src/app.ts: PUT /v1/bots/:id/config`；`apps/node-agent/src/agent.ts: context/apply链` | 沿已有revision与config.saved审计提供真实网页编辑来源证明；不信任请求body里自报web flag。先确认实际部署入口版本与共享模式映射 |

不要为这些逻辑新增后台Task、全局缓存Manager或另一个记忆表。建议把纯许可验证器放在现有`decision_history.py`中供readonly复用，引用现有memory控制/水位，避免循环依赖到数据库Owner。

### 4.2 证明与状态结构（拟新增，不是当前已有字段）

沿现有reflection控制/进度维护最小checkpoint元数据，版本化迁移；具体建议新增同库表`memory_context_checkpoints`，它只保存已有摘要事务的证明，**不保存第二份摘要、聊天或权限**：

```text
id INTEGER PRIMARY KEY
scope TEXT
from_watermark INTEGER
through_watermark INTEGER
round_count INTEGER CHECK(round_count=35)
summary_id INTEGER
forget_epoch INTEGER
committed_at REAL
UNIQUE(scope,through_watermark,forget_epoch)
```

约束：事务中核对这35个真实round ID/事件唯一性，不能只看watermark相减（ID可能有空洞、跨scope）。来源和summary现有表可追溯；回滚不留证明。summary模型响应完成不等于数据库提交。删除摘要/遗忘不得留下可用的虚假许可；证明作为审计保留时标记retired，不继续授权新请求。

拟在Prepared携带：

```text
candidateSerial, baselineSerial, bindingKey
checkpointId, baselineCheckpointId, webRevisionProof
forgetEpoch, summaryContentDigest, summaryCoverageDigest
systemManifestSha, nativeBaseSha, layoutVersion
beforeUsage, attemptedUsage, finalUsage, reasonFlags
```

`bindingKey=(tenantId,botId,logicalScope,phase,providerSignature,configRevision)`；Work ID只在同一任务的内部ToolLoop复用，不能用于跨任务权限。providerSignature是模型别名、规范化endpoint/非秘密配置摘要，不能靠`id(provider)`跨进程复原；认证身份只用不可逆绑定指纹，禁止写Key。

`webRevisionProof`必须源自已认证用户的配置保存事务及对应审计事件，包含bot、tenant、previous/new revision和服务端事件ID。不依赖浏览器伪造Header，也不把普通自动续租或配置文件mtime当网页操作。若API与网页共用，合同须明确“经相同认证的显式配置保存”来源；不能在实施中扩大为任何revision变化。未确认来源时不发许可。账号切换/删除等网页操作沿既有专门合同，不能用旧bot前缀跨身份。

### 4.3 状态转换与不可绕过的断言

```text
BOOTSTRAP（从未有基线的真实scope/phase）→ CANDIDATE → COMMITTED
COMMITTED → prepare append → CANDIDATE
CANDIDATE completed + serial/dependencies/current有效 → COMMITTED
CANDIDATE failed/canceled/timeout → abort candidate；保留之前COMMITTED
旧serial返回 → reject；不得清除/覆盖新COMMITTED
35轮事务证明或真实网页编辑证明 → REBUILD_PERMITTED
REBUILD_PERMITTED → 当前权威材料重新构建 → CANDIDATE → COMMITTED
其他前缀/容量/摘要/闲置变更 → BLOCKED_FOR_CONTRACT；不得隐式clear后bootstrap
遗忘/权限失效 → 禁止旧材料再次发送；无许可/无安全载体则BLOCKED
```

最高断言：已初始化的逻辑上下文中，`system vector changed OR logical rebuild`必有`checkpoint35_success OR authenticated_web_edit`证明。检查**所有system消息的数量、顺序、role、完整content表示**，不能只测message0或拼接正文；工具schema及模型参数另记。不可用“换phase/scope/Work名”伪造新会话绕过。

第一次创建新阶段可沿现有peer冷启动复制兼容已提交基线；必须通过同一guard，复制不代表许可。首次bootstrap只准一次，持久记录其身份。进程重启、LRU驱逐、prepare异常、commit超限不能让已初始化scope重新冒充首次创建。

35轮证明按机器人/来源会话生成；两条共享记忆的外层journal可在同一新checkpoint后分别重构一次，不能每次请求重用同一许可不断重构。无实际布局/内容改变时不强制重构。不同机器人的checkpoint绝不通用。某scope的35轮是否允许重构其他scope：仅当其实际依赖该共享摘要且同bot的上下文合同明确，默认不跨scope传播；外层bot-wide依赖必须记录来源scope集合。

### 4.4 保持有界与进程重启

需要最大输入/尾巴/回复预留，不能等commit才clear：prepare同时计已提交、候选新增、runtime、system、tools、媒体wire与输出预算；最终HTTP再校验provider容量。使用真实usage校准，不将字符/3当Token。无法安全预测时保守标记估算，不宣称精确计费。

现有384K等硬上限先保留作容量拒绝阈值，不再作为获准前的自动重构触发器；不要贸然调大。首请求本身超限走明确预算失败，不能完整发送后不断重建。新布局必须在35轮离线轨迹及最坏有效消息场景证明不频繁触限，否则不得部署阻塞行为。

若要求重启后仍保持35轮期间逐字节前缀，必须补现有journal的**有界传输恢复**，而不是从DB重新猜一段历史。首选沿机器人私有runtime文件新增版本化transport快照，内容限当前有效journal/许可与system manifest，不成为事实/授权来源；0600、原子临时文件+rename，绑定租户/bot/provider/layout/epoch。每次commit写一个最新快照；候选绝不落为已提交。快照失败不回滚已执行外部动作；下一次不得冒称连续性可用。

容量建议先按既有8个chat journal、2个外层与1个当前内部Work评估，提出32MiB/机器人序列化字节的候选总预算，**必须用真实35轮与媒体轨迹实测后定值**；不是直接套新常量。不能为省内存提前删除仍受35轮保护的scope后再bootstrap。不能满足总预算时暂停新模型请求并报警，不删必要历史；上线前正常负载零阻塞为门槛。

恢复时读当前后端配置/forget epoch/合法摘要依赖；快照与当前不兼容、损坏或缺失，发出context_restore_unavailable，不带旧身份继续请求，不静默冷启动绕过护栏。更深入的持久恢复增加隐私与IO成本；若用户不接受该新增有界传输文件，则“重启也保持严格前缀”的目标暂缓，不能在计划中假装已解决。它不存新的业务记忆、不改变数据库事实归属，无独立后台任务。

## 5. 上下文精简：最高优先级的体积治理

### 5.1 先建立逐轮账本

修改`decision_context.split_snapshot`、`decision_wire.render`和`model_cache`诊断，按每次成功候选记录：

```text
committed/attempted/final: messages,plainTextChars,textChars,wireChars,wireBytes
newRecordCount/newRecordChars/byKind；active与retained记录数及字符
contextState/contextChanges/runtime/assistantDecision/system/tools各自字符
同事件正文重复次数；全列表替换次数与其字节；新增/更新/引用迁移的原因
input/cached/output真实Token，reported状态，TTFB/总延迟
```

细粒度byKind若不适合现有scalar whitelist，用有界固定枚举字段或脱敏侧统计；不要将任意dict塞入diagnostics或记录正文。阈值记录before/attempted/after三组，所有reasonFlags保留，主reason不能掩盖同时发生的summary/system变化。记录prepare/commit容量分别在哪个表示层计算。检查诊断256KiB轮转不足以覆盖35轮：增大预算必须先资源评估，不无限保留，也不额外抓全量正文。

### 5.2 首选精简：表达可逆，必要信息不删

具体文件：`context_transport.memory_context_view`、`decision_context.decision_view/split_snapshot/expand_snapshot`、`decision_wire.render/expand_tables`、`context_protocol.model_json`。仅改请求副本，不改源SQL正文、事实提取、回执账本。

按下列顺序实施，每步独立比较收益，未产生显著体积改善就不引入格式复杂度：

1. **固定格式指南。** 将context_references指南定义一次固定协议文本，不再让“本次是否发生正文引用”改变system。保留已生成text_ref/reply_ref的语义；未知同名数据不能当平台指南。先离线确认当前新旧装配路径，避免只修早期已淘汰版本。
2. **同来源正文单份。** 复用现有memory_context_view的精确事件键；外层也使用同样的正文引用机制。键至少包括`source_scope,event_id,role,sender_id,完整正文摘要`，机器人/租户由当前请求绑定。只有全部匹配才共享body。保留round/timeline/recent各自列表、顺序、作者、接收者、时间和状态，不能合并成一条事件。相同文本但事件/作者不同不共享为同一事实。工具回执的ID、unknown/confirmed和完整值不能被普通文本摘要代替。
3. **消除因kind不同而重复的大正文。** 在现有recordTables协议内新增明确版本的正文引用，复用同一个本请求body表；记录kind和所有差异元数据继续各自保存。扩展`expand_tables`先还原body，再`restore_append`；reserved标记冲突时保守完整fallback，不能误解释用户文字。不要另设永久body数据库或跨租户字典。
4. **字段与结构共享。** 优先沿现有columns/common机制共享同构记录的字段名和相同常量；只在同一新记录块内应用，不能回改旧wire。表头顺序固定、数组顺序不变；精确ID与回执不截断。若共同字段共享会把不同来源混淆，则不共享。
5. **增量最小化。** 对contextChanges统计whole-list replace与点patch；保留`apply_changes(before,operations)==current`强断言，以最终编码实际长度选择较短表示。审查record引用编号变化和runtimeLayout导致的连锁替换；稳定别名只在同journal生命周期内分配，不因遍历当前active顺序重编号已提交记录。现有render从历史重演aliases，优化必须得到同样旧前缀。
6. **减少自生增长。** 核对recentActions与autonomous_experience.decisions是否同一真实决策重复进入记录；只有同来源、同值才共享。旧模型决策不等于执行事实；保留未完成Work、当前feedback与unknown依据。不能为了短提示删掉全部执行经历或只剩模型的“已完成”文字。

通过标准：每轮`restore_append(expand_tables(wire))`与改前的当前完整输入语义逐字段一致；未知字段和媒体原样可恢复。精简并非语义摘要，不用新模型“压一下”来代替无损验证。不缩35、不删事实、不砍群轮次，不把真实回执剪成省略号。

评价至少三个量：首基线大小、每轮新增长度、35轮累计最大请求。离线必须提供相同轨迹修改前/后表，分别列真实Token或估算、字符/字节与媒体；没有真实Token时不写精确节省Token。首选目标是**35轮前不因容量重构且正常请求零预算阻塞**；在此基础上追求最大精简，而非先定随意百分比。若仍超限，继续定位表示冗余或暂缓，不改护栏。

### 5.3 获准重构时保留合法公共前缀

当前重构已经保留system，不能重复计算收益。首选每次获准checkpoint重新用当前数据库/Work构建完整active输入，旧候选和旧contextState不保留。复用现有摘要，不新增35轮之外的自动摘要或第二套长期记忆。

深入分块方案仅在必要时实施：`split_snapshot`保持当前active记录顺序，`render`按相同kind/columns、每块最多16记录或8Ki字符形成确定性小块；超过单块的大记录单独保留，不裁。输出先固定规则，再当前合法记录块，再当前contextState/runtime/阶段指令。只在两个请求**从起点开始连续消息相同**时计算共同前缀；跳过中间变更后找到“相同对象”不算前缀。

重构前校验每个保留块的全部正文仍在当前active集合、epoch/权限/binding有效，没有旧摘要、删除事实、已忘内容或旧Work私有材料；缺一个证据就重建该块及其后，不保留旧view。不要把记录排序仅为命中而改变源列表。已发生遗忘时旧块不能作为模型可见的历史证据继续发送。

分块改变表common利用率，可能反而增加体积；旧aliases与新块ID也可能导致首差异提前。因此只有相同真实轨迹下总输入、未共享前缀及资源均实测改善，且35轮/身份/回执验收通过才采用。不得承诺上游cached比例≥0.5作为纯本地可保证条件。回退在下个获准边界切旧renderer，不能当场非法重写。

## 6. system恒定与可信动态信息设计

### 6.1 固定/动态字段合同

`system`是**整个system消息向量**，不是仅message[0]。默认所有人格、基础规则、来源解释、执行披露、记忆引用语义、普通中英文输出规则都进入固定模板；模板内不插当前时间、sender、identity JSON、工具临时状态、context_references开关、检索结果或当前Work。可变摘要/便签也不靠冻结保持旧system，应经当前数据平面及时传入，完整记忆内容仍按ContextBuilder读取。

| 类别 | 拟放置与规则 |
|---|---|
| 人格/基础规则/固定协议指南 | 固定system manifest；仅获准35轮成功提交或网页显式修改时允许新manifest；没变不强行更换 |
| 配置能力规则 | 固定描述“以本轮可信能力快照及后端检查为准”；真实配置保存可获网页许可更新；不可用工具不在后端放行 |
| 实时speaker、owner、principal、destination、权限及事件规则 | **可信动态载体**；不得进入普通user授权内容，也不得冻结旧值 |
| 只读facts、summary、core_note、timeline、round/recent、工具观察 | 既有readonly数据包，当前值完整；不得作为指令或授权 |
| 用户正文、昵称、引用、工具返回的任意文字 | 保留原低可信来源与role；不能触发manifest/角色升级 |

当前代码已有AUTHORITY_CURRENT system快照，不能简单“再拆一个system”就声称满足护栏。要满足全部system恒定，动态可信快照必须离开system；这不是把它降为user。

### 6.2 可信角色兼容门槛，未通过就暂缓

首选研究路径是提供商/SDK真正支持的`developer`角色：平台单独生成动态可信快照，优先级低于固定system、高于user；全部消息来源仅由代码构建。**当前deepseek/中转是否原样支持并保持语义尚未证实**，不得在生产直接添加字段试错。

下一轮先在历史离线SDK装配与获准的隔离测试账户验证：role是否原样进入最终HTTP；SDK/网关是否改成system或user；同一工具链和媒体是否保持邻接；模型是否正确按最新可信快照识别speaker/owner；伪造user/developer标记、quoted system文本能否绕过；不同模型/alias/endpoint分别验证。只有HTTP200不足以证明可信语义。若服务商不支持，不启用这条路径；不能将它静默映射user，也不能放松system护栏。

平台生成的动态快照包含version、真实sender/owner、scope、principal、Work绑定与能力观察；不接受模型提供的ID覆盖。权限仍由`qq_actions.allowed/execute`及其他既有工具入口实时校验；developer快照不是执行许可。工具列表继续按真实事件装配，变更工具不授权更换system。旧动态快照中的权限撤销：真正网页绑定/权限变更使旧上下文退役；不同真实说话者按最新可信快照理解，不继承主人权限。涉及删除/遗忘则不能仅用最新快照覆盖旧正文。

静态system将此角色协议写明一次，且35轮前不得动态改模板。模板迁移本身只能在获准边界发生。不能先上线system护栏把正常identity变化全部堵住，再声称兼容工作以后补。若无法同时保证稳定system和身份安全，前台结构调整列为暂缓，继续提供独立证据，不出不安全版本。

兼容实现位置：`context_transport.request_context_view/authority_context_view`生成可信包，`behavior.inject/prepare_chat_payload`保持来源，`readonly_journal.prepare`识别平台生成可信包并在变更时追加；必须新增显式role与结构验证，而非按用户正文的同名字符串识别。`native_internal`与opaque/tool_calls_result老入口分别覆盖；保守fallback不允许违反system护栏，无法安全表示时返回明确不支持。

## 7. 摘要、遗忘、候选与两阶段一致性

1. **摘要读取一致性。** `invoke_decision`调用`shared_context`及计算依赖stamp应来自同一无await读取段/SQLite读快照。用当前真实材料构建一次，再prepare；不要取旧prompt后单独给它盖新stamp。前台跨媒体await后按相同依赖验证投影，不将旧facts配新epoch。
2. **35轮提交许可。** 普通summary事务生成checkpoint；big合并事务只迁移摘要/coverage并更新当前材料，不凭它允许system或全量重构。若旧摘要正文必须从模型可见历史撤回且当前不可合法追加表达，应阻塞并报告合同冲突；不能保留它假装新记忆已生效。通过将记忆始终放只读数据、明确当前视图更新可解决普通“替换当前值”，但主动遗忘不允许残留字面。
3. **摘要指纹分开。** 保留全表auditDigest；另计算当前有效材料正文/来源/coverage投影的contentDigest和coverageDigest。ID或updated变化但内容完全相同只更新审计；只有经展开证明语义等价才能不中途失效。来源和覆盖变化不能按“正文同”忽略；暂不缩小forget权限失效范围。
4. **提交fence。** await返回后检查serial、owner、binding、Work/lease、policy epoch、forget epoch、summary依赖。若摘要已变，拒绝把旧候选作为新基线，先检查已有成功基线仍合法则只abort；不因旧候选失败清掉其他成功状态。下一请求用最新数据和许可决定追加/合法重构/阻塞。是否继续采用旧模型业务决策必须通过既有valid/feedbackVersion，不因“缓存没提交”重复模型或外部动作。
5. **两条journal。** orientation/planning分别commit/abort，checkpoint依赖共享但不互相写候选；当前peer复制仅首次、只复制已成功且同绑定的对象。summary变更不会同时清空不相关租户或内部Work。新checkpoint后两次必要请求计为两个实际请求，费用不能“除二”隐藏。
6. **失败与取消。** 延续现有abort_candidate，不恢复老`discard`清空所有成功历史的调用。500、超时、取消、解析JSON失败均不伪造assistant结果。HTTP失败与业务blocked分别记录；无usage保持unknown。
7. **遗忘/内存关闭。** 先使旧epoch与候选不可提交，再阻止旧材料发送；数据删除沿现有事务和coverage触发器。来自网页的真实遗忘/设置变更可带用户例外许可；其他入口不能擅自伪造网页来源。若当前产品支持聊天遗忘命令，下一轮必须确认其实际合同：安全删除立即生效，但未获重构许可不能继续模型请求，需明确提示而非保留已忘信息。不得为缓存延迟删除。

测试并发必须用barrier：prepare→暂停→摘要提交/遗忘/网页修改→恢复；以及旧A失败晚于新B成功。不要靠sleep碰运气。摘要元数据写、内容写、big合并分别测试，不把它们统称summary_changed。

## 8. 输出链路、候选补丁与稳定性

### 8.1 model_cache补丁

在冻结的当前生产基线上提取诊断差异，独立提交；验证response_shape对dict/SDK对象、content为空、缺失/空reasoning、多choice、finishReason异常、流式最终usage的行为。只记录长度、枚举、哈希，不记录文本。`responseIdShape`只是形状，不用于通道路由/限流。诊断失败不得改变模型结果；测试一次调用结束只写一次result，失败不补0。

### 8.2 output_clean与behavior补丁

原without_analysis候选不得照搬。删除拟上线版本中“英文占比”“Planning等标题”和“rest英文少中文就全删”的拦截决策；原候选保留为审计材料，不能覆盖用户本地补丁后声称原样。

确定可处理的输入是服务商独立reasoning字段、明确规范的控制标记与当前项目已有内部标签。reasoning字段不拼入可见content；content中疑似英文分析只做有界分类观测，不凭语言/标题吞正常回复。若需要在content中阻断无标记泄露，须单独建立授权质量策略与标注集；本轮证据不足，列为暂缓，不能宣称彻底修复泄露。

`behavior.send`（嵌套patched发送路径）在创建OutputPlan前决定可见正文；保留图片、语音、At、表情和分条。只有没有任何可见载荷才记empty_visible_text；独立reasoning有内容但可见载荷为空，才记reasoning_only_reply。启发式扣留不能冒称“纯推理”。`[NO_REPLY]`的意图判定必须区分模型控制输出和代码块/引用中正常讨论该字符串，当前`in`搜索会否吞正常消息先补负面测试。

`bot_pipeline.stop`只更新当前Work终态，不取消其他Task，不重置journal。若工具已执行/未知而最终沉默，记录副作用实际状态，不能把整个Work写成未执行，不自动重跑。OutputPlan及QQ ACK以统一协议为准：生成了正文不等于sent，HTTP成功不等于投递确认，多个bubble局部成功不能整体重发。

行为测试入口沿现有`tests/behavior_test.py`、`tests/send_lifecycle_test.py`、`tests/behavior_memory_integration_test.py`、`tests/output_clean_analysis_test.py`、`tests/model_cache_test.py`。先修测试环境依赖/夹具使基线可运行；不能屏蔽异常当通过。结构化导入冒烟不能替代真实patched方法执行和dispatch/commit断言。

### 8.3 模型切换及上游未知

当前配置切换使用网页例外许可，与运行中provider配置、最终HTTP和审计revision对应；模型不支持reasoning_effort时在已有配置校验拒绝，不自动降级到未知参数。兼容矩阵按alias+endpoint+SDK格式版本记录；探针仅下一轮获得授权后在隔离账户运行，不主动发QQ。

上游满前缀0：新增endpoint/非秘密headers绑定指纹、provider/credential身份不可逆指纹、模型实际响应别名、明确usage来源、前一可比较attemptId和间隔。禁止记录认证头值。日志区分本地断裂/完整且0/未报告/失败取消。向服务商提供request时间、ID、脱敏哈希证据后，仍不可见的节点/TTL标unknown；不为此换路由或增加预热请求。

## 9. 防回归验收矩阵

每行均保存修改前基线与修改后同输入结果，包含最终HTTP消息、可还原当前上下文、后端工具权限、实际dispatch次数和终态。离线fixture来自脱敏真实请求，网络/QQ由可控stub替代；上游命中另行真实授权验证。

| 类别 | 必测场景 | 客观通过条件/负面断言 |
|---|---|---|
| 最高护栏 | 1–34轮、大量后台调用、工具7↔10、不同speaker、大小/idle边界、失败重启 | 全部system向量恒定；未获35/web许可逻辑重构次数0；无通过换scope/clear/bootstrap绕过 |
| 35轮 | 普通第35轮成功、生成失败、DB回滚、big合并、同水位重复任务 | 只有真实35轮成功事务签发一次许可；两阶段最多各消费一次；big/失败不冒充 |
| 网页例外 | 合法用户保存、他租户保存、body伪造来源、自动revision/续租、并发expectedRevision | 仅真实对应bot的认证网页修改允许例外；旧候选不可提交；配置实际生效与最终HTTP一致 |
| 缓存连续性 | 正常追加、满/部分前缀、工具续调用、获准边界重构 | 已提交且合法前缀逐消息不变；未变system/tools/参数分别证明；不能把本地相同对象当服务端命中 |
| 体积与增长 | 真实35轮、群私交替、高活跃、多图、长工具结果、大反馈 | 必要字段完整，35轮前正常轨迹零容量重构/预算阻塞；每轮与累计体积不回退；单一巨大合法输入明确失败而非截必要内容 |
| 历史一致性 | 35轮覆盖、前台30窗口、群13条、摘要合并、遗忘、检索遗漏 | 重要约定在下一请求确实可见；已忘正文不进入任何角色；工具调用与回执邻接完整；未知内容无静默丢弃 |
| 并发与失败 | A慢B快、旧epoch、取消、超时、500、解析失败、摘要在await中提交 | 旧候选不覆写新基线；普通失败不清成功历史；已执行副作用不重发；过时权限/Work不执行 |
| 身份权限 | 不同QQ、主人/非主人、群私、跨租户、服务sender0、伪造标记 | 当前真实sender正确、非主人无法借旧权限；后端实际拒绝非法操作；动态可信角色未降为user |
| 模型与工具 | 不同alias/endpoint、developer兼容、stream、ToolLoop、schema增减 | unsupported明确拒绝，不能静默改role；每个tool_call有匹配回执；工具顺序与参数可审计 |
| 输出发送 | 正常中文/英文/中英、Planning等标题、分析后正常英文、代码引用NO_REPLY | 正常文本不误删；确定reasoning不拼content；沉默reason准确；history bytes不因新过滤改变 |
| 媒体/OutputPlan/ACK | 纯图、纯语音、At、4分条、部分送达、unknown ACK、已执行工具后空答 | 仅有效ACK记sent/confirmed；未确认不当成功；无自动重发；原外部操作次数不增加 |
| 资源 | 内存、CPU、JSON复制、renderer成本、日志与快照IO、请求大小、延迟 | 峰值RSS/CPU/延迟给改前后分位；35轮长轨迹不无界；预算、日志和快照上限有效；退化超门槛拒上线 |
| 生命周期 | 进程重启、损坏/旧版本快照、8+会话、共享AstrBot、长时间运行 | 不借重启绕护栏；恢复绑定正确；无跨bot污染；缺失快照明确受阻而非伪造连续性；正常重启路径可用 |

资源门槛应在阶段0冻结真实基线后定数值：默认相同内容的峰值请求字节、未缓存Token和峰值RSS不得变差；处理CPU/延迟超过基线10%需解释并经专项验收。若为了无损精简引入合理局部CPU开销，必须以总成本、TTFB及质量证据评估，不能自动用10%当硬性能真理。正常回复误删、跨租户、已忘信息、权限错误、重复副作用、非法提前重构均为**零容忍**，不能用平均指标抵消。

记忆质量集至少包含：未成fact但明确的重要约定、群私同人约定、不同人物同名区分、被纠正事实、已忘事件、unknown回执、已确认外部操作、未完成Work、延期任务、摘要覆盖边缘第34/35/36轮。每例标原事件、目标会话与下一请求所需证据路径，检查可见性并由行为输出验证；不能只看DB还有行。

## 10. 分阶段实施顺序、验收与回退

## 11. 缓存、费用、资源和质量评价

单位以每真实35轮周期、每Work、每阶段及同一有效model/endpoint/config身份分层；另给全量真实流量加权汇总。至少列：input/cached/uncached/output，usage未知率、explicit0率、首差异分布、合法/非法重构数、system变更原因、每轮新增/累计字节、TTFB/p50/p95总延迟、失败/沉默/sent/ACK、峰值内存/CPU与恢复IO、必要记忆可见率和回复质量。

费用采用实际代理账单价格及模型usage，不用字数/3；失败取消费用若无账单标unknown。R4窗口仅能用`1.422586×P_u+6.434242×P_c`估算输入费用（价格每百万Token），不是日/月预算，也不是可保证节省额。正常新增必须与重建反事实分开；离线重放能证明内容/前缀，不能证明服务端节点相同或未来cache一定命中。

优化收益以**信息完整且护栏成立**为先决条件。请求变短、未缓存费用下降而召回变差、身份错误、误吞正常文本，都判失败。反过来，必须保持的可信变化导致上游命中下降时如实报告，不能冒称全修好。既有高命中轨迹应原样复测，确保不会因新版alias、common字段或角色转换退化。

生产监控要能在单个异常发生时定位：哪个35/web许可、哪个baseline/candidate、哪个最终HTTP首差异、哪些系统字段类别变化、usage是否明确报告。禁止只汇总一个全局命中率。内容抓包仅沿用户授权的既有私有受限入口，默认用哈希、计数、固定原因枚举。

## 13. 最终可执行任务清单（依赖顺序）

1. 冻结新一轮生产加载版本、实际配置及本地脏差异；备份三个候选补丁，按SHA提取最小差异。
2. 核对真实35轮业务水位与网页PUT配置审计链，写入测试合同；不再以模型调用次数代替。
3. 建立两类P0失败回归：非35/web system或上下文重构；正常英文/媒体误吞。修复可执行行为测试环境。
4. 建立每轮committed/attempted/final体积与record-by-kind账本，保留上下文完整还原oracle和既有高命中轨迹。
5. 实现固定格式指南和同来源正文单份的最小可逆精简；再按收益实施表结构共享与增量稳定，验证35轮容量。
6. 定义并实现35轮成功事务checkpoint、真实网页编辑许可、system向量guard、候选依赖fence与有界恢复；正常轨迹有阻塞则不部署。
7. 在隔离环境验证可信动态角色；通过后改request_context_view与所有前台/内部/外层入口，保持system恒定、后端授权和工具邻接；不支持则暂缓该项。
8. 分离model_cache观测、沉默reason与输出处理；修正候选过滤设计，保证正常文本/媒体/ACK/历史前缀不受损。
9. 跑完整矩阵与长轨迹改前/后对照；可选记录分块只有在额外收益明确时实施，再重跑受影响矩阵。
10. 下一轮获得隔离真实模型验证授权后测Token/角色/上游缓存；未知项保留，不主动请求QQ。
11. 完成Plan vs Actual：原要求→文件/函数→测试/实际结果→偏移及未完成项；任何硬护栏项不得用测试通过数量替代。
12. 取得明确部署授权后，在合法边界仅发布受影响组件；记录加载版本、监控完整35轮周期，按合规回退预案处置。

本计划没有选择后立即实施任何候选方案。只有在35轮最高护栏、必要信息完整、可信身份权限、正常回复及副作用一致性同时得到验证时，才具备交付整改版本的条件。
