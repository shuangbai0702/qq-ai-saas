- `tests/bilibili.test.ts`：新增签名缓存生命周期、取消、无效材料、风控不重试及完整搜索链路测试；已有模拟 nav 的非真实格式 key 改为 32 位十六进制测试值。

同一会话连续两次签名搜索，原本各需一次 nav，现在在有效期内合计一次 nav + 两次搜索。缓存没有存储搜索内容，也不合并跨 Work 的任务。没有改变任何模型提示词、内外层调度、记忆合同、冷却时间或权限。

HTTP 412/429 及现有平台风控码仍停止任务，并保留已有 15 分钟服务冷却。该冷却时长是 FishBot 的保护策略，不是 B站返回的解封时间。没有自动降为匿名、改 IP、伪造浏览器指纹或自动重试。

旧接口与现有签名搜索不一致是已证实现问题；它是否就是此前 HTTP 412 的唯一原因，没有证据。新接口当次成功也不能证明以后永不风控。

## 协作缺陷一：新目标的来源丢失

`apps/node-agent/src/autonomous.ts` 中：

1. 读取 `goals` 快照。
2. 模型决策通过 `commitDecision` 创建新目标和动作。
3. 随后却仍用旧 `goals.find(...)` 查该动作对应的目标来源。

新目标不存在于旧快照，本轮交给内层的 `sourceScope` 因而为空。实际研究动作的持久目标具有正确的群来源，但执行反馈中 `sourceScope` 为空。这个缺陷影响“这项工作是为哪段群对话做的”的上下文衔接，而不是 B站登录身份。

建议后续从本次事务返回的已接受目标或带租户校验的最新持久记录取来源；不要让模型自行声明可信会话归属。**尚未修改。**

## 协作缺陷二：群里的研究经历投影不完整

`adapters/astrbot/bot_pipeline.py::experience_context` 有两处相关边界：

- 相同来源群只会通过排除不同群的检查，随后仍要求 `target == scope`；research 动作通常没有发送目标，因此即使有正确 `sourceScope`，也可能无法出现在来源群的动作经历中。
- 本地 `pipeline_actions` 记录无条件覆盖同 ID 的 PostgreSQL 动作投影。PostgreSQL 通过关联目标可以得到正确来源；本地 task 若缺来源，就可能替换掉较完整的记录。

建议只让权威来源决定可见范围，并按字段来源、阶段及新旧程度合并同一动作。来源群可以看到自己的研究事实，不等于其他群或其他租户可以看到私有任务。**尚未修改。**

## 协作并非完全不共享记忆

`packages/database/execution-memory.ts::ExecutionMemory.recall` 已从同一份工具台账读取结果，通过动作关联目标恢复来源群。前台 `behavior.py` 会请求该执行经历投影。

因此不能说“内层完全看不到后台做过的查询”。第一次搜索的候选在当前设计中可被来源群召回；实际回复也包含相同三个候选。由于没有保存完整的那次模型输入，不能把“可召回”直接当成“已证明完整输入已送达且模型理解了”。

目前该投影是有界的事实视图：默认 6 条、总体约 6500 字符，搜索仅保留前三个候选，不带原始查询词。它包含操作、状态和时间，但不能完整回答“这项工作与当前提问是否相同、是否已有人负责给出最终答复”。

## 协作缺陷三：新 Work 没有同主题工作衔接

稳定 action ID 和写入幂等主要阻止同一动作重放，并不等于不同 Work 的语义任务自动合并。第二条真实用户请求创建新前台 Work，执行器可以合法地再次读取。

后续建议分开处理两个职责：

1. 工作事实：展示正在处理或刚完成的任务、可信来源、时间、查询摘要及回执，供内层判断是否继续查、直接回答或补充查询。不能把“任务已登记”说成“已经查完”。
2. 只读请求复用：以 tenant、bot、账号修订、操作、规范化参数及短时新鲜度限定复用范围。读请求共享不改变发送许可；评论、私信等写入不能套用搜索缓存。共享在途请求还需明确真正的请求 Owner，防止一个消费者取消而误伤另一消费者。

这两项涉及内外层和跨 Work 协作，**按用户要求，本轮均未实现**。不建议用“外层必须联系主人”或“不要再查”之类固定提示词掩盖归属和状态缺陷。
