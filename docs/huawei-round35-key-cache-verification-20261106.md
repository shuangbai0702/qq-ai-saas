## 26 号连接失败的实际原因

URL 和模型可用，但保存的 Key 末尾有两个空白字符。Node 的 HTTP Header 路径自动处理了边缘空白，因此连通性探测能成功；实际 Python OpenAI SDK 的 HTTP Header 校验拒绝该值，在发出 HTTP 请求前抛出 `LocalProtocolError`，外层表现为 `APIConnectionError`。

已对该账号加密保存的 Key 去除末尾空白，并通过普通配置修订和 apply 接线生效，没有替换其他账号凭证。相同 Python 解释器、SDK 和受控传输层的实际请求成功；随后真实自主 orientation 请求完成。

API 创建机器人和保存模型配置共用 `modelKeyInput`：边缘空白 trim，内部空白及控制字符拒绝。其他服务凭证没有借本次任务批量改写。

## 尚未收口的构造问题

真实旧采样已证实，前台 system 前部会因签名提示是否启用、当前作者、合并消息提示及 `context_references` 是否出现而变化。调用链为 `behavior.inject → request_context_view → 原生 provider 装配 → readonly_journal.prepare`；journal 对原生前缀要求精确一致，因此这类变化会触发安全重建。摘要/核心便签发生真实更新也应重建，不能全部作为异常消除。

目前尚没有上述每一条历史请求的完整原始请求体，不能把所有 `native_prefix_changed` 进一步归因到同一个字段。已为两个机器人开启现有的 15 分钟、每号最多 8 次原始请求采样；不新增常驻任务，不主动发送聊天消息。原始数据仅留生产私有目录，不入仓库。

进一步核验最终 HTTP 请求哈希：26 号在 18:57:27 到 18:57:40 之间，工具定义从包含 `hosted_qq_publish / hosted_qq_signature / hosted_qq_view` 变为不包含这三项。工具顺序本身有序，实际集合变化；需要沿当前作者和真实授权检查其必要性，不能为缓存一律向所有人开放。18:59:35 工具哈希与 18:57:40 相同、路由字段也没有变化，因此该次上游零命中仍不能归结为这三项工具切换。小双白在 18:45:50 后至 18:47:17 的工具哈希和路由字段均相同，但仍出现多次前缀重建，进一步排除了“全是工具列表变化”的解释。

这项缓存问题仍在排查，尚未部署新的上下文布局修复。尤其不能为提高命中而冻结身份/权限、恢复过时摘要，或把上游未报告缓存数当成真实零。现阶段的结论是：确有前台构造不稳定现象，部分重建属于必要失效，且至少一条本地具有相同前缀而上游报零的请求仍需独立核验。
