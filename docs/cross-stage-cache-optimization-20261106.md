# 外层梳理与规划：跨阶段缓存优化

## 范围与方案

针对用户 05:34 的约 42K/44K 外层请求：原来两阶段各有连续历史，阶段特有提示词位于大段资料之前，并使用不同缓存路由。各自后续可高命中，但首次规划无法利用刚刚完成的梳理前缀。

现在固定人格、通用规则、可信身份与工具权限前缀；阶段合同以平台运行时消息定义一次，之后短消息选择。两阶段共享同一机器人缓存路由，但仍分别延续已有有界历史；冷阶段可借用另一阶段已完成历史，通过原有 scope/system/摘要校验后才复用。模型结果不成为执行回执，工具权限和 Work 校验没有改变。

## 实验与取舍

使用用户自己授权的 aiapi.codes / gpt-6-luna / medium，读取其真实外层捕获资料，隔离调用模型；无工具执行、QQ 消息、目标提交或生产学习写入。每个回答通过当前生产 OrientationSchema / DecisionEnvelopeSchema，逐请求无损还原最新输入。

| 方案 | 首次规划 | 后续梳理 | 后续规划 | 处置 |
|---|---:|---:|---:|---|
| 原布局对照 | 缓存字段未报告 | 99.60% | 99.09% | 保留为对照 |
| 共享连续历史、后置 system 合同 | 未报告 | 18.70% | 17.67% | 拒绝上线 |
| 共享连续历史、运行时合同 | 85.93% | 93.62% | 93.94% | 拒绝上线，交替状态增长偏多 |
| 冷阶段借用前缀、后续独立追加 | 85.81% | 99.19% | 98.81% | 最终候选 |

最终候选原始 usage：梳理首轮 47,247 输入（缓存字段未报告）；规划首轮 54,896 输入 / 47,104 缓存；梳理次轮 47,488 / 47,104；规划次轮 55,315 / 54,656。后两轮未缓存分别 384 / 659。对照后两轮分别 190 / 516，候选有小幅合同与路由开销，不将命中率提高描述为每一次成本都下降。首次规划已实际复用 47,104 token，主要收益在冷阶段首次请求；对照冷请求缺失 cached_tokens，不能冒称精确费用节省百分比。各模型输出与时延不同，四条请求不能证明 P95 或长期服务商费用。

第一版虽有完整线缆前缀，实际缓存仍低，说明仅检查消息相同不足以验收；后置 system 影响上游处理是推断，未取得服务商内部证据。最终方案未添加显式断点、不支持字段或生产预热。

## 实际修改

- autonomous_runtime.py：共同系统装配、真实阶段诊断、共用路由及冷阶段借用；继续使用原始租户/实例/provider/epoch/摘要校验。
- decision_history.py：已有 AppendHistory 接收可选平台阶段合同，定义去重并选择；不改变源记忆。
- model_cache.py：明确支持 deliberation 作用域，仍绑定实际 provider 和租户/机器人。
- 相关测试：完整前缀、最新状态还原、合同去重、路由隔离、取消、权限变化后的退休、正常投递和回执边界。

## 验证与 Plan vs Actual

本地及 Linux 隔离管线已执行；最终追加的取消分支独立和新权限不得借用旧分支测试需以最终日志为准。生产部署结果另补。

原计划共同前缀和跨阶段复用已经实现；实际保留两个阶段分支，而非让所有阶段一直串在同一日志上，因为真实测试证明后者重复新增较多。该偏移保留现有两份有界传输历史，避免建设新记忆系统，并恢复各阶段热缓存。未改前台、摘要、主动目标、工具权限、QQ、前端或内存策略。无 Git 写操作。

未知：长期自然流量缓存、P95、提供商实际账单及更换上游后的兼容性；隔离模型实验不能替代这些生产验收。
