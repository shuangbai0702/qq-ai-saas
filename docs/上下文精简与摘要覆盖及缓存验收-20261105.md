# FishBot 上下文精简、摘要覆盖与前缀缓存验收

日期：2026-11-05。范围：现有上下文管线、执行经历、原生历史与摘要衔接、请求前缀布局。没有执行 Git 操作，没有覆盖并行前端成果。

## 结论与证据边界

有效的主改动是：压缩历史执行叙述；为实际请求中的引用、图片及完整回复补齐摘要材料；摘要成功后再投影移除旧历史；把动态可信上下文从请求前端移到当前用户消息附近。真实身份仍为 system 信息，不降为用户正文。

固定执行经历样本约 7,457 → 3,687 个 cl100k 估算词元，减少 50.56%。另一份原生历史仅通过精简生成的图片路径说明，用户侧文字 18,593 → 14,596，减少 21.50%。两者不是同一分母，不能相加，也不是全部请求或账单的节省比例。

缓存布局的 468 次合成请求回放，在 TTL=300 秒、块=64 tokens、常规间隔条件下，输入加权命中率 57.57% → 82.38%，未命中输入减少 58.34%。这是模拟，不是线上稳定命中率或费用承诺。缓存过期时收益会显著减小。

对“本轮状态也按较早内容在前排列”做了额外实验：保持所有值和列表顺序不变，仅重排对象字段及规则位置，结果 82.38% → 82.33%，没有净收益，未部署此方案。没有引入保存过期状态的追加日志或第二套上下文池。

另一项小优化是 JSON 结构分隔符紧凑化，前台与内层两个组装入口一致；外层主决策原本已经使用紧凑分隔符。它不删除字符串里的空格、换行、正文或字段。独立回放总输入减少 1.66%，同条件未命中输入减少 7.45%；用户授权测试接口单对请求计数 6,042 → 5,964，约减少 1.29%。这项的价值小于前缀布局，不与其他百分比相加。

## 1. 当前上下文的权威与调用关系

主路径：协议真实身份/Work → ContextBuilder → 现有记忆与近期记录贡献 → 公共 provider 注入 → AstrBot 原生 ToolLoop → OutputPlan/投递回执 → 成功轮次及整理提交。

| 层 | 当前职责与处理 |
|---|---|
| 固定人格、平台规则、工具合同 | 放在稳定部分；不为缓存修改权限或启用未授权工具 |
| 原生用户、助手及工具历史 | 按原有会话使用；请求视图精简生成说明；原始数据库不被改写 |
| 核心便签 | 唯一一段，最多 300 字符，固定读取；不是身份或权限来源 |
| 大、小摘要 | 大摘要最多 1,500 字符；普通摘要最多 800；三个小摘要并入大摘要后清空；读取沿用已有跨会话来源规则 |
| 事实、人物、兴趣、表达与情绪 | 使用现有存储和召回；本轮没有另造记忆系统或改衰减规则 |
| 当前可信身份与状态 | 移至当前用户消息附近，仍为 system；每次请求使用当前事件绑定的有效快照 |
| 执行经历 | 读取实际动作和回执；历史描述简化，当前任务、证据和未知状态不靠摘要猜测 |
| 外层自主决策 | 使用同一记忆来源，原本为稳定 system 加当前结构化 payload；不把所有原生内层工具历史再复制一遍 |

摘要门槛沿用当前代码：每个会话范围按成功回复轮数配置，默认 30，允许 30–200。群聊旁听、轮次关联及 15 条样本规则继续由现有存储控制。本轮没有为提高缓存而延迟摘要、累计虚假轮次或保留无限历史。

“当前快照”不等于每次调用都重新写兴趣。一次工具任务可能多次调用模型，工具反馈会追加；长期记忆通常只在正常整理或有新证据时更新。当前任务发生换代、遗忘或租约失效时，保留既有取消保护。

## 2. 发现的问题与实际修复

### 执行经历重复叙述

`context_transport.experience_view` 在模型视图中限制旧目标、理由、摘要与工具说明的长度。保留动作 ID、目标对象、来源、真实状态、证据、错误和未完成项；显式 null 时间仍表示未知。入口在 `bot_pipeline.experience_context`，前台、内层和外层共用。完整账本不修改。

### 原生历史与整理材料脱节

此前普通整理记录不一定包含最终送进模型的引用正文、图片，也可能只保留截断的助手答复。新增 `summary_material.py`，附着在既有 reflection SQLite：

- 从严格的协议来源包装识别 scope、作者和 event，不从引用正文猜身份。
- 在共同请求准备边界捕获真实模型视图，图片沿用最长边 384 的既有处理。
- 成功发送后补入完整确认回复，避免旧的 800 字符清理结果代替完整答复。
- 图片在摘要阶段做有界证据整理，再由原有摘要请求综合，不每次聊天单独识图。
- 保存摘要、覆盖证明及清理待整理材料在同一事务中完成；失败或异步迟到不提交证明。
- 大摘要合并时迁移覆盖证明；主动遗忘、删除摘要及轮次清理保持对应失效。
- 修复了旧 pending 恢复记录没有 memory_round 行时，依赖触发器无法清掉 staging 的遗漏：摘要成功后明确清理该批材料。

覆盖证明必须匹配 scope、作者和原始用户内容摘要。只有证明完整且不是当前问题时，才把对应历史块移出模型请求。最新用户消息始终保留。工具调用及返回成对保留，不切断调用链。

**保守边界：** 当前普通用户材料证明不代表任意工具结果也完成摘要，因此含工具调用/结果的整块不会仅凭用户证明删除。尚未实现任意工具历史的完全覆盖压缩，不能宣称全部超长内容都已清空。

材料单段文本及回复上限各 64,000 字符，图片材料每轮最多 4 MiB，单机器人 staging 总量 24 MiB；超限、缺媒体或缺来源时不生成虚假的完整覆盖证明。每批图片调用最多八张、有限超时，失败保留原材料。没有增加常驻服务或高频后台扫描。

### 旧历史恢复

对用户之前要求配置记忆的机器人，从仍留存的原生档案恢复了八条旧的、确有成功 QQ 回执的来源，与原有 23 条成功轮次材料合并为 31 条待整理材料；没有造消息、补轮数、即时调用模型或改原生档案。

后续又补齐这 31 条材料留存的完整助手回复，共 6,968 字节。操作前 SQLite 在线备份；检查 epoch、作者、事件、摘要值和 confirmed/message_id，未通过的不补。23 条成功轮次保持不变。下一次正常到达门槛时由现有整理入口处理，而非伪造已完成摘要。

最后线上读取：该机器人 23 个待计数成功轮次、31 条材料，约 2.74 MiB；覆盖证明仍为零。**这明确表示真实的新摘要周期尚未发生，不能将测试中的摘要成功冒充生产已经压缩。** 已不在原生档案中的资料无法凭空恢复。

### 早变动字段破坏请求前缀

原先动态 system 会插在原生人格和完整历史前面。现在公共 `request_context_view` 保持稳定规则在前，把最新可信上下文放在当前 user 前；ToolLoop 当前 user 已存在时，插入位置仍在该 user 前，不插到 assistant.tool_calls 与 tool 之间。

对旧式直接传 tool_calls_result 或非标准 contexts，保留原布局回退，优先协议兼容。前台普通与流式、内层执行使用同一边界；条件式群参与提示、当前作者、签名提示跟随当前快照，不伪装为永久固定规则。工具列表顺序没有随意重排。

## 3. 缓存文档、源码研究和模拟方法

官方依据：[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)。结论是复用实际渲染后的共同前缀，而非请求里任意位置出现过相同文字。DeepSeek 当前描述的是持久前缀单元及共同前缀检测；没有公开保证一个适用于所有代理的固定 TTL。下述 TTL/块大小只用于敏感性分析。

研究副本在工作树外的 `../qq-ai-saas-research/context-cache-20261105`，不进入生产依赖。

| 项目与固定提交 | 实际用途 |
|---|---|
| [agentic-coding-analysis](https://github.com/callanjfox/agentic-coding-analysis/tree/15e88f72f902c7852c330caf2cc11722e5dbc1aa) | 读取 CompleteCacheSimulator，作为回放主工具；MIT |
| [kv-cache-sim](https://github.com/theraihanrakibb/kv-cache-sim/tree/674580b34a835aa2e662ec14b69e0ae94458db29) | 实际 PrefixCache/NoCache 独立交叉核验；MIT |
| [vllm-local-benchmarks](https://github.com/wojciech-wais/vllm-local-benchmarks/tree/30971f32894deedd7ee60517376ac6f656161f22) | 比较前缀长度与时延实验方法；没有在 2GB VPS 安装 vLLM 或声称做 GPU 测量 |

主模拟器原始分块若独立匹配，存在把不同前缀分支错误拼接的问题。研究适配器改用链式哈希；负例 A+B、C+D 之后请求 A+D，只能复用 A。kv-cache-sim 直接接收相同的预分词轨迹，避免它另一个基于 Python hash 的文本编码影响比较。

轨迹通过真实 FishBot provider 包装及 AstrBot payload 准备生成；模拟三个机器人、六个会话，每会话 65 轮，390 个聊天请求及 78 个工具续步。每 30 轮触发合成历史压缩边界。优化前轨迹在改布局前保存，不用新代码冒充旧基线。逐项核验 468 对请求：非 system 历史、可信上下文值、工具 schema 及顺序相同。

限制：cl100k 为近似分词，不是服务商私有分词与渲染；没有模拟私有路由、全部缓存容量、真实并发驱逐、TTFT 或账单。

| 条件 | 旧布局命中率 | 新布局命中率 | 未命中输入减少 |
|---|---:|---:|---:|
| TTL 300s，块 64，常规间隔 | 57.57% | 82.38% | 58.34% |
| TTL 300s，块 256，常规间隔 | 56.70% | 81.16% | 56.35% |
| TTL 300s，块 64，间隔扩大八倍 | 36.61% | 37.85% | 1.64% |

常规条件下，普通聊天 49.67% → 79.31%；工具续步原本已有 98.33%，新布局为 98.23%，不能声称每类请求均提高。输入总量 3,869,484 → 3,881,652，增加约 0.31%，源于可信上下文包装，而非删掉业务内容制造命中率。

额外排列实验保持同一轨迹的全部内容：本轮对象字段重排 82.33%，本轮 JSON 放到动态规则之前也是 82.33%，均未采用。没有为微小且不确定的收益更改模型所见语义或持久化结构。

## 4. 真实 API 验证与授权纠正

最早十次隔离探针使用了既有机器人的绑定凭据，共 39,872 输入、32 输出 tokens。用户指出后已承认此处授权选择不当并停止使用；旧读取机器人凭据的探针入口现已禁用。它们没有 QQ 发送、工具副作用或生产配置改写。历史测试证据保留，但不能以此授权继续使用他人 Key。

最早八次缓存 A/B 的全样本命中率 27.20% → 60.76%，剔除各自首个冷请求后 36.04% → 80.52%。这是小批合成输入，候选时延没有改善，不能证明正常聊天 P95。

之后只使用用户明确提供的独立测试凭据。实际发现 `/dashboard/v1/models` 返回网页，真实 API 是同域 `/v1`；模型列表提供 `deepseek-v4.1-flash`。凭据仅保存在忽略的本地私有测试文件，未写入任何机器人配置、报告或 Linux 生产账号。

- 第一批八次：48,426 输入、637 输出 tokens；候选连续三次各明确返回 4,096 cached tokens。其余五次缺少缓存字段，按“未知”处理，不能直接宣称未命中为零，也不能计算可信的完整 A/B 命中率。
- 第二批两个格式对照请求：相同结构化内容，spaced 6,042、compact 5,964 输入 tokens；各 128 输出 tokens。
- 合计十次：60,432 输入、893 输出 tokens，没有执行工具或 QQ/B站写入。
- 接口在请求 thinking=disabled、max_tokens=8 时仍返回推理 tokens，存在兼容差异。这批只验证请求计量与缓存字段，不作为回答完整性或正常推理性能验收。没有增加重试。
- 用户所说“20额度”的计费单位、余额及账单未得到可信接口证明，因此不换算货币，也不声称已精确核对扣费。测试已结束，不继续扩大付费矩阵。

覆盖点包括：90 轮三次小摘要再合并大摘要、SQLite 重开、遗忘、失败识图、同图去重、迟到 epoch、旧 pending 与正常轮次合并清理、长回复尾部进入摘要、跨 scope/作者/摘要值不匹配、当前 user 不删除、工具调用顺序及配置换代取消。

后续只读检查发现一个机器人 revision 从 7 变成 9、generation 不变。最初“必须等于部署前版本”的检查因此失败；保留记录，没有回滚该新配置，也不冒称此后所有配置一直不变。源码哈希仍一致，QQ 与 Agent 没有重启。只读检查本身没有配置写入；现有证据不足以归因该配置变化。

格式精简后续发布及最终 PID 以本文末尾的最终发布补记和部署记录为准，不能拿旧 PID 当作最终状态。

## 6. Plan vs Actual

| 原要求 | 实际结果 | 状态/偏移 |
|---|---|---|
| 高强度精简执行经历与重复说明 | 共同模型视图精简，原账本不改，固定样本减少约一半 | 完成 |
| 需要摘要的内容进入摘要再移出池子 | 捕获引用/图像/完整答复，成功提交后按证明移除 | 代码与隔离验证完成；真实新周期待触发 |
| 全上下文检查类似遗漏 | 修复旧 pending 清理、旧回复截断、覆盖查询按事件限量；核验大/小摘要共同读取 | 完成此范围；任意工具历史完整压缩仍有缺口 |
| 比较开源缓存方案、先基线再优化 | 三个固定版本研究；实际 payload 回放与独立实现交叉检查 | 完成；商用缓存私有实现不可完全复现 |
| 用真实接口确认收益 | 历史小批与用户授权独立接口验证均保留 | 部分完成；缺少完整账单及正常流量 P95 |
| 不影响稳定性与原有能力 | 权限、消息内容、摘要轮数不变；Windows/Linux 回归及在线进程核验 | 当前证据通过；不等于长期稳定性已证明 |
| 探索进一步缓存优化 | 两种排列无益不采用；紧凑序列化作小项验证 | 不以命中率数字牺牲新鲜度或累积无限历史 |

明确保留的偏移：移出的是后续模型请求视图，原生数据库档案保留以便核对/回退；含任意工具证据的块保守保留；旧资料只恢复有真实回执者，不修改成功轮数；图片整理会在正常摘要阶段额外调用有限模型请求，不能说完全零额外 Token。

尚未验收：线上带真实图像的新一轮完整摘要与其质量、普通流量长期命中率及费用变化、正常聊天 P95、2GB 容量压测。本轮没有借口把模拟通过填成这些项目完成。
