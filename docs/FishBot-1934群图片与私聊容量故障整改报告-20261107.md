## 2. 已证实的根因

### 2.1 私聊提前撞到相对容量门槛

大肥鱼在19:33多次出现`ContextCapacityExceeded / request_not_sent`；梁沅芷19:25存在同型失败。保存的上下文文本分别约293313、293055字符，距既有384000文本总上限仍约9万字符，wire也未达到2MiB上限。

实际触发的是“相对最初基线增长超过256000字符”的额外门槛。这不是供应商已返回上下文超限，也不是35轮护栏允许清理历史。没有合法许可时，旧实现只能拒绝请求，导致原本尚有总容量的会话提前阻断。

Journal内部46/27等计数不等于35个可签发许可的完整业务轮次，不能据此补签检查点。

### 2.2 新图与文字来自同群不同人

观察账本显示，文字“这是什么玩意”约19:33:38到达，另一人的图片约19:33:40到达；19:33:44组装请求时，该图已被机器人观察。

原`attach_recent`只选同一发送者的图片，因此文字提问没有带上这张同群新图。该轮user消息确实无`image_url`；请求中虽有6张历史图片，也不能证明模型看到了本次新图。没有证据支持把这次问题归因于QQ丢图或原图下载失败。

### 2.3 Hold使pending登记条件自相矛盾

摘要事务写入Hold后，又要求范围内完全没有Hold才能进入检查点登记分支。因此真正需要`pending_coverage`的批次反而无法登记等待身份，设计中的闭环不完整。

本次没有从旧摘要数量推算、回填历史检查点，也没有替丢失证据伪造coverage。

## 3. 实际修改

| 模块及路径 | 最小修改 | 保持的约束 |
|---|---|---|
| `decision_history.history_boundary → readonly_journal.prepare/commit` | 为共用容量判断增加默认开启的增长限制参数；ReadonlyJournal关闭相对增长门槛，使用原有总容量边界；诊断同步反映实际余量 | 总文本384000字符、wire 2MiB不变；其他DecisionHistory/AppendHistory调用默认行为不变；硬边界仍需合法许可 |
| `incoming_media.attach_recent → quote_reply.media_catalog/resolve_media` | 在既有同发送者规则之外，允许附带一张同群45秒内最新观察图片，并标出真实作者、消息、时间和“仅供判断关联” | 当前会话、QQ账号、generation及get_msg来源复核保留；QQ域名限制保留；不跨群或私聊，不接受模型自造URL |
| `memory_reflection.retry → _promote_pending_checkpoints` | 35个全新完整业务轮次的摘要事务可以登记等待行；存在Hold时保持pending。晋升同时检查等待清单coverage及整个through范围内的Hold | pending不可reserve、不能退休旧wire；等待清单最多64项，范围检查防止未列出的Hold被忽略；lost证据仍阻塞 |

图片来源说明只追加到新请求，不重写旧消息。模型判断是否相关，程序不通过关键词猜测图片意图，也不把图片归给当前提问者。没有新增AI、记忆库或常驻状态机制。
