## 根因与真实证据

1. 旧 `journal_storage.retire_archived_members` 将归档清理扩展到了活动 Journal。即使只清掉 `state.dialogue/recent_messages` 中一条旧动态记录，也会进入非完整 canonical 分支，删除实际消息中的整个 `FOUNDATION_CURRENT` 基础区及部分资料包。
2. `state.memory_foundation` 元数据仍在。后续复用又将元数据存在误当作模型可见基础区存在，因此不补入，形成持久化缺口。
3. `semantic_runtime.finish_semantic_batches` 重访已退休批次时也会调用上述清理，再将投影快照刷新到运行实例。这条路径不要求新的合法压缩检查点，越过了原主 Journal Owner 的标准重建流程。
4. 隔离复现：无旧动态记录时固定区 2→2；仅加入一条待清理旧动态记录时固定区 **2→0**，元数据仍保留。
5. 生产备份对照：20:33、21:24 和 21:51 的模型实际消息固定区均为 0；33 条消息是 57 条的精确前缀，57 条又是 159 条的精确前缀，System 向量一致。故不能将该缺失归因于本次换模型；缺口在换模型前已经存在。首次误删的精确时间尚无直接证据。
6. 之前不回复另有独立原因：旧模型发生上游超时；随后错误模型名称产生 NotFound。修正为合法模型名称后已有真实回复。此次未擅自改回模型，部署时保留用户最新 revision 34。
