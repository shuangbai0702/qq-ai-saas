# FishBot 主动模式架构收敛与35轮压缩健壮性：调查与整改规划

日期：2026-11-14。状态：只读审查完成，整改尚未实施。

本轮没有修改业务代码、部署、触发生产压缩、运行或新增测试、发起模型请求、操作旧华为云，也没有启动子智能体。按中途明确要求单独在 AGENTS.md 增加了“不做无必要旧版本兼容、旧数据不丢失不是底线”规则；本报告是另一项文档产出。原有六份脏测试及未跟踪材料未改动。

## 1. 结论与证据边界

**当前不是最终目标架构。** 自主时刻已经接续原主 Journal，但入口和执行身份仍绑定 Cycle/Action；调度器还会挑到期 Goal 执行，在部分结果后自动完成 Goal。Goal 读取工具也仍返回 Action/ToolEffects。不能把“使用同一 Journal”写成“整条执行链已经统一”。

**35轮是持续到期阈值，这部分已经实现；安全排空和失败恢复仍不完整。** 已有持久轮数、水位、退避、事件唤醒、原 writer 独占和原始输入队列，应复用。最需要整改的是：等待期间没有封闭的工作集合，可能长期饥饿；已提交摘要的无模型恢复被模型配置前置条件挡住；进程死在许可 reserved 窗口缺乏语义退休专用恢复；摘要提交被管理接口当成整项完成；媒体清理失败缺少独立可靠再唤醒条件。

源码基准：`01359ac231b8b6ed46fc70d1702b5c14aa21b9db`，加本轮 AGENTS.md 文档改动。最近生产发布记录仍是 `d277efbdef6f159ea889090804c0f6c592c73d99`；`ea70ce7` 删除兼容路径的发布因健康 IPC 超时停在 hold/替换之前。本轮没有重新连接生产测量实时健康或版本，因此下文生产事实均明确引用最近已有记录，不能视为本轮实时运行证明。

复用材料：四号强压与35轮排队处理结果、主线平台上下文精简实施记录、主AI/DSH完全委托规划及全局健壮性调查。旧报告中的时间冲突、双 Journal 兼容、完整目标基线等结论均对照当前源码重新判断，不照搬。

## 2. 当前真实调用链

### 2.1 主动与普通输入

```text
普通QQ输入 → native_ingress持久保留 → 原事件队列 → behavior.execute
  → Work/Scope准入 → shared_context.Writer → 主Journal → 模型/工具
  → 公共输出护栏/发送许可/协议回执 → 原Work结算与计轮

自主调度 → PG cycle/action → policy许可 → autonomous_runtime.execute(moment)
  → 本地pipeline_actions身份 → invoke/RunControl → 同一主Journal writer
  → 模型/工具/公共发送保护 → 本地执行结果 → PG Action反馈

旧到期任务 → dueHandoffs → goalAction/markExecuting → 独立内部任务执行
  → 回执/重试/自动completeGoal等调度语义
```

主要入口：`apps/node-agent/src/autonomous.ts:195–335`、`adapters/astrbot/autonomous_runtime.py:341–380,541–724`、`behavior.py:841–916,1739–1750,1947–1959`。

自主时刻的确进入主 Journal：`main_activation` 选择主 Journal key、原人格 System 和同一个 writer；不是另开思考 Journal。但普通 `behavior.execute` 的 `wait_compression()` 与内部 `invoke` 的准入不同。内部路径检查 active/waiting、预算和自主许可，然后增加 active；没有在同一入口等待 compression_active。writer 仍提供串行保护，故不能据此宣称已发生并发历史破坏；但压缩期间的新激活会提前登记工作，属于需要消除的准入分叉。

当前主动提示仍每次带 `necessary_goals(visible_goals(goalSnapshot))`，不是只发机会提示。`activity_context.encode_goal_candidate:201–239` 只修改新候选，保留当前非终结 Goal 的标题、原意、限制、revision、进度等；不再把历史 Action/Effects 全量基线带入该提示。文件中旧 `goal_delta`/完整 baseline 阅读合同仍存在，不能误认为这就是现行自动编码入口，也不应继续保留为将来回退方案。

### 2.2 35轮压缩状态机

```text
memory_rounds完成轮 − summary_watermark >= 35
  → reflection.retry选中到期Scope（失败退避仍从原表读取）
  → admission等待active/ingress/batches/waiting/Scope users/queued输入排空
  → compression_active=True → 取得原model_writer
  → 再读全部已完成轮（无LIMIT 35，因此可能36/37/更多）
  → 回采整批材料/真实来源、工具与媒体 → 有界模型摘要与验证
  → 单事务提交记忆产品/摘要/水位/checkpoint/semantic batch
  → 必要时先进行摘要产品合并，checkpoint由pending_merge变available
  → reserved → 原Journal精确退休投影 + consume许可 + batch retired + purge
  → 原生SDK历史/媒体清理 → 释放writer → 原输入队列恢复
```

证据：`memory_reflection.py:976–1040,1205–1232,1355–1470`；`behavior.py:110–136`；`semantic_runtime.py:116–177`；`readonly_journal.py:499–620,1087–1119`。

“持续待压缩”主要由持久轮数、水位与未退休 batch 推导，不需要再建一个计轮器。模型失败前已经写入 `memory_reflection_retry`，上限1800秒退避；正常失败不推进水位。Work完成等由 `RuntimeCare.stamp` 合并事件唤醒，既有60秒维护钟兜底，重启重新读DB。排空等待另有1秒超时复查；不应在此基础上再叠加高频循环。

## 3. 已有防护：保留而不重做

| 能力 | 当前证据与适用范围 |
|---|---|
| 超过35轮仍可压缩 | retry读取水位后全部完成轮；提交检查使用`>=35`。不是固定37轮批次 |
| 有效计轮与服务身份 | `activation_rounds.record/valid`复用原round表，激活在候选合法stage事务登记；服务不是人类发言，工具续接不另赚主动轮 |
| 失败材料保留 | 模型请求/解码/验证失败不提交记忆水位；取消记录失败来源，原材料仍在 |
| 请求超时有界 | `model_cache.py:26`摘要180秒；外层185秒；最多两次读取尝试，局部非流式回退不改变普通聊天默认流式 |
| Journal前缀保护 | 同一writer、stage SHA、序列化前缀检查；退休投影仅移除精确批次，其他输入及未结工具材料保留 |
| 原子持久化 | 语义退休候选stage内部消费许可、标记batch retired和purge；失败回滚。媒体unlink是事务后的独立可重试步骤，不能当作已同事务完成 |
| SDK旧历史复活阻止 | `semantic_runtime.install_native_retirement_guard`及Journal读取退休成员过滤，按精确来源拒绝复活 |
| 不重放未知外部写 | 既有发送回执、外部工具dispatch/unknown和预算预留；不是模型摘要可以替代的事实 |
| 时间锚点修复 | `f77932c`按完成轮精确身份处理捕获时间偏差；不再把这项已修问题安排重新开发 |
| writer取消所有权 | `shared_context.Writer.release`核对当前task；取消尚未获得writer的任务不会释放别人的锁。不能按普通无owner的asyncio.Lock误报 |

复核排除了一个先前疑点：`initiative.resume_scope_input:205`不检查`RuntimeCare.busy`，而是检查实际原生事件队列及该成员未完成事件任务。没有证据支持“reflection.task使care.busy为真，导致该恢复器永远不运行”的特定循环等待。不能把它列为已确认死锁。

## 4. 已确认缺口与源码推导风险

以下优先级是整改排序，不表示本轮在生产复现了每项故障。

### P1-A 排空集合不封口，可无限饥饿【源码确认缺少防护，生产未做持续输入复现】

`behavior.conversation_pending:110–114`统计不断变化的全局集合；`compression_admission:125–130`只有全部为空才立compression_active。等待期间普通输入、群批次、内部激活仍可加入，未见以到期时既有输入身份为界的准入屏障。只要新工作不断填充，永远可能没有空窗。

最小修复：复用原可靠输入队列和Work所有权，在35轮首次到期时固定一个可排空的接收边界；既有Work及其必要工具续接完整处理，边界后的新输入只入原队列，不开始新主线工作。完成边界前最后一个Work后，在同一调度临界区转交原writer。恢复时用既有队列顺序/业务身份重建边界，不建立第二队列或独立状态机。外部异步媒体尚pending但不占主线执行权时，不无限等待其完成；保留原责任及结果入口，完成事件按边界排队。

### P1-B 无模型的已提交恢复也被模型开关阻止【已确认控制流】

`memory_reflection.retry:979`先检查binding、memory/memorySummary、provider.text_chat_stream、is_current；之后才尝试checkpoint_callback和已提交batch恢复。关闭提取或Provider暂不可用时，明明已有合法摘要，仍可能完全不做剩余Journal替换与清理。

最小修复：把“已提交产物的本地恢复”和“申请新摘要模型请求”的准入分开；仍核验当前租户、DB、epoch、writer和许可，但已提交本地恢复不依赖模型可用或再次付费。新摘要无法请求时应保留到期与明确错误，不能标完成。配置关闭不能悄悄抹掉已产生的压缩债务。

### P1-C reserved许可崩溃窗口可卡住已提交batch【源码可达风险，未注入崩溃】

`reserve_context_reconstruction:415–467`以独立事务提交reserved，随后才stage退休Journal；只选择available。文档明确一般请求失联不能擅自退还许可。但`semantic_runtime:141–155`这条纯本地退休路径没有HTTP：若进程死在reserve提交后、stage前，异常处理无法执行，重启看到checkpoint不是available就持续pending。不能将一般“可能已发模型”的保守规则原样套到确定无HTTP的本地提交阶段。

最小修复：利用现有checkpoint的精确batch/digest、持久Journal SHA和stage消费事实恢复；确认未stage且该路径不可能提交模型时才能恢复原许可。已consumed或可能已提交模型的候选绝不盲目退款。不新增另一套许可表。

### P1-D completed口径过早，清理失败可能没有后续唤醒【已确认控制流，已有生产记录佐证残留】

`memory_reflection:1430`手动返回ok依据摘要提交及剩余round，`compression_admin:66`据此标completed，不要求Journal已consume、SDK历史和媒体清理完成。`semantic_runtime:177`恢复容量等待输入只看顶层pending，不看media/native状态；这可以表示主线可继续，却不能表示整批清理完成。

另外`retry:1013`恢复条件列举semantic_retirement/native清理issue，没有media pending/errors/protocol_unresolved；`semantic_runtime`也未在此处为媒体失败建立等价完成判定。若batch已retired且native干净、没有下一批到期，媒体残留不保证再次进入drain。`semantic_media:248–290`本身有重试数据和文件身份校验，应直接复用其状态，不重新做文件回收账本。

最小修复：原状态回执区分“摘要已提交、Journal已替换、清理待完成、完整完成”；仅全部必要清理闭环才声称完成。原维护事件读取既有媒体pending和issue驱动drain。与本批无关的未知协议素材需明确归属，不能扩大删除范围。生产备份/本地调查原文副本仍须按精确批次清理合同处理；旧报告已明确没有完成，不能因当前Journal变小宣称全清。

### P1-E 压缩准入未完全覆盖所有主线来源【已确认入口不同，具体竞态待验证】

普通消息在`behavior:855`等待compression_active；内部激活`autonomous_runtime.invoke:341–354`没有相同等待，可能提前创建内部Work/active再等writer。实际提交仍由writer保护，未证明历史被同时改写。应统一入口，由同一准入安排普通输入、主动激活、完成唤醒与工具续接，避免每个入口各补一把锁。压缩中的新激活只持久排队，不因busy直接丢弃或登记为已完成。

### P1-F 摘要/合并永久失败与过大基础区【部分已有保护，恢复策略不足】

Provider断网、无视觉能力、上下文超过上游限制、无效JSON/finish reason、输出截断、受保护资料不合规等都会合法失败并退避；失败不是错误退休的许可。到达第三份小摘要后可能进入pending_merge，后续大合并一直失败时，checkpoint就不能用于新基础区。当前流程仍可能反复提交同样必失败的材料，只有失败计数而无可执行修复。

`context_foundation.read:10–58`对facts有12000字符界限、styles有24条界限，但relations读取所有行；10个Goal的字段各可达12000字符，必要状态和未退休输入仍可能使新基础区很大。`readonly_journal.retire_semantic_batch:1101`有本地字符容量拒绝保护，但它不是实际Provider Token/视觉窗口证明。因此“生成了800字符摘要”不保证下次请求能发出去。

最小修复：错误分类后区分可重试传输与确定性准入失败；明确记录实际模型输入容量、媒体能力及最大输出。重建前测量完整候选（System、基础、必要保留项、媒体/Schema），对确定不可能成功的请求停止重复付费并保留待执行/告警。只有确实超限时才设计在同一合法批次内的有界提炼；最终产物通过后一次事务退休，不能提前压缩主Journal或删除必要事实。模型/预算不可用只能等待修复，不能“无条件成功”。

### P1-G 容量等待与35轮到期可能互相等待【源码条件风险】

`bot_pipeline.wait_for_compression:639–658`仅对尚未提交HTTP、没有外部派发的真实输入登记waiting_compression；`resume_compression_inputs:660`要看到更新的已退休checkpoint才释放。这是正确的防重放保护，但如果上下文在不足35轮时已经耗尽，自动retry没有合法新batch，等待的输入也不能产生新完成轮。当前不能证明所有合法输入规模下都能完成35轮，因此不能把这条等待路径当成必然能自行恢复。

最小处理：明确区分“已到35轮、等待本轮退休”与“未到合法轮数、容量已耗尽”；后者显示具体阻塞，不能只静默等待永远不存在的新水位。正常准入需证明基础区和有界新输入能支持检查点周期；必要媒体采用原已支持的有效引用/表示，不改已提交表示。若已进入不足轮数且历史不可变的不可恢复状态，不能自动制造轮次、提前压缩或扩大无限上限，须报告具体状态并走单独明确授权的处置。

### P2 运行与历史结构的残留边界

- 当前源码保留shared_context开关及独立Scope路径；删除本次联合退休兼容不等于所有旧分支已退出。按新规则，后续统一标准账号入口，旧结构不再维护联合重建。遇到不兼容旧账号应按具体授权结束旧结构，而不是再建迁移框架。
- 数据库忙、stage未结、Journal损坏、epoch/来源冲突仍会正确拒绝非法退休。应区分可重试所有权与不可恢复数据证据错误；不得去掉这些保护来实现“什么都不能阻止”。待压缩状态和错误要一直可见。
- 周期模型预算当前绑定cycle/work（`model_request_budget.bind`），前台与媒体已有在途预留职责；退休Action时必须保留它们。摘要则走`auxiliary_scope`，不能直接假定适用同一cycle身份，也不能因为共享Provider就认定有可用额度。本轮未重新实测预算不足场景，实施时只补“准入拒绝后due仍在、已预留请求取消/迟到仍结算、已提交本地退休不再次申请模型预算”这条路径，不重做预算账本。
- `RuntimeCare.run`外层仅捕获OSError/sqlite3.Error；本地纯恢复抛出其他异常时存在维护task退出风险，事件唤醒路径虽有更宽捕获，但不能保证所有后续重试来源存活。整改应沿原维护owner记录异常并继续可恢复周期，不吞取消、不静默忽略。
- queued输入恢复在原生全局队列不空时暂停；跨Bot持续流量是否导致孤立pending迟迟无法恢复，当前源码有风险条件，未做生产复现。和压缩防饥饿边界一起验证，不另建恢复器。

## 5. 主动模式与旧账本的最简收敛方案

### 5.1 直接收敛的部分

1. 保留现有调度身份/租约、可靠队列和权限边界；到期仅投递一种服务激活Work，短提示说明自主机会和非用户来源。进入普通主线准入、原writer、原Journal、原工具和原输出链。沉默仍按原合法主动轮规则计一次，续接不另计。
2. 移除调度器`dueHandoffs → goalAction → 自动执行/completeGoal`的语义决策；不让Goal更新成功自动触发执行器。Goal由模型通过工具选择、修改、终结；已有真实到期约定由原调度发送必要事件给主AI，不再替模型规划。
3. `read_autonomous_goals`只读唯一Goal的当前有效表述/原意/约束/revision/进度；删除Action/effects/unfinished联合视图及旧baseline阅读合同。每Bot最多10个非终结Goal，包括所有暂停态，沿用现有Bot事务锁；当前handoff创建路径已经有count>=10保护且terminal禁止原地复活，无需再做一套配额。
4. 清理自动`execution_experience/actionChanges`入口，只有真实的新工具结果、投递变化和必要未完Work状态由原Journal/工具回执提供。旧完整过程不再次投影。不能为了删除Action正文又新增currentResponsibilities。

### 5.2 不能靠删表完成的部分

| 当前拥有者 | 仍承担的实际职责 | 收敛归属与退休门槛 |
|---|---|---|
| PG autonomy_actions/cycles | 内部执行身份、租约、到期派发、IPC失联回执、Goal自动执行/结算、用量关联 | 唤醒保留原调度/租约；行为归原Work，移除Goal自动推进。普通执行不得继续以Action为必需身份 |
| SQLite pipeline_actions | 内部Work指纹/working/中断/结果；activation_rounds还以其证明计轮归属 | 迁入原统一Work的身份与结算机制；必须先修正计轮和服务来源引用，不能直接删表使合法轮失去owner |
| PG tool_effects | 前台和自主B站任务共同的准入、精确参数幂等、领取/派发/unknown、媒体任务结果、完成租约/通知、预算关联 | 工具执行状态归原Work与执行器的单一生命周期；工具调用/结果按原Journal保存，必要未知派发凭据仍须耐久。不能仅将表改名为Task或DSHEffect |
| 周期模型/外部预算及独立发送回执 | 在途预留、实际/未知结算、真实发送确认 | 保留原权威预算/发送机制，改其Work绑定；不得随Action退休而取消预留或失去迟到结算 |

关键事实：当前ToolEffects不是仅存冗余历史的表，尤其普通前台媒体任务也使用它。当前源码中尚未看到另一个现成机制已经完整承接它的全部跨进程派发职责；原Journal的调用/结果也不能独自填补“外部副作用已发出但结果未持久化”的窗口。故**完全退休需要真正的执行owner改造，不是一个可安全立即删表的小补丁**。

推荐顺序是先取消第二套模型认知和自动语义调度，再按原统一Work能力逐项接管派发与恢复，最后删除所有Action/ToolEffects消费者和表。每项职责只能有一个写owner；过渡仅为有明确终点的切换步骤，不建设长期兼容层。旧终态历史不要求完整迁移；可按授权舍弃。真实在途/unknown写不能当成普通旧数据丢弃后重放：需保留最小安全凭据、对账或明确停止，不得无证据再次执行。

DSH不是本轮压缩修复的前置条件，也不应为退休旧账本预先搭建另一套Session镜像。将来DSH接入仍只是执行owner，不能接管主AI的Goal语义决策或另造自主目标体系。

## 6. Goal、约定工具与7轮提醒

当前有效代码：`periodic_guidance.py:7–56`、`behavior.py:1572–1576,2139–2140`。周期仍为7，计数沿原成功完成业务Work：source为message/deferred_group、status sent、计划消息数>0且全部确认。不是“所有模型请求7次”，也不把自主沉默和工具续接塞入该提醒计数。35轮计数与它业务合同不同，不能为了统一提醒把两个计数混为一个。

`view`以completed整除7得到through，attach加入状态后由既有增量编码处理；不是每次无条件追加一份新System。目前正文仅有稳定人格、来源和自然回应提醒，**没有合并当前Goal/约定提醒**。

Goal CAS在PG事务立即提交（`packages/database/autonomous.ts:54–85`），约定工具在SQLite commit后立即更新当前发送fence并返回真实revision（`agreement_state.py:275–329`）；不是等7轮才写库。需要保留这些现有行为。

最小合并方法：沿原through周期，在原提醒入口读取当前授权有效的Goal与约定，和已提交Journal实际可见的最新revision比较，仅补缺失或实质变化的最小必要字段；稳定人格提醒仍按原7轮合同出现。直接复用原Journal比较，不加Goal专属计数器、快照池或版本字典。模型刚成功修改的工具调用/结果已经在Journal时，不另追加一份完整列表。

压缩退休后不能把不存在的旧工具回执当仍可见；新基础区按合法重建合同提供必要状态，或保留清晰的现有查询能力及最小提示，不能灌回旧执行历史。外部合法修改导致当前权限/限制变化，程序立即按权威revision生效；模型若必须知晓该新事实，应合法追加必要变化，不能机械等待第7轮。7轮只是集中提醒，既不是生效屏障，也不是许可忽略新限制。
