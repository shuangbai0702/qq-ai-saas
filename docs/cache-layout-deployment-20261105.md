## 实际请求比较与定位

调用链为：

`behavior.py ContextBuilder 贡献 → inner_tools.request_context(event) 追加实时工具候选 → behavior.py 前台/内部 Work provider 注入 → context_transport.request_context_view() → AstrBot _prepare_chat_payload → behavior.py 公共出口投影/图片/摘要覆盖检查 → model_egress.GuardedTransport → API`。

构造函数职责：

- `inner_tools.request_context()` 每次读取事件的当前上下文及候选，不保存另一份记忆。
- `context_transport.split_context_snapshot()` 将当前摘要、核心便签、执行记录正文与 sampledAt 分开；保留对象路径、列表顺序、原字段值，合并后等于原快照。
- `context_transport.request_context_view()` 是本轮修复点。当前可信身份/权限/联系对象、参与判断和禁止写入规则留在 system；只读名单字段进入独立资料包；未知根级贡献保守留在 system。
- `behavior.py` 两个 provider 注入分支共用上述函数；不是只修一个机器人或一个聊天分支。工具执行、Work lease、主人 QQ 校验、发送回执仍沿用既有管线。

对正式实际发出的两轮 HTTP body 逐字段比较：

- 两条 system 消息分别完全相同；工具 schema 完全相同。
- 第一个消息序列差异出现在第 61 项：本轮资料包的位置随最新用户轮次移动；旧的整包实时状态不会被存进原生历史反复累计。
- 实际变化包括 state 的观察时间、recent_messages、recent_cross_session_messages、conversation_timeline、经历采样时间、companion、recent_burst、dialogue。原 identity 未变，摘要与既有执行正文未变。
- 当前只读包约含近期消息 3,684 字符、跨会话消息 5,615、social 2,220、工具候选 1,400、state 1,055 等。字符数不是 API 词元数，部分字段本轮确实变化，不能冻结它们换取命中。

本地不同 tokenizer 对原生消息的公共前缀估算与 API 的 17,536 缓存词元仍不完全一致；序列化估算不是服务商真实模型模板。尚不能将剩余差额全部归因于 FishBot，也没有证据确定第三方内部如何合并角色、路由或淘汰缓存。

## 线上真实请求复核与二次修正（约 19:03）

用户提供 18:46–18:48 的新账单后，没有按受控 48% 宣称完成。读取原生 provider_stats，确认群聊仍有首请求缓存记录 0 或 2,816；又限时抓到同一机器人两个不同真实事件的原始 HTTP body。

## 继续排查大量未命中：时间线与对照实验（19:10—20:20）

本节保留此前已验证修复，不把新候选覆盖到生产。当前重点是解释大量 0/缺缓存字段的请求，不是追求一个受控实验的最高百分比。

### 当前能证明什么

- 50% 不是硬上限。多组真实上下文追加实验第二轮约 57.5%—58.0%；线上外层 planning 的一条真实调用为 39,703 输入、39,552 缓存，约 99.62%。不同入口、首请求和工具续跑必须分开统计。
- 原生 provider_stats 统计一整个逻辑模型/工具循环，且历史实现将未提供缓存字段映射成 0。因此它不能独立证明每个 HTTP 请求实际缓存为零；同样不能反过来声称缺字段其实命中了。真实账单仍需要按请求核对。
- 19:25:38 与 19:36:41 的两个真实外层 planning 请求，system 的 9,266 个字符完全一致，其他非 messages 参数相同，user 部分前 21,793 字符相同，首次分叉是 environment.now。前者返回 99.62%，后者未返回缓存细分字段。间隔 662.7 秒，包含缓存过期/服务端路由等未控制因素，不能据此唯一归因。
- 20:08:53 最新原生私聊记录为 31,928 输入、缓存记录 0；距前一条该私聊记录约 59 分钟。没有当时原始 usage，不能把它当成“连续两轮仍必然 0”的证据。

### 内外层交错是否会清空缓存

使用同一自有 Key，外层请求不执行任何工具或 QQ 发送，串行比较：

| 实验 | 第二个聊天请求输入/缓存 | 说明 |
|---|---:|---|
| 直接 A1→A2 | 22,737 / 13,184 | 57.98% |
| A1→外层 B→A2，第一组 | 22,739 / 缺字段 | 不作隐式缓存推断 |
| 反向顺序重测 A1→B→A2 | 22,745 / 13,184 | 57.96% |

反向顺序的另一个直接对照因 TLS 错误失败，恢复请求也断连，不补记为缓存 0 或测试通过。现有结果不支持“内外层轮流调用必然破坏缓存”，但还不能排除上游容量、路由和缓存生命周期影响。

### 只改变布局的候选没有收益，未部署

当前资料包的位置会与原生历史的追加顺序发生变化，这是可测的前缀限制。实验将单一实时只读包固定到 system 后，并将较稳定的已完成群轮次等排在包前：序列化消息共同前缀从 10,642 增至 16,127 字符，内容、权限和工具不变。

Linux 同一出口实际请求：对照第二轮 22,733 / 13,184（57.99%）；固定包位置候选 22,735 / 13,184（57.99%）。另拆独立 social 只读消息的候选为 22,781 / 13,184（57.87%），没有改善。后者存在与极小接口探测时间接近的因素，不作为严格隔离 A/B 结论。两个候选均不实装；离线共同字符变长不等于 API 缓存必然增加。

### 接口路径差异：线索，不是已定根因

同一自有生产 Key 已私下验证与探针 Key 一致，没有使用其他租户 Key。

极短请求的实测：Responses 不提交 instructions 时，4,392 输入中有 4,382 被 usage attribution 归为 instructions；显式提供短 instructions 后仅 23 输入。Chat 带相同短 system/user 时为 4,401 输入。改变 User-Agent 为 astrbot 或 httpx，输入均为 4,401，排除了这一个变量。

真实上下文协议对照：Chat 追加第二轮 22,749 / 13,184（57.95%）；实验转换为显式 instructions 的 Responses，两轮输入 17,534 和 18,363，缓存明确为 0。随后原样重发同一 Responses 请求，18,363 输入仍明确缓存 0。首次转换因 content.type 不匹配返回 400；修正仅发生在隔离实验脚本，没有更改生产适配器。Responses 路线没有缓存收益，不切换生产。

这证明两条兼容接口的输入计量/实际处理存在差异，但不能仅凭 attribution 断言隐藏内容是什么、动态变化原因或供应商缺陷。后续只围绕实际未命中继续取证，不索要隐藏指令、不将接口实验作为解决方案。
