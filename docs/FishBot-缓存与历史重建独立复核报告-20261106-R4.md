## 3. 384K机制、真正的增长及35轮合同

E4 `decision_history.py:10–51,244–315`，调用入口`autonomous_runtime.invoke_decision:504–557`。

| 名称 | 实际含义 | 不可混淆项 |
|---|---|---|
| MAX_ADDED_CHARS=256,000 | 相对本基线累计增加的历史字符预算 | 不是单次新增、不是256K Token |
| MAX_RETAINED_TEXT_CHARS=384,000 | 现用外层对history所有content字符串长度求和的阈值 | 不是整个HTTP大小，不含system/tools，不是实际Token |
| MAX_RETAINED_WIRE_CHARS=2Mi字符 | ReadonlyJournal调用history_usage后的wire阈值 | 外层AppendHistory未传wire_chars，不能声称外层执行相同wire上限 |
| history_usage.textChars | messages紧凑JSON字符−已识别image data URL字符，仍含结构开销 | 不是plainTextChars，不是UTF-8字节，也不是图片解码字节 |
| MAX_TURNS | 从共享memory-defaults.json读取summaryRounds，当前文件35 | AppendHistory.turns按该journal成功调用递增，**不是35轮真实对话** |

外层prepare先`assemble(reuse)`：旧已提交history＋新增记录＋当前视图变更＋阶段指令；对该**候选contexts**求字符。先判断text总量，再判断相对基线累计量，任一越界立即`assemble(False)`。runtime尾巴在其后生成，因此prepare边界没有包括本次尾巴/回复。commit再加尾巴和真实JSON决策，越界会clear并返回False，下一轮可能只显示initial_or_cleared，掩盖commit超限原因。另有scope、system、summary、空闲6小时、turns边界、oversized_active_snapshot等提前失效路径。

**已证实：** 两次text_size_limit日志只能由`chars>384000`分支给出；随后4条contexts和6条HTTP证明重新组装。**高度可能：** 触发候选确实越过384K，当前源码、reason、相邻增长共同支持。**未证实：** 触发前候选究竟384,001还是更大：日志只记重建后的historyChars，没有保留触发前候选，也没有该时刻正文。因此不能用150,731/143,140证明“未达到384K”，也不能把前次378,691/374,791当成确切触发值。

旧说法“17–19轮84–95条达到边界”应修正：前一候选planning19轮95条，orientation18轮89条；84条是更早的orientation候选。orientation有取消候选，因此准备日志里turn17出现不止一次，不能当完成次数。当前窗口还证实19:05:40、19:12:20曾因**added_text_limit**先重建，不能把所有大小重建都叫384K；历史加载常量版本需与当时进程分开，当前256K不能直接解释早期96K部署时期。

**已排除：** “384K等价正常35轮摘要周期”。这两套计数完全不同。现有代码把外层调用数与summaryRounds复用，更不能证明已完成35轮真实消息。用户新增的硬护栏要求改变失效合同，而不是调大常量或换个reset标签。

## 4. 21:08摘要双重失效的因果链

执行路径：`Reflection.maybe_start`选普通summary或big任务→异步摘要生成→校验closed/config/forget epoch→`BEGIN IMMEDIATE`→写摘要与覆盖证明/来源/people、清理旧摘要或已覆盖轮次→事务提交→下一次`invoke_decision`查询所有摘要行→计算stamp→各自`AppendHistory.prepare`比较retirement。

`summary_stamp=SHA256(model_json(SELECT id,text,sources,updated,scope FROM memory_summaries ORDER BY id))`。**已证实：** 不仅正文变化，ID、sources序列化、updated或scope变化也会变stamp；纯时间戳更新在算法上能失效，但本窗口没有确认这种空写事件。两阶段都依赖整个机器人摘要表，不是只依赖本轮实际选中的摘要。

E3：当前唯一摘要id29，level=big，scope=self，text长度517，sources成员773个，updated=21:06:33。`memory_reflection.py:398–414`的大摘要路径插入新big、迁移origins/people/coverage，再删旧摘要；普通路径插入small并推进轮次水位。**高度可能：** 21:08双失效由21:06大摘要合并触发，而非一条35轮小摘要本身。当前DB不是历史快照，缺少旧行内容、事务ID与每次stamp；不能把“同一cycle两次summary_changed”提升成唯一写入的数学证明，也不能判断新旧文字实质相同。

保护：旧摘要正文、已删除/合并的来源、过期的资料选择不继续作为当前记忆。代价：任何摘要表更新都使两个阶段丢弃大部分历史与临时推理；即便只改不相关scope、ID或更新时间也可能如此。是否两条都必须全量失效：**未证实**；当前共享依赖使其一致，过粗依赖是已确认机制，但减小依赖必须证明没有将已遗忘内容留在旧可见前缀。

不能用“最后的patch删掉旧引用”证明模型看不到旧内容：旧record和旧摘要字面仍在前缀。遗忘、权限撤回等不能只追加一句“忽略以前”。保存旧contextState作为稳定基线尤其危险，它包含当时选用材料、目标、运行布局及旧Work。

并发：prepare之后await期间普通摘要提交不会递增forget epoch；`authority_current`及commit条件不重读summary_stamp。**已证实的代码窗口：** 新摘要提交后，旧候选仍可能提交旧retirement；下一次prepare才识别差异。**未证实：** 本窗口实际发生该交错或导致错误动作。source使用serial防旧候选覆盖新prepare；这不能代替摘要依赖版本检查。内层`constrain_messages`含await，跨await的summary投影也需要同类验证。

## 6. 重建对记忆、身份、权限和未完成Work的影响

**已证实：** AppendHistory/ReadonlyJournal是传输派生对象，clear不DELETE facts、memory_summaries、core_note或执行账本。成功重建重新通过ContextBuilder及conversation_context读取当前记忆、近期消息、群轮次和执行经历；`shared_context`选择self、主人私聊及近期会话，并有数量/检索预算，不能声称读取整个数据库。

**未证实：** 下一次模型能看到全部必要信息。原始模型决策、被裁过的工具结果、当前窗口以外但尚未摘要的重要约定可能只在旧journal中；未被长期事实提取或源档案召回的推理依据会消失。DB中还有数据不能证明检索命中。旧报告“只丢临时原文所以覆盖不受损”应撤回。

`conversation_context`在装配时重新读facts与summaries，减少旧snapshot被错误绑定新forget epoch的风险。group_context读取真实已回复轮次（默认35，pending时留34+当前）；timeline以事件顺序提供不同记录，pending/recent跨会话还有自己的保留窗口。前台原生30轮、业务35轮摘要、外层35次模型调用和群每轮13条并非同一时间轴。当前SQL默认值已核实35/13，但未读取所有运行中配置对象，不能把默认值当所有会话生效值的证明。

可信身份/权限来源仍是Work、lease、绑定及工具实时校验，不是模型记忆。只保留旧system或把它移入user都可能降低身份安全；保留旧Work目的地、旧动作理由、旧unknown回执也可能诱发错误重发。`qq_actions.execute`先登记attempt再await，unknown不自动重试，是必须保留的实际安全机制。

候选生命周期：prepare递增serial，不覆盖成功基线；成功且有效才commit；普通失败abort_candidate只加serial，保留基线；authority失效才retire_committed；旧serial无法commit/清新基线。E7的21项journal测试和新近真实取消/500共同支持。没有必要重新发明第二套异步框架。但普通摘要版本未在提交前核验，是具体待验证交错；是否需要拒绝旧决策的业务执行还须与已有valid/feedbackVersion合同分别判断，不能仅凭cache stale重复外部操作。

遗忘应立即使旧材料不再进入请求；硬护栏不允许代码通过提前重建解决时，应废弃候选并暂停发送，等待可信网页修改/获准边界，不能继续复用包含已遗忘信息的前缀。部署计划必须先证明正常流量不会频繁落入这种阻塞状态，不能把“安全阻塞”伪装成正常回复无退化。
