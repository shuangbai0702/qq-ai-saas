# 下一轮：交付真实 QQ 纵向闭环

保持当前 Web/API/DB/AstrBot 边界，不重新做全局选型。

## 1. 优先完成受控 NapCat runner（产品代码，最高阻塞）

输入 `napcat-platform.json`，输出独立 QQ profile、NapCat config 和受控主进程树。先固定 Linux QQ/NapCat 版本，在隔离环境安装可复现依赖。安装器校验文件来源/散列、记录版本，明确 cwd、HOME、配置根；不要把多个 QQ profile 写到一个用户 HOME。实现 OneBot websocketClients 自动注入、私有WebUI端口/密码、退出清理。平台需要调用此 runner 的真实命令，不允许只登记公共 NapCat endpoint。

验收：用户A、B不接触终端，各自从网页拿真实 QR；扫码后真实身份校验再绑定；未扫码取消后旧QR失效；过期刷新；QQ发文字并获得 AstrBot 的真实模型回复；停止A不影响B；API、QQ和服务器重启后恢复；相同QQ不能在两个实例有效在线。记录视频/事件/日志，不能由测试 fixture 代替。

## 2. 真实账户和供应商验收（外部条件）

需要项目方实际可扫码QQ和用户提供模型Key。Key经现有加密存储注入；校验供应商超时、限流、错误Key是否在页面可诊断且无明文日志。需要2个QQ完成隔离，4个QQ验证首客户容量。不能要求开发AI代替用户扫码或伪造结果。

## 3. Euler 并行实验（不阻断主闭环）

使用当前版本锁和 `protocol:lab`，先确定签名服务兼容的 appinfo/protocol、请求格式和网络可达；缺服务需实现/部署兼容签名基础设施，而不是删配额判断。真实QR→扫码→register→OneBot→消息→恢复，再把 hiro hook 和事件顺序与日志对照。补额外验证挑战提交、签名重试、断线状态测试；通过后与 NapCat 同负载比 RSS/PSS/失败率。

## 4. 上线前的隔离与可靠性

- 独立 PostgreSQL 跑完整测试与真实Migration；测试事务并发、备份还原、Key轮换。PGlite只保留开发用途。
- Linux单节点runner：每bot独立UID/profile/目录权限；cgroup v2配额实机验证；禁止任意租户插件执行。现有“独立进程”不等同于安全沙箱。
- 持久化重试预算与熔断；启动ready超时、进程存活但卡死检测；确保无重复节点Agent；随机端口分配冲突重试和端口被外部占用诊断。
- 命令处理迁移为数据库原子claim/lease后，才允许拆独立API/Agent或多节点。目前单Agent假设必须保留。
- 秘密日志跨chunk脱敏、媒体与测试数据清理、删除后保留/销毁流程；平台API配置供应商地址的出口策略。

## 5. 首四客户验收

真实协议下测1/4/10/20实例，空闲30min、持续聊、群聊、图片/语音、断网重连、并发峰值。Linux记录PSS/USS/cgroup memory.current、CPU、缓存/磁盘；根据实际峰值与余量再定2/4/8/16GB容量。18.8元价格不作为强行降低资源预算的依据。

首四客户验收前不宣称“QQ云托管已可生产使用”。插件管理、记忆管理UI、用量/到期/套餐页仍需开发；支付仍排除在当前范围外。
