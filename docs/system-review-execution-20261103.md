### 确定修复的缺陷

- **F01/F16：反馈与回执。** 前台结果中的可信工具返回、证据和回执进入外层；裸文本“做完了”仍是模型陈述。消息空对象或无有效 `message_id` 不记成功；签名/空间的 OneBot ACK 与消息 ID 分开。
- **F02：一次行动不再等于一条气泡。** 一次聊天行动可投递 1–4 条，每条保留 sequence、回执和取消栅栏；第三条不明时前两条实发前缀保留，未发后缀不入记忆，也不自动重发。没有靠合并气泡或全局放开预算解决。
- **F03/F15/F22：同源、有范围的上下文。** 自主经历及近期 event 去重；真实关系在需要的三个入口可见；自身公共偏好跨会话持续，某群局部话题热度不升级成全局爱好；不向群泄露私聊原文。
- **F06/F07/F11/F24：调度与恢复。** 慢成员不阻塞所有续期；新策略受 issuedAt 单调栅栏保护；公平让出不把 90 秒重新变成总执行硬杀。外部写不明只能核查，旧只读研究可安全收口。仅恢复仍新鲜、已确认、本 scope 的短窗口，不用恢复时刻刷新旧跟聊。
- **F12/F17/F21：记忆来源和整理。** 更正 A 不删除同群 B 的待整理原料；摘要 reset epoch/来源版本阻止迟到回写；全机器人 1000 条/7 天上限不变，按 scope 轮次保留，避免热群挤光安静会话。满 1000 条时“安静会话 5 条 + 热群 996 条”测试保住安静会话，整理后只替换实际来源。
- **F08–F10/F13/F18–F20/F23：真实控制面。** 草稿、保存 revision、实例已应用分开；清理未消费 trigger/random 参数的编辑入口；跟聊概率如实显示为启停语义。聊天开关、工具授权和自主研究各自解释；不能把关聊天当作已暂停全部自主任务。

## 2. 默认、人物成长与资源约束

`packages/contracts/behavior-defaults.ts` 是版本 2 的行为默认来源，当前 80 字段：原 79 字段减去摘要日限额，加真实 QQ 收藏、引用两个能力开关。18 项旧默认分叉已对齐。显式 `false`、`0`、空数组、自定义主人/白名单/间隔继续保留；鱼预设仍只覆盖原来的 52 项，不把“应用预设”变成全字段重置。

摘要每日次数硬门和对应设置已删除；用量统计保留。达到有效问答阈值后，忙碌/失败的整理债务持久化，重试退避 60 秒至 1800 秒。复用现有共享 caretaker 每 60 秒检查，只选一个空闲机器人继续，不为每个 QQ 创建周期模型任务。未获回复的消息仍保留 pending，不伪装成已完成问答。

好感度按真实事件、去重、冷却及防刷计算；日界线统一北京时间。没有给生产人物灌分或重置数据。只读最终样本中主机器人有 105 条关系、27 条正好感关系；23 号两条关系均为正。关系、情绪、兴趣、动机各自保持原存储与范围；这些是模型参考，不能保证每次回复会表现出特定语气。

远程 Embedding 使用 4.5 秒单轮期限、全局并发 2、同查询复用、事实/摘要各 16 条增量候选及有界 top-K，不常驻加载整库浮点向量。排队超时不计作实际请求。实际配置 `embeddingModel` 为空，已配置服务列出的 13 个模型未发现 Embedding；主机器人和两个测试号向量表均为 0。**HTTP/SDK 合同和失败回退已测，真实向量写入、检索、换模型生命周期尚未验收，不能宣称远程语义召回已工作。** 普通事实/摘要检索继续可用。

48MiB 空闲 `memory.high`、独立 AI 16MiB、40 秒 PAGEOUT、zswap/Swap、Guard、离线清退未改参数或脚本；参与真实任务时的 `max` 放宽和异常回退保留。API/PostgreSQL 原阈值保持不变。

## 12. QQ 收藏的发送形式及流量优化：最终收口

用户追加询问能否直接按 QQ 收藏表情形式发送并省流量，随后要求优化完成后收口。实际 Linux NapCat.Onebot 为 **4.18.41**，加载 bundle SHA-256 为 `c37989cfaf1c361619d764b22655316e988523041f91c546a96d57b88180581e`。普通收藏不是商城表情：`mface` 需要商城包身份，不能用普通收藏的 resId 冒充；实际 bundle 没有 `send_custom_face`/`sendFavEmoji`，普通图片发送仍经图片接口。QQ 收藏详情虽然带本地路径，测试号四个条目的 `isExist` 都为 false，原图路径为空或文件不存在，不能直接信任这些路径跳过读取。

上游源码依据为 [CustomFace.ts](https://github.com/NapNeko/NapCatQQ/blob/98d781d19815d1625b24d717ce280ecf0a4f6d0c/packages/napcat-onebot/action/extends/CustomFace.ts)、[图片与商城表情转换](https://github.com/NapNeko/NapCatQQ/blob/98d781d19815d1625b24d717ce280ecf0a4f6d0c/packages/napcat-onebot/api/msg.ts)、[图片元素构造](https://github.com/NapNeko/NapCatQQ/blob/98d781d19815d1625b24d717ce280ecf0a4f6d0c/packages/napcat-onebot/api/file.ts)。运行包与上游源码版本分别记录，真正是否可发送以实际 QQ 实收为准；没有升级或改造 NapCat。

### 最终实现

1. QQ 收藏随本轮输出发送时，仍走既有 OutputPlan、末端许可、OneBot 与消息回执；只对渲染器已绑定的真实收藏图片携带 `sub_type=1`，按 QQ 自定义表情标记发送。普通图片不会仅因在同一条回复里就被改成表情，原生小黄脸策略不变。主人授权的既有群发送工具对已准备的收藏图片采用相同标记。
2. 准备收藏图片前仍读取当前 QQ 的真实 detail，校验当前配置和身份；优先复用本机器人 `uploads` 中 MD5 一致的原文件。不会接受模型提供或协议任意返回的本地路径。
3. 没有已保存原图时，只在必要时下载当前详情对应的 QQ 原图，核对 MD5 和原有大小/图片安全限制。下载后写入独立的可清理发送缓存；后续命中直接读磁盘，保留原 GIF 字节。缓存按账号+MD5 区分，**每机器人最多 16 张、总量 32MiB**，原子落盘、近期使用淘汰，不增加内存常驻字典、定时器、模型或服务。
4. 淘汰仅作用于新 `send-cache` 内受控文件；不删除 `uploads`、QQ 原有收藏、Session、配置或记忆。内容不符/缓存损坏不冒充正确原图，下载后解绑则不落盘或绑定旧结果；缓存写入故障不妨碍有效回复。

这修复的是重复下载和发送类型。**没有实现“只发 resId、完全零上传”的新协议，也不能声称 QQ 服务端一定免上传或总出口流量为零。** Base64/图片发送路径保持原架构，QQ 端是否复用既有资源取决于实际协议处理。
