# 统一回复适宜性判断强化与验证

## 范围与审查结论

基线为`72a41bc`。本轮只修改回复前复核提示、统一请求诊断类型及replace执行分支，不部署、不外发真实QQ、不调用付费模型。工作区已有`shared_context.py`队列窗口修改保留且不纳入本次提交。

真实调用链：`behavior.py`发送前检查 → `GroupFreshness.check` → `review_request` → 同一`decision_scope(...,'group_freshness',...)` → Provider → keep/replace/drop → 既有OutputPlan → 目的会话cursor及权限/StopFence → 协议发送 → 真实回执/Work结算。

现状有两处不一致：

1. Provider缓存路由已经统一，但System分群聊/私聊，辅助诊断phase也分开，不能保证相同Bot下跨场景稳定前缀一致。
2. 共享上下文的replace会抛开复核器已经给出的新稿，返回主Work要求再生成；这不是“本次草稿需要修改”的直接执行，还可能额外调用模型。非共享模式已有直接替换渲染能力，无须新建执行器。

此前已移除“旧队列非空就否决keep”的门槛，本轮核对它没有重新出现。群表情回应没有加入过滤列表。实际dispatch前检测到新版本、失效Owner或权限不足仍应拒发，不能把这些安全拒绝当作与keep冲突。

## 最小实现

`adapters/astrbot/group_freshness.py`：移除独立`SYSTEM_PRIVATE`，使用一个回复适宜性System。私聊、群聊条件规则同时固定在这一公共前缀，可信调用方在动态`context.scene`写入`private`或`group`。不根据用户文字猜场景。

- 私聊：对方最新原话、双方关系、对话进展、当前草稿与是否需要回复；明确不套用全群氛围或公开插话规则。
- 群聊：同时评估目标人的真实身份/意图/关系及草稿准确性，以及全群最新话题、其他人发言、氛围、时机、公开表达是否自然。无关插话、旧队列或话题变化本身不是否决条件，只有实际影响准确性、对象或社交适宜性才修改或放弃。
- keep允许正常发送；replace给出完整可发送新稿；drop不发送此稿，不意味着所有其他输入已处理。
- 保留真实来源、未发送草稿不等于发言、部分投递禁止整段replace、媒体控制符、工具与权限边界。

现有`decision_conversation`已按目的会话提供有界participants与timeline：群scope下涵盖不同发言者，不按目标人单独过滤；最新变化另由latest_messages提供。原问题携带真实sender_id，记忆动态区保留关系、约定及回执。复核未新增第二份原文/全群历史副本，也不新建目标人数据库。

`adapters/astrbot/behavior.py`：统一辅助phase为既有`group_freshness`，与既有路由标识一致。名称沿用是为了避免无收益的协议迁移，并不代表私聊被按群聊处理。独立Work ID、租户、Bot和真实Scope仍分别保留；统一请求类型不等于合并会话或授权。

replace直接走既有受控OutputPlan重渲染，不再触发共享模式专属的主模型再生成。部分已发时原解析保护仍拒绝replace；现有渲染次数上限、目的cursor、StopFence、当前lease检查、回执及unknown机制不变。修改稿不引入新工具执行或权限。

无新信息且无真实状态变化时继续使用原来的免调用keep捷径；复核期间发生变化仍可按原合同有限重试，不承诺永远恰好一次请求。此次没有加入关键词判断或额外的适宜性模型调用。

## 稳定前缀与历史边界

相同Bot、相同人格和Reference状态下，私聊/群聊System及独立Reference物理消息逐字相同，场景、Scope、时间、目标原话和最新输入都位于后面的动态消息。辅助请求类型和路由使用同一个`group_freshness`，保留原多租户/Bot命名空间。

真实关系、事实和约定变化仍及时进入动态资料，不能为缓存冻结。不同Bot人格、身份或不同版本记忆导致前缀不同属于正确隔离，不伪称全部请求共有前缀。物理前缀一致只证明客户端可复用，不证明供应商缓存实际命中。

本轮不修改35轮常量、计数、Journal、Root、已提交消息的角色/内容/顺序/序列化。辅助请求的新提示只影响新请求。草稿结算继续沿用前次修复的最小状态，不新造用户消息或重复存正文。

| keep正常准入，replace修改，drop拒发 | keep现有修复保留、replace复用OutputPlan、drop现有路径 | 专项验证通过 |
| 安全、回执、35轮及不可变历史 | 未触及历史模块；相关边界回归通过 | 已核对本轮改动 |
| 不增加无谓请求 | 移除共享replace额外主模型生成，保留必要变化重试 | 两个SDK专项各1+1调用 |

合理的实施调整是删除共享replace再生成分支：它与“复用现有判断调用、replace修改稿”的目标相冲突；既有直接渲染职责已经足够，无须新增状态系统。

仍有边界：群聊timeline及最新变化都是原有有界视图，不能宣称覆盖全群无限历史；不充分资料下的真实模型判断质量需后续合成真实模型对照或正常运行观察。生产未部署，本地构建含原工作区未提交的队列窗口修改，不能直接当作可发布的干净独立版本，部署须从明确提交隔离构建，并先定位上述多人排队失败。
