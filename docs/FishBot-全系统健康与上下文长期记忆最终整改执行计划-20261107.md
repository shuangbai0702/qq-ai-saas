## 5. 根因、因果关系与数学边界

### 5.1 两类阻断应分开

调用路径：`behavior.inject → native_history / summary_material.project_history → prepare_chat_payload → model_images.constrain_messages → ReadonlyJournal.prepare → wire校验/SystemContract → provider → settle_journal`。

1. `ContextCapacityExceeded`：`decision_history.history_boundary`分别限制增量256000字符、总文本384000字符、wire2Mi字符；provider模型还有独立Token上下文和输出上限；Journal持久层另有16MiB/64活跃记录/4096墓碑。它们都没有与“剩余到35轮的最坏增量”形成准入合同。梁沅芷已接近增量上限，即使媒体少，也会卡在下一次合法许可前。
2. `ContextReconstructionDenied`：旧base与新native输入不能证明精确扩展、受众/retirement变化等要求重构，而没有可预留许可。`confirmed_native_window_extension`能保住部分SDK截窗，不能证明任意删除/改序/工具块变化。小双白、大肥鱼的摘要/覆盖投影时间与失败紧邻，但**失败分支在记录context诊断之前抛出**，缺reason和首差异类型，具体触发项尚未完全证实。
3. System、工具定义、图片重编码、角色或来源序列化改变可能是独立触发，不把“部署/重启必然重构”当事实。完整持久Journal正常恢复时重启应继续原wire；缺失、容量失败、版本不兼容才需另诊断。

### 5.2 证据闭环中的实质缺口

`summary_material.snapshots`遇未知part、工具块等会置complete=false；`supported_block`拒绝tool_calls/tool角色；`store`在容量不足时可丢images并置不完整，后续合并沿用不完整标志。当前四条活跃Hold都已有材料但complete=false；仅重试相同材料或再攒35轮不能证明它们能恢复。

成功摘要可以推进watermark和生成coverage，但它不必然铸许可；缺覆盖仍Hold。`project_history`又依据已有coverage先改变SDK投影。Journal若不能证明扩展且许可不存在，就在真正发模型前被拒。d0006fb修复计数/清理，**没有把所有这种投影变化与合法切换同步**。

另有确定性持久化风险：`ReadonlyJournal._persist`容量失败分支可将已有scope写成unavailable并置payload=NULL；如果发生在模型成功之后，会丢最后可恢复快照。样本未证明该分支已造成事故，但源码足以要求修复。

请求失败也必须分型：`settle_journal(False)`丢弃候选、`abandoned_request()`按PID退出回收reservation，不能证明请求从未到达模型。已发请求断流/进程崩溃与发送前本地拒绝不同；不能把“没有成功回复”当成“历史从未提交”。这是源码存在的恢复边界风险，未声称在当前三会话中已复现。

### 5.3 有限容量无法提供的保证

设合法重构后基线为B，容量为C，下一35轮每轮最坏新增I/O/工具/只读资料为Δi。只有 `B + ΣΔi ≤ C`，且持久化与provider容量也满足，才能保证这段**已约定上限内**的对话走到检查点。没有输入/输出/工具结果上界时，不存在有限C可无条件保证。

Δ还必须覆盖一个业务轮内的全部ToolLoop子请求，以及不算完成轮的主动时刻、NO_REPLY和已发失败请求；这些额外请求若无累计上界，单纯给35条成功回复留空间仍不成立。低价值内部触发可在现有预算用尽后暂停等待真实新输入，不能将它们改算完成轮来解除容量压力。

拒绝一个超长新请求能保护历史，但不等于恢复已经卡住的28轮会话；缩小未来资料包也不能收回已经提交的250K增量。完全丢失来源、旧前缀无法精确恢复、所需容量超出provider硬上限时，必须BLOCKED并说明条件。另开scope/epoch冒充原会话恢复也违反本任务约束。

## 10. 安全不变量与逐会话合法恢复手册

1. 已被模型接收的历史内容、角色、顺序、媒体表示及序列化在合法35检查点前绝对不变；工具定义/System改动也不得成为逃逸通道。纯失败或NO_REPLY不自动算已完成业务轮。
2. 所有许可由真实后端证据签发，绑定scope/epoch/request/受众/承接摘要，一次消费；待覆盖不是许可，配置审计不是历史重写授权，consumed不回滚复活。
3. 恢复前只读导出scope状态：最后成功请求与prefix摘要、Journal完整性、容量余量、真实完成轮/Hold/coverage/水位、许可状态/关联、运行版本及必要备份清单。不能由机器人昵称或原文指定别的租户/QQ目标。
4. **精确恢复**：若Journal内存丢失但持久快照完整，恢复同字节；若仅文件丢失而受信备份可证明精确前缀，需管理员明确授权写回、校验与审计，不产生新许可、不改历史。未知请求是否到达模型的情形保守保留证据，不自动重试外部动作。
5. **仅本地容量不足**：核实provider、RAM、磁盘及剩余轮数预算后，可申请单独有界调整；全程历史不变。容量上调不是伪装35许可，既有新请求预算同时生效。
6. **已有合法35证明但未可用**：修复合法的关联/事务/待覆盖承接，不能以“现已有35个message”替代。历史来源不足时不得追认许可。
7. **来源缺失/隐私冲突/硬容量不可兼容**：停止含越权资料的请求、保留证据并报告BLOCKED。当前约束没有“点一下强制重建”的合法恢复；用户如决定丢弃历史或改变护栏，必须另立明确新合同，本计划不提供伪授权按钮。用户知情通知属于平台状态，不是继续角色对话的假象。
8. 任何恢复/存量隔离都应有操作人、受影响scope散列、前后摘要、依据、回滚点。不得批量清Journal、清lost、改epoch、复用cutover或覆盖原图换成功率。
