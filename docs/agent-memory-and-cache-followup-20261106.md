# Agent 内存与 19:31–19:34 缓存核验

本次范围：Node Agent OOM 容量与对象生命周期检查、针对性降峰，以及用户追加的缓存记录。没有进行 Git 写操作；不代表此前统一整改计划全部收口。

## 已证事实

- 19:26:02 Agent 因 V8 堆达到 128MiB 崩溃，Docker `OOMKilled=false`。原进程运行约 3.87 天。这证明内部堆上限触发，不证明不存在泄漏。
- 容器自动恢复时协议与共享 AI 被重新创建。因此不能把 19:24 部署时“QQ PID 未变”扩大为本轮全过程无中断。
- 恢复后核对 PID 与创建时间：5 个协议、2 个共享 AI 存活；数据库 5 个运行实例均 online。
- 后续 Agent 采样：RSS 95.5MiB、PSS 67.2MiB、USS 61.4MiB、Swap 52.9MiB；另一次 RSS 72.6MiB、PSS 41.6MiB、USS 34.7MiB、Swap 90.9MiB。不同时间/负载，不是修改前后 A/B，不据此声称内存净节省或长期稳定。
- 单独导入 Agent 类的隔离进程，GC 后 heapUsed 约 12.9MiB、RSS 约 73.1MiB；不包含数据库连接、正常任务或多天维护操作，不能代替生产容量测量。

## 实际修改

1. `process-host.ts` 原来只有每个子进程最多 32 个待写日志的数量限制。每行允许接近 64Ki 字符，7 个子进程可同时保留约 14Mi 字符，且需考虑脱敏中间对象。新增每个子进程合计 256Ki 字符限制，保留原逐行脱敏、超长整行丢弃、队列清理与管道所有权。不是认定日志就是本次 OOM 根因。
2. 新增 `agent-memory.ts`，独立 Agent 启动时默认将堆参数提高到 192MiB。仅在 Linux 且尚未打开数据库/持有 QQ 管道时同 PID `execve`。保留其他启动参数；默认不降低已有更大上限；可用 `FISHBOT_AGENT_HEAP_MIB=128` 回到原值，允许区间 128–384。没有修改 API、NapCat 或 AstrBot 的堆参数。
3. 现有心跳每 30 秒附带一次 `process.memoryUsage()` 与 V8 总堆上限，不增加定时器或模型请求。

当前部署是**磁盘待生效**：当前在线 Agent 仍 PID 1868419、原启动参数 128MiB。没有为了启用新上限重启它。新心跳字段和已有子进程的日志闭包也尚未切换；新启动入口、192MiB 与日志上限需在下一次 Agent 正常启动时加载。

## 生命周期调查的边界

正常业务的进程表、检查快照、后台单任务与日志队列都有数量或生命周期控制。B站签名缓存有容量/过期限制；未证明它们构成持续泄漏。

旧维护脚本存在按 release 保存回退对象的实现，会保留旧协调器、方法和闭包；多次带版本参数的 ESM 导入也不会自动卸载。源码已证这种保留路径，但旧 OOM 进程已消失，没有堆快照，无法量化其占比或认定其为唯一根因。本轮不再向生产 Agent 注入维护模块，使用独立测试与磁盘备份回退。不能宣称“四天泄漏问题已彻底解决”。
