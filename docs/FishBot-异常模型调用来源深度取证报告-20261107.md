### 2.3 时间解释

本文统一使用北京时间。中转 `createdAt` 返回明确的 UTC 偏移；SQLite 为 Unix epoch，按 UTC+8 转换。模型判断记录与中转开始时间通常相差约一两秒，可由本地准备、传输和中转计时边界解释，未发现足以解释“请求全消失”的时区偏移。

**不要把 `pipeline_events.at` 当作最终模型请求时间。** 它在首次入站插入，后续更新 stage/status 不重写 `at`。例如事件 `6780104a47a5` 首次入站为 16:18:55，实际到期判断为 16:28:34；只按 16:28 搜索入站表会遗漏它。`autonomy_decisions` 的 group/owner 时间是判断开始时间，而 plan 行约在结果完成时写入，三者也不能机械等同。

### 3.1 为什么恰好十分钟

实际调用链：

`真实群消息 → behavior.before → GroupPresence.ready/evaluate → provider.text_chat`

或者：

`真实消息被 defer 保存 → initiative.sweep → pending/claim → 原协议事件重新入队 → 同一 evaluate`

生产 `autonomy.py:207–237` 校验原始群消息身份，一群仅保留一份最新候选；`pending` 要求候选时间晚于最近 checked/interaction。`ready` 在 254–258 行校验群许可、静默时段、当前配置、预算、不同 event 和冷却。此次已保存决策的 `base_seconds` 确实是 600，不是只根据默认配置猜测。

`evaluate` 在 await 前提交 checked/event 并清理已消费 inbox，随后实际请求模型；`initiative.py:182–196` 的 sweep 才负责取出到期真实事件。**五秒 sweep 不等于五秒付费调用，十分钟冷却也不等于无消息时必定调用。** 五次事件指纹不同，没有证据证明它们是同一旧消息反复执行。

### 3.2 为什么 16:48 没有成功决策行

`autonomy.py:295–311` 只有 `current && decision.source=='ai'` 才写 `autonomy_decisions`；policy、stale、异常分支仅覆盖 `lastGroupDecision` 等内存字段。后续 16:58 成功会覆盖最近失败／策略结果。本次 health 只能读到最新结果。

因此“没有决策行”并不推出“没有模型请求”。中转已证明 16:48 请求成功返回；本地最终采用结果的具体原因没有持久证据，保持未查明。累计一次 groupDecisionFailure 也不能直接扣到这一笔上。

### 4.1 两笔 0/0 究竟是什么

**已证实：** 中转确实收到请求并留下 499 记录；不是“FishBot 在发送前被护栏拒绝，所以中转不存在请求”。0/0 只代表这两条账本没有计到 Token，不能证明没有网络请求或没有上游执行。

**推断：** 生产群参与调用外包 `asyncio.wait_for(..., groupDecisionTimeoutSeconds 默认10秒)`；本地计时还包含到达中转前的准备／网络时间。中转记录的 8.540／9.641 秒，与客户端十秒取消吻合，状态 499 也与客户端断开相符。缺少中转内部取消原因及当时本地异常类型，不能声称精确找到了服务器拒绝原因、模型根本没开始运行，或简单建议提高超时。

### 4.2 15:17 为什么“中转成功”与“本地护栏失败”同时存在

前一个阶段是独立短上下文的群参与判断，结果为允许参与；后一个阶段才构建正常聊天历史并运行 Agent，触发 `ContextReconstructionDenied`。`provider_stats` 中 15:17:57 的 0 Token error 对应后者；中转 15:17:47 的 7562／38 对应前者。把这两个阶段合并为“一笔本地失败”，就是旧报告遗漏真实调用的具体例子。

## 5. 日志盲区的确定根因

### 5.1 Agent 统计不覆盖所有 provider.text_chat

群参与 `autonomy.py:290`、主人联系 `companion_schedule.py:140`、联系计划 `companion_schedule.py:71`、表达学习 `social.py:368` 都直接调用 provider，并显式把 `current_message_event` 设为 None。

AstrBot 的 `provider_stats` 是 Agent runner 执行统计的持久化结果，不是所有 HTTP 请求的总账。参考 `internal.py` 的 `_record_internal_agent_stats`（约 600–640 行）。**普通对话 Agent 的表为空，不代表辅助模型没有调用。** 摘要表未更新也无法排除群参与、主人判断或表达学习。

### 5.2 无 event 时 lease 元组下标写错，导致诊断静默丢弃

冻结生产源码：

```python
# model_cache.py:146–147
_system_contracts[id(provider)] = (provider, contract, lease)

# model_cache.py:132–138，前面没有 event/decision lease 时
return binding[1] if binding and binding[0] is provider else None
```

`binding[1]` 是 SystemContract，正确 lease 位于 `binding[2]`。`record_diagnostic` 在 55 行以后要求 lease 为包含 root/botId/tenantId 的 dict，收到 contract 后直接返回 False，不写记录。四类直接调用又没有建立自己的 `decision_scope`，因此恰好落入此缺陷。

离线验证结果：`returnsContractInsteadOfLease=true`，`leaseIsDict=false`。测试仅编译并执行生产源码中这两个函数，使用内存占位对象；未 import 应用、未连接网络、未请求模型。本地当前文件也仍有同一返回值，不能标成已修复。

### 5.3 其他证据源也有范围限制

- `behavior.py:1309–1317` 的最近调用／usage 日志依赖有效 event，直接辅助调用同样绕开。
- `shared-worker.py:70–72` 为避免多租户原始日志泄漏，禁用通用 logging；这有安全理由，不应通过重新打开全部 prompt／response 日志解决。
- `autonomy_decisions` 不持久化所有 policy/stale/error 结果；health 只保留最近结果及进程内累计数，不能恢复完整历史。
- `model-diagnostics` 每 256KiB 轮换且只保留 previous；缺失旧记录还可能是留存边界，不能当无调用证据。
- `pipeline_events.at` 是入站时间；不同机器人／worker、不同业务阶段也不能靠一个时间字段统一匹配。

旧专项报告第 4、10、17、23–29、39、47、84–88 行中“完整、无遗漏通道、无 diagnostics 即无调用、九笔非 FishBot、疑似其他消费者”的论证均失效。缓存命中和旧架构调用下降等其他结论需要各自证据，本次没有以这些小调用推翻或重做整个缓存系统。
