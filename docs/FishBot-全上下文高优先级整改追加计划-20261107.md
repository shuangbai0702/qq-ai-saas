适用项目：`qq-ai-saas`。原计划指[长期记忆与对话能力最终整改执行计划](FishBot-长期记忆与对话能力最终整改执行计划-20261107.md)，新审计指[全上下文系统多智能体深度审计](FishBot-全上下文系统多智能体深度审计-20261107.md)。本文完整阅读两文后，只核查影响实施决定的关键节点，没有重新全面调查，也没有连接生产。生产现状引用既有发布记录和审计取证，不能冒称本轮实时验证。

## 1. 执行结论与效力

优先执行：**H0版本冻结及统计校准 → H1失败夹具与权限/入站完整性验证 → H2无损增量和容量验证 → H3外层独立检查点及恢复 → 原计划其余修复及联合验收**。H4故障调度与费用可观测性在H1后即可独立推进，不必等H3；涉及共同调度/finish事务的部分与H3合流验证。原D1/D2/D3的来源、受众和纠错安全工作与H2并行，不因性能整改后移；真实越权复现必须先修。H1中确认的入站信息丢失也不得等自然度优化。

关键判断：

1. **已证实**：发布工作树与主工作区的外层实现不同。主工作区新增许可门却未接线，是候选发布阻断项；发布工作树仍保留摘要/空闲/调用次数等自动重建路径，属于外层尚未整改。不能把两个版本拼成同一个生产事故。
2. **已证实**：数组按位置差分可在头插/窗口移动时重复发送大量仍在集合中的内容。**高度可能**：其显著推动当前容量增长。具体冗余比例、距离第35轮的容量余量尚需同口径重放；不能直接宣布“第35轮必卡死”。
3. **已证实**：外层失败可保守扣账且较快重新唤醒；高请求量是值得前置的问题。**未证实**：全部输入Token等于未缓存费用、无聊天等于无自主业务、全部unconfirmed等于零有效工作。
4. **已排除作为有效论证**：响应ID格式足以证明缓存路由；data URL天生不可缓存；缺journal表就证明机器人漏部署；阈值96K→256K是四倍；唯一部署副本必然只在脏工作树。
5. 审计提出的“summary_changed后自动许可”“遗忘应急许可”“全bot重做cutover”“整体重启消除版本混合”“动态policy全部升System”不得执行。它们分别违反最高护栏，或缺少必要性/安全证据。

本文替代新审计§13中与此冲突的概要修复办法；不取消原D1–D9，也不把原本已覆盖的问题重新立成另一套架构。所有新增字段和接口均为拟实施设计。

## 2. 不变合同

- 合法检查点前，已提交模型消息的System、角色、顺序、正文、媒体表示和序列化结果完全不变，只在末尾追加必要短增量。每次最终模型请求都校验完整已提交前缀，而不是只比较消息数量或本地对象。
- 前台35轮真实完成业务对话与外层35个有效完整规划周期独立计数、独立许可。工具调用、阶段调用、回执轮询、失败、重复finish、后台修复不冒充有效轮次。外层许可不改前台或任何System。
- System仅凭35真实对话成功摘要许可或后端可信网页配置保存许可改变；部署、工具变化、摘要选择、普通摘要、大合并、容量、超时、重启都不是许可。
- 任何新协议说明或字段含义如需改变System，只能排队等System自己的合法许可；外层压缩许可不能顺便激活它。检查点可以压缩的前提仍包括完整资料和未完成执行可见性。
- 后端实时身份、工具授权、遗忘/受众限制继续生效。不引入developer角色，不让模型自报授权。旧wire已含禁止继续发送的数据时明确阻断受影响scope；不能尾部remove冒充删除，也不能新铸“应急许可”。必须提供真正合法且不死锁的恢复路径，无法证明则该子项暂缓发布。

### 3.2 外层执行路径与许可

**已证实，候选风险**：主`decision_history.AppendHistory.prepare:255–320`在非复用且已有view时reserve重构许可，无许可抛异常；主`autonomous_runtime.invoke_decision:517`没有传authority。触发条件是首次成功基线之后发生需要重建的变化，不是所有初始调用一律瘫痪。另发现该主函数:532使用`namespace`，本函数未赋值且文件无该全局定义；发布树:511有赋值。这也是独立候选阻断项，下一轮须用真实包装器替身测试覆盖，不能只做导入检查。本轮未运行调用，不把静态缺陷写成已发生生产异常。

**已证实，发布树机制**：发布`AppendHistory.prepare:244起`把相同绑定、摘要指纹、6h空闲和`turns<MAX_TURNS`结合判复用；容量边界仍可assemble新基线。`invoke_decision`的`summary_stamp`取全表摘要id/text/sources/updated/scope，摘要写入会影响两个外层phase。这不等于35个完整cycle，更不是合法System许可。审计样本中size/idle/turn未出现，只能说明观察窗口未触发，不能证明路径不存在。

**前台必须区分**：发布`readonly_journal.prepare:298–323`在guarded时普通`summary_changed`本身不清wire，真正依赖retirement等。普通召回摘要变化走delta；不能把外层summary_stamp自动重建归因到所有前台请求。删除非法6h/调用次数重构是必要方向，不能称其本身为“护栏回归”；缺的是真正外层35周期许可和有界恢复。

### 3.3 容量与差分

**已证实**：`decision_history.changes:54起`递归按数组下标比较，头插和滑窗可能令长列表逐项set；发布`readonly_journal.prepare`把结果附加到旧wire后。`context_transport.request_context_view:126–132`构造完整事件/只读包，但之后journal会投影为增量，所以“入口构造全量”不等于“最终HTTP每轮又发全量”。必须在最终wire定量归因。

发布prepare已比较`authority!=old.authority`并省略相同policy。需检查保存的是完整当前有效状态还是缩短后的包：若完整/增量表示混比，可制造重复；若当前事实真的变化，重复标记不等于冗余。A→B→A必须再次传A，禁止用全历史哈希集合“以前见过就不发”。

容量定义见`decision_history.history_usage/history_boundary:32–51`：wire是JSON序列化**字符**；textChars=wire减去已知data:image URL字符，并非纯正文；plainTextChars另计。384000是保留textChars上限，256000是相对首次提交anchor累计新增上限，wire上限2×1024²字符。`base_chars`是建立本周期基线时的textChars锚点，不是此刻`base`JSON的长度；两者不同本身不证明诊断造假。持久化另有16MiB、64journal、4096墓碑保护，不等于模型容量。

“27轮追加250K、只剩6K”需先确认27是业务完成轮还是请求次数，并统一prepare/commit/候选/已提交口径。已发布重放的19个重叠35轮窗口最大wire373909/text283984，仅证明那组重建材料通过，不能覆盖新高峰；该材料也不是35个完整原始HTTP/ACK。新增压力风险提高发布门槛，不能反向擦掉既有样本结果。

## 6. 容量、语义和防回归验收

### 6.1 材料和逐轮记录

复用已有脱敏native/HTTP/ACK证据；区分完整原始请求重放、原始事件重新装配、纯合成压力，分别报告置信度。前台按完成业务轮对齐35，外层按上述有效cycle对齐35；工具循环多请求单列，不算额外轮。至少连续3个周期、多tenant两worker交错，覆盖大量工具、长正文、媒体和未完Work。没有完整真实35轮材料时明确缺口，不能把27请求外推后写“真实35轮已过”。

每个请求记录：周期/业务轮/模型尝试序号、初始text/wire/media/UTF8体积、当前与累计追加、候选峰值、commit后保留、基线anchor、record字典/快照大小、剩余容量、完整prefix/System哈希、许可/拒绝原因；实际usage有则关联，无则null。CPU、进程RSS/峰值、SQLite字节、装配p50/p95、端到端延迟分别测。离线模型不调用，不能制造实际Token；不按字符除3/4冒充Token。持久化峰值需包含base/wire/字典共存，不能只量单份wire。

门槛：

- 现有原容量保护全部保留；正常35轮/35周期材料及预先登记的高峰压力材料全程无容量阻断，不缩短覆盖/减少必要信息；无法满足则H3不发布。最大值及最小余量公开，压力模型和余量是否充足显式评审，不用一次未越界保证无限流量。
