# FishBot 插件对照与后续实施计划

日期：2026-11-01。范围：当前 Windows 工作树中的实际实现、已保存的参考源码及本次能访问的上游源码。**本轮只调查和出计划，空间意图改造也尚未实施；没有改应用代码、配置、数据库，没有部署、重启或执行 Git 操作。**

## 结论

过去为共享多租户和内存密度做平台适配有实际理由，但不能据此认定每项功能都应重新实现。当前有些能力只是参考机制的简化版本，不能再以“已对齐原插件”概括。

建议顺序：**空间意图 → 群聊参与判断 → 事实记忆与检索 → 情绪/关系 → 兴趣动机 → 表情语义与表达学习**。优先改善实际聊天行为，不增加一套新的 Agent 或多个后台调度器。

源码比较可以确认某种机制更完整，不能证明上游实际聊天一定更好。本轮没有安装运行上游插件，没有进行 Linux 新一轮性能测试，也没有发送空间动态或修改签名。下文的效果优势是待验证假设，资源成本没有虚构 MiB、CPU 或延迟数值。

## 一、空间改成意图判断

### 当前问题与调用链

实际代码：`adapters/astrbot/qq_actions.py`。

1. `intents()` 用句首动词和正则匹配识别空间请求。
2. `allowed()` 将匹配结果与主人身份、功能开关交集，决定工具是否提供给模型。
3. `tools()` 创建工具，模型才能选择调用。
4. `execute()` 再调用 `allowed()`，执行端仍受同一正则限制。

因此目前是“规则先放行，模型后执行”，不是完整的模型意图判断。只修改工具描述或提示词不能解决漏识别；只改工具提供处而不改执行处也不行。

### 推荐方案

- 对可信主人且已开启空间功能的真实聊天事件，提供少量明确的空间工具，由当前回复模型理解自然表达并选择调用。普通聊天、能力询问、讨论文案、引用他人的指令、否定发布应正常聊天或提供草稿，不发生发布。
- 工具描述明确区分“发布到当前机器人自己的空间”和“写一份文案”；文字回复不得冒充工具成功。内容或执行意图仍不清楚时再简短询问，不对所有发布增加固定确认步骤。
- 执行端取消空间动作对句首正则的依赖，继续校验可信 QQ 发送者、所属机器人、功能开关、当前事件/配置代次、当前 QQ 身份、内容长度、可见范围、额度和幂等记录。
- 模型给出的意图、理由或 `owner_asked` 字段都不授予权限。机器人、QQ 账号、Cookie、收件目标不能由模型随意指定；保留当前固定账号和接口边界。
- 同一真实事件最多执行一次；超时等结果不确定时记录为未确认，不能自动重发，也不能告诉用户“已经发了”。
- 优先复用本轮模型的工具选择，不默认新增一次独立意图分类请求。工具调用可能增加模型往返，必须在验收中测量，不能承诺零延迟。
- 本阶段只调整空间。签名、头像等可以随后复用相同原则，但不借此次改造扩大自主发空间权限。

这能消除固定措辞造成的漏判，但不能用程序硬校验证明语义判定永远正确。需要用正常表达、连续对话中的指代、草稿请求、否定、引用、越权和重放测试分别核验。

### 验收与回退

- 自然措辞可进入正确工具；能力咨询/草稿/引用/否定不发布；他人自称主人无效；其他租户或其他 QQ 的工具句柄无效。
- 消息重放、配置变更、QQ 改绑、接口超时、限额耗尽均不重复写入、不谎报成功。
- 隔离协议测试通过后，在真实 QQ 上核验一次明确发布及空间可见结果；日志中的模型调用不能代替发布回执。
- 保留当前执行保护和发布历史，按机器人灰度。出现误发或可靠性下降，回退本阶段代码，不删除历史、Session 或配置。

## 二、逐项插件核对

下面按插件/参考模块逐项列出。AstrBot 插件、DSH 插件和完整机器人项目不是同一种接入形式；不能把所有源码目录当作可直接安装的 AstrBot 插件。

### 1. Group Chat Plus：群聊判断、注意力、并发与疲劳

参考：本地 `references/social-learning/group-chat-plus`，metadata 为 `V1.2.3.hotfix.2`；[上游决策代码](https://github.com/Him666233/astrbot_plugin_group_chat_plus/blob/main/utils/decision_ai.py)。

- 实际机制：`decision_ai.py` 让模型判断是否回应，考虑说话人、@ 指向、他人对话、近期未回复消息和追加消息；`smart_concurrent_manager.py` 负责同期消息合并；`attention_manager.py` 维护多用户注意力与衰减。
- 我们：`participation.py` 主要用中文二元词、最近话题和最近一个已回复对象；同一对象在有效窗口内可持续接话，其他成员加入仍更依赖规则。疲劳主要是窗口内回复计数，不是真正的“聊腻了”。
- 值得学习：多人会话对象判断、等待期间补入新消息、疲劳作为参与倾向而非简单硬挡。现有连续接话修复保留，不能退回每句话都要重新碰概率。
- 接入判断：先在隔离环境试插件最小配置，核对现有发送/上下文钩子是否冲突；若必须改写主链路很多，再复用其独立模块。源码中注意力图有类级共享状态和固定数据路径，必须验证机器人维度，不能只因有 `chat_key` 就认定满足平台隔离。
- 成本：独立决策模型会增加请求；不能对每条群消息无条件调用。需比较合并批次和候选判断的收益，而不是再加一层词语否决规则。

### 2. MaiBot attention_drift：自然联想

参考：`references/social-learning/maibot/src/maisaka/attention_drift.py`；[上游文件](https://github.com/Mai-with-u/MaiBot/blob/main/src/maisaka/attention_drift.py)。

- 它提供由最近细节支撑的不同联想幅度，不等于简单“命中兴趣词才回复”。
- 我们尚无等价的联想幅度与话题回归机制。适合学习其上下文构造与短促表达原则，先以原有回复模型消化。
- MaiBot 是完整框架，不建议另起一套常驻运行时。联想过强也可能抢话；不能把最高档直接作为默认值。

### 3. Proactive Chat：主动消息

参考：`references/social-learning/proactive-chat`，metadata `v1.2.6`；[上游](https://github.com/Pancakes-Labs/astrbot_plugin_proactive_chat)。

- 实际有会话键解析、持久化会话、沉默计时、调度、上下文和发送服务。`SessionKey` 保留平台前缀；不能笼统说它没有会话隔离。
- 我们已有 `initiative.py` + `companion_schedule.py`：真实互动目标、拒绝/告别处理、未回应上限、成员核对、模型规划、迟到结果保护。模型规划默认每日最多 6 次，另有发送预算；规划对象筛选与选人仍有规则限制。
- 值得学习：会话配置、真实聊天上下文、沉默/重试解释和管理诊断。现阶段不同时启用两个调度器，避免重复主动消息。
- 原插件包含遥测与独立管理入口，应先核对关闭方式和必要性；这不是否定插件，而是部署时明确行为。
- 另外 AstrBot 原生已有 `cron_tools.py`。准确提醒/定时任务应先核对原生能力，不把我们的 30–600 分钟聊天规划器包装成完整提醒功能。

### 4. LivingMemory：检索与记忆生命周期

参考：`references/social-learning/livingmemory`，metadata `2.8.2`；[上游](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory)。

- 实际代码包含中文 bigram + SQLite FTS5/BM25、混合检索、文档/图路线融合、召回诊断与记忆作用域解析。
- 我们默认 `semantic_context.py` 是词匹配结果加近期候选，最多 16 条事实/1600 字、5 条摘要/1200 字，交给当前回复模型阅读；远程 Embedding 是另配模型后才使用的路径。默认路径不能等同于全库向量语义检索，历史记忆超出候选范围时可能根本看不到。
- 值得学习：先按授权范围检索，再排序和 LIMIT；中文检索；来源、版本、失效、召回原因；事实与对话摘要分开。优先补足候选召回，而不是让模型重复重排同一小批候选。
- 接入判断：在小库中比较原插件最小检索路线与平台适配路线，不预先决定全量重写。全局/用户作用域不能直接沿用默认；同一个 QQ 在不同机器人下也必须隔离。
- 纠正旧判断：本地 requirements 是 `networkx/jieba/aiosqlite` 等，不能把它说成必然要启动本地 Embedding 模型或必然要装 FAISS。图加载、分词、缓存和实际检索内存另测。

### 5. DSH fish-memory：稳定事实、事件与更新

参考：`references/round3-behavior/dsh-fish-memory/lib/index.js`；保存快照 `8b3571da`；[上游](https://github.com/Yuuyuko-uu/dsh-fish-memory)。

- 优点：区分稳定事实和有时效事件，将相关性与鲜活度分开，并保留时间/来源；比“新近记录总是更有价值”更合理。
- 我们已有事实类型、来源、版本、纠正/遗忘及有限自动捕获，但自动捕获主要是少数完整自述正则，不能等同于通用自然语言记忆提取。
- 建议学习更新、冲突与事件过期规则；与 LivingMemory 的检索能力互补。它依赖 DSH 接口，不能直接装到 AstrBot。只选择必要机制，避免建立第二份互不一致的事实库。

### 6. dafeiyu-qq-bot / dsh-memory：自然聊天中的记忆提取

参考：`../qq-ai-saas-research/sources/nanbengxian-cyber__dafeiyu-qq-bot/plugins/dsh-memory/main.py`；[上游源码](https://github.com/nanbengxian-cyber/dafeiyu-qq-bot/blob/main/plugins/dsh-memory/main.py)。

- 有聊天缓冲、后台提取、逐人上限、来源和抽取租约等机制；后台提取避免每条入站同步增加模型等待。
- 我们对复杂自述、关系变化、同义表达的抽取弱于这个设计。建议在已完成真实对话后做有预算的结构化候选提取，沿用现有事实库版本与遗忘控制，不让模型自行决定存储目标。
- 原参考中多处按群/人建键及固定路径，仍需增加机器人归属。后台提取会增加模型请求；能与现有摘要合并的先合并，不为每条群消息额外请求。

### 7. Self Learning：表达、黑话、人格与亲密度

参考：`references/social-learning/self-learning`，metadata `4.4.3`；[上游](https://github.com/NickCharlie/astrbot_plugin_self_learning)。

- 实际有表达学习记录、样本过滤、黑话学习、人格候选/审阅，以及按群/按用户的好感度模式和测试。它不是简单追加一句模仿提示。
- 我们 `social.py` 从至少 12 条、两个群友的真实样本提取少量原样短语，每 Bot 每 24 小时最多 4 次学习；不自动改人格。亲密度在 `behavior.py` 按真实定向消息、去重、冷却和每日额度调整，正负信号仍是规则。
- 值得学习：表达适用场景、样本质量、学习结果审阅、停用/回退、黑话含义与表达习惯分开。
- 不应直接把整套人格进化默认打开；用户写的人格需要保留版本和恢复路径。按群/按用户的配置不等于机器人隔离，需要验证共享实例中的数据库与缓存归属。
- 本地 requirements 不能证明它必然运行本地大模型；模块、缓存和后台请求分别计量。

### 8. 两种情绪插件：不能混为一种“对齐”

参考 A：[dafeiyu-qq-bot / dsh-emotion](https://github.com/nanbengxian-cyber/dafeiyu-qq-bot/blob/main/plugins/dsh-emotion/main.py)，本地实际使用规则提取候选、状态转移、定向识别和 TTL。

参考 B：[Yuuyuko-uu / dsh-feiyu-mood](https://github.com/Yuuyuko-uu/dsh-feiyu-mood)，本地保存快照 `4e210244`，`lib/index.js` 中有模型 `judge()`、多维状态、衰减，以及 `judgeChain/judgeVersion` 防旧结果覆盖。

- 我们 `emotion_state.py` 对齐的是 A 的部分机制：单一主导情绪、引用/指向排除、修复、连续中性释放和 TTL；仍是压缩过的规则实现，不是 B 的模型情绪判断。
- 建议先统一当前“关系中的短期情绪”和“机器人会话心境”的用途，避免两套状态给模型互相矛盾的提示。
- 后续学习 B 的有证据变化、逐渐恢复和迟到保护；先比较少量结构化语义判断能否减少错判，不直接全量增加七维 UI 和每轮独立模型请求。
- 亲密度、情绪、主人身份、管理权限保持独立。分数变化不授予权限，也不能为了让页面有变化而随机加分。

### 9. dsh-social：社交距离

参考：[源码](https://github.com/nanbengxian-cyber/dafeiyu-qq-bot/blob/main/plugins/dsh-social/main.py)。本地默认 `shadow`，只记分审计；`style` 才注入口吻。

### 10. dsh-interest / desire / will：自身喜好和动机

参考：`dafeiyu-qq-bot/plugins/dsh-interest`、`dsh-desire`、`dsh-will`；[上游项目](https://github.com/nanbengxian-cyber/dafeiyu-qq-bot)。

- 它们区分兴趣热度、驱动力、主导选择/行动阶段；模式开关和实际注入/行动路径必须分别看。兴趣热度本身也包含规则，不是全部由模型生成。
- 我们 `companion_state.py` 有人格偏好、机器人表达、共同话题热度、少量未完成话题；提取主要靠固定句式，选人评分主要靠未完成话题、关系和最近出现。它是可持久化聊天状态，尚非完整的长期动机闭环。
- 值得学习：兴趣从何而来、多久保持、为什么现在联系、联系后是否完成/放弃；共同话题热度不能直接冒充机器人稳定喜好。
- 建议复用现有状态与调度表补充原因和完成证据，不把所有心理模块、全局环境变量、固定群号/主人号直接搬进共享运行时，不虚构线下经历。

### 11. Meme Manager：平台表情库、选包与语义检索

参考：`references/social-learning/meme-manager`，metadata `5.2.9`；[语义索引源码](https://github.com/anka-afk/astrbot_plugin_meme_manager/blob/main/backend/semantic/index.py)。

- 实际有按包的存储/管理、语义描述、远程 Embedding 适配、模型指纹与缓存、FAISS 索引；存在包作用域写入回归测试。
- 我们已有按启用包取候选、词义/情绪评分、可选远程向量、模型标记与遗漏时补图。`behavior.py` 在已经提供候选时按显式路径传入，当前不是简单重复抽两次概率。冷却、额度和严重场景保护仍会影响最终发送。
- 差距：复杂语境和反讽匹配仍偏规则；自动回退在没有明确匹配时仍可能选出一张语境一般的图。应加强候选语义质量，而不是悄悄再次随机跳过已触发候选。
- 建议优先复用资源包格式、元数据、描述与检索评估；保留用户要求的“候选已触发则发图”合同及现有防重复投递。
- 源码明确依赖 FAISS；不能称完整语义索引零额外内存。图库规模与冷缓存/热缓存分开测，不因采用远程 Embedding 就声称本地无索引成本。

### 12. Meme Magpie：收集、识图和语义标签

参考：`references/social-learning/meme-magpie`；[上游](https://github.com/Whereis-Alice/astrbot_plugin_meme_magpie)。

- 值得学习识图语义标签、内容审核、限速队列、失败原因与重试管理。当前“收集到了”不等于“识图完成且已能自动发送”。
- 建议原插件作为单独候选，不与 Meme Manager 同时接管发送；先比较哪一个更适合现有平台图库和低内存目标，再决定采用独立模块还是原插件最小配置。

### 13. 大肥鱼 Signature 与 QQProfileEx：资料动作

参考：`references/dafeiyu-config-pack/plugins/astrbot_plugin_dafeiyu_signature/main.py`；[QQProfileEx 源码](https://raw.githubusercontent.com/Akusative/astrbot_plugin_qqprofile_ex/main/main.py)。

- 签名原插件本来就把签名作为模型工具，不强制句首命令；它也有 MOODS 词表提示，不能说原版已完全按语义识别心情。
- 它按 `owner_session` 或 AstrBot 管理员判权限，使用固定插件历史文件；找不到 event 客户端时回退到首个协议客户端。适合单机单账号的便利回退不适合共享多租户。
- QQProfileEx 的模型工具是语义使用方式，但所读实现的自动动作使用插件级当前值/冷却，自动工具没有手动指令同样的管理员装饰器，定时状态使用最近保存的客户端。不能直接代替我们的主人核验与机器人归属。
- 建议学习“工具真实存在、模型自然选择”的优点，保留平台事件绑定、QQ 身份核对、数据库幂等和每日额度。自动签名进一步接入真实心境，而非持续扩充 MOODS 词表。

### 14. Qzone 专门插件：暂不能判定直接替换更好

查到 `Zhalslar/astrbot_plugin_qzone`、`astrbot_plugin_qzone_tools` 等候选，但本轮搜索缓存与实时源码访问存在不一致，部分原始地址返回 404。**未完成版本与调用链核验，不把搜索摘要作为采用依据。**

我们的发布路径已经是 NapCat 协议动作，当前主要问题在意图门槛，暂不需要为修它引入带浏览器、群管理和大量工具的完整工具包。之后如要空间浏览/评论/图片发布，应另核验专门插件的登录凭据、接口维护和真实回执，再评估替换。

### 15. 输出清理、分段、打字与回戳

- `output_clean.py` 明确保留 `dafeiyu-config-pack` 快照 `8c01b036` 的来源和 MIT 许可，已有直接代码复用；这项不能说成只是“学了行为”。当前同时清理历史助手文本、模型响应和发送文本，应保留并回归。
- `chat_rhythm.py` 的打字等待、轻量错字和回戳已能以低成本实现。参考插件的自然节奏可借鉴，但没有证据支持整套替换；固定错字也不能当成降低 AI 味的核心办法。
- 平台表情图片与 QQ 内置 Face 分开处理，重用插件时必须保留现有禁用 Face 的用户约束。

### 16. 语音、唱歌、B站等额外功能

配置包里有 TTS、唱歌插件和独立声音服务；参考项目还有提醒、B站等模块。这些不因参考目录存在或人格写了能力就成为平台已启用功能。

本轮没有逐个执行这些外部服务，不宣称其可用，也不默认安装本地语音/歌声模型。它们属于单独产品能力评估，优先远程服务并明确额度和真实工具状态；不插入本次空间和聊天主链路改造。

## 四、实施计划（待后续授权实施）

| 阶段 | 最小改动与交付 | 验收重点 |
|---|---|---|
| P0 空间意图 | 同步调整工具提供和执行校验；保留原协议动作与所有硬保护 | 自然请求、草稿/否定/引用、越权、重放、超时；真实空间发布回执 |
| P1 群聊参与 | 对照 Group Chat Plus 的语义判断与消息合并，保留连续对话优先；先比较最小原插件配置再定接入方式 | 多成员接话、指代、@ 他人、不重复、不抢话；疲劳不切断正常交流 |
| P2 记忆 | 对照 LivingMemory 的受限域检索与 DSH 的后台提取；沿用事实/摘要/遗忘数据边界 | 同义查询、旧事实、事实更新、摘要非事实；遗忘后缓存/向量/迟到任务不能复活数据 |
| P3 关系与心境 | 统一状态职责、变化来源和自然恢复；补充必要语义识别，供签名参考 | 否定/转述/玩笑/道歉；真实互动变化、持久化和重置；权限不受分数影响 |
| P4 兴趣与主动联系 | 为已有兴趣/话题/计划补证据、完成与退出，不新增独立调度器 | 联系时机合理、群成员真实、拒绝后停止、无人回应不追问、无假经历 |
| P5 表情与表达 | 比较主图库方案，改善语义标签/候选相关性与学习审阅 | 正常群聊及被@可图文；候选触发无二次概率；冷却/限额可解释；不发 QQ Face |

不是一次性全部上线。每阶段先在独立测试数据和协议替身下回归，再灰度一个明确机器人；同一事件只允许一条实际发送链路，不能让 A/B 两条路径各发一遍。聊天质量比较使用脱敏历史及真实后续聊天，不伪造生产亲密度或记忆。

每阶段均记录模型请求数/Token、真实入站至首条/完整回复 P50/P95、消息漏回/重复/失败、整机实际 RAM、PSS、Swap、zswap 池、CPU 与 PSI。空闲和繁忙同负载比较，不把 USS 低点当收益；额外 P95 以现有约束 ≤5 秒为上线门槛。QQ 平均 CPU 3–6% 是已有目标参考，口径需按实际核数和采样窗口记录。

保持 `memory.high` 共享 AstrBot/NapCat 48MiB、独立 16MiB、40 秒 PAGEOUT、Guard/回退/离线清退策略不变。不新增本地 Embedding/视觉模型常驻，不凭源码行数预测内存。某插件最小配置若实测效果好且适配量少，应直接采用，不为了维持自研而重复实现。

部署前保存各 Bot 配置版本与必要数据备份，核对应用变化和 Windows 前端协作内容；仅更新受影响服务，不能顺带重启 Agent/NapCat/在线 QQ。新增检索结构可重建但事实、人格、账号、Key、Session、身份文件必须保留。失败按阶段回退，不能清库来制造通过。
