## 对旧判断的纠正与保留

- **“2～3K Token 全是真实必要新增”不成立为总括结论。** 候选目录重发和自动附图均有可复现的避免空间；同时真实新消息、作者/受众资料、真实图片与回执必须保留，不能为降数字全部去掉。
- **“约 23K 未命中必然是上游缓存问题”证据不足。** 字节前缀一致证明客户端连续发送稳定，无法确定中转路由、TTL、缓存生效时间等具体原因。现场相邻请求既出现高命中，也出现返回的 0 命中；未返回字段仍属于未知。没有中转唯一请求证据，本轮不编造上游根因或命中率承诺。
- **未对已提交历史做媒体去重或重编码。** 新附图检查只发生在本轮尚未提交前。已提交重复图片也必须等待真正合法检查点退出；不能追溯修改。
- 工具循环沿用 SDK 步数预算、既有写入回执/unknown 规则及禁用自动重试的入口。本轮没有证据支持新增循环判定器、第二套规划或语义关键词拦截。
- 长期记忆继续由现有摘要模型选择语义；没有因目录展示优化改变 Claims/Facts 语义、来源校验、召回授权或 Protected 状态，也未提高摘要长度。

## 剩余边界与明确舍弃

1. 真实图片持续累积仍可能在 35 轮前达到有限传输或存储容量。本轮降低自动重复附图的压力，但无法保证任意大小输入都无条件通过；触顶必须在提交前拒绝，不能清历史、切 epoch 或靠失败次数越过护栏。
2. 暖 Journal 去重不覆盖所有冷启动/仅曾自动关联图片的变体；保守保留原附图路径。没有为此新增跨重启媒体索引或长期图片存储架构。
3. 高峰出现 `foreground_capacity_timeout`，属于每 bot 执行容量等待超时，与完整性死锁不同；本轮未扩大并发、自动重放或宣称解决所有突发负载问题。
4. 缓存波动没有足够证据指向确定的上游机制；不通过改写历史、更换模型或新建缓存系统强行“修复”。wire/base64 字符量不等于计费 Token。
5. 生产磁盘仍约 87% 使用、可用约 5 GiB，不能无限积累取证副本和备份。本轮没有删除既有业务或他人文件。
