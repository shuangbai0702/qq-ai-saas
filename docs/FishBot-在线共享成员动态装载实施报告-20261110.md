# 在线共享成员动态装载实施与复核

本次只修改源码和隔离测试，没有提交或部署，没有操作生产进程、QQ、数据库或会话。

## 原问题与范围

`SharedAstrBotAdapter.assign` 按持久 `group_members` 行数分配，普通停止只将成员标记 stopped，保留原 group_id，停用账号长期占据八成员配额。Agent 的普通启动和扫码登录先加载 AI，组恢复还按 desired_state 批量装载，均未以当前协议在线状态作为成员加载条件。

改动仅涉及 `adapters/astrbot/shared.ts` 与 `apps/node-agent/src/agent.ts` 的装载、卸载和恢复边界，以及相应测试。不修改原生 SDK 工作/发送实现、不创建第二个 Journal、不改变 35 轮许可或媒体退休规则。

## 实际行为

- 共享机器人先恢复或启动 QQ 协议；待扫码、离线、停用时不加载 SDK 成员。健康检查核验真实 QQ 身份，现有恢复命令装载在线成员。
- 组启动和配置写入可能经历等待，最终 PUT 成员前再次核验当前机器人、租户、generation、revision、运行意图、协议在线状态与绑定 QQ 身份。
- 每组仍最多八成员，后上线成员复用最早的可用组。正常运行的在线成员不因组内出现空位而被强制搬迁。
- 离线卸载沿现有 worker 的失效、drain、平台/provider 卸载与 Store release；得到成功响应，或确认原组进程已不存在后，才移除 group_members/group_id。卸载结果不明时保留关联，不把该槽授予另一个所有者。
- Agent 获取现有独占 lease 后，以及每次健康检查，主动处理旧 stopped/deleted/成员 stopped 行。即使原 bot health 为空、不进入旧健康扫描，也会清理其旧成员；清理失败保留并重试。
- 组崩溃后只恢复当前已经检查的成员，其他成员逐个经过自己的在线与身份检查，不再凭持久 desired_state 批量预载。
- 机器人自己的 root、behavior.sqlite、Work、回执、未知发送与共享 Journal 不随运行组改变。协议原有登录/离线宽限与清退逻辑保留。


22 项通过，0 失败，总耗时 177.159 秒。覆盖：

- 九在线成员的八/一边界；十账号中离线账号不占位；释放后新上线账号复用旧槽；每账号最多一个 SDK owner。
- 真实控制数据库中的旧九个 stopped 成员，以及仍存活的组 owner，在升级清理后释放，QQ 协议句柄保持。
- 卸载响应失败保留成员与组关联；配置等待期间离线，最终装载围栏拒绝并撤销暂存关联。
- 两租户的配置、Key、root 与 API 归属；同组 PID 和成员级恢复边界。
- 真实 AstrBot SDK＋本地 OneBot/模型 fixture：八成员、配置更新、停止/删除、组崩溃与 Agent 重启；双成员的模型响应跨 apply、离线/重上线、stop、delete 后迟到，均不能发送旧结果，其他成员继续工作。

随后将在线成员测试中的普通文件哨兵升级为真实 BehaviorStore/SQLite 证据，再单独运行该测试通过（5.242 秒）：先用原 BotPipeline 形成 attempted=1、confirmed=0 的 unknown 发送及已提交媒体 Journal，再在卸载、换组恢复、组重启和迟到装载拒绝后重新打开该库，unknown 状态不变、同事件仍为 duplicate、Journal wire SHA 完全相同。

这是本地真实 SDK 与受控协议/模型证据，不是生产 QQ 正向发送或上游模型验收。

合理实现细节：不为了填平空槽搬迁仍在线成员；空槽交给后续上线成员，避免中断其他人的在途 Work。旧组失败且无法确认卸载时仍暂占槽，以保留唯一所有权。在线/离线是现有健康采样与装载前核验结果，不宣称瞬时无延迟感知协议变化。未增加调度器、永久分组身份、数据复制、自动历史重建或新的退休许可。
