## 调查、根因和修改

### 1. UNEXPECTED_B 与 HOTBATCH：测试消息分类缺陷

实际链路：模拟OneBot事件 → 真实AstrBot SDK → Work/队列 → ContextBuilder/Journal → 真实HTTP请求 → 测试Provider分类器。

两个集成用例均用 `nativeMessages(body).at(-1)` 判别当前业务输入。原 `tests/helpers/model-fixture.ts` 已过滤事件包/只读增量，却没有过滤独立的 `[FishBot 阅读格式B v1]`、`[FishBot 上下文固定基础区 v1]` 定义消息。新增定义恰好落在物理尾部时，分类器识别到B格式说明，报告 `UNEXPECTED_B`，或找不到 HOTBATCH 标签而抛异常。实际HTTP请求中仍存在 OTHER_C/HOT_INPUT 原始消息。

修复只作用于**测试视图**，不改变Provider请求、生产角色、顺序、物理边界及序列化。新增 `tests/model-fixture-boundaries.test.ts:1` 检查：独立定义被排除，真人多模态消息、assistant工具调用、tool结果、正文内引用的标记仍保留，原请求对象不变。两份原集成测试的业务断言没有删除或放宽。

### 2. 跨Scope回归：旧合同、调度不确定性与真实恢复缺陷分别处理

`tests/scope-work-runtime.test.ts` 中的旧预期与当前合同有三处差异：

- 私聊复核仍按旧System识别；改成统一复核System，场景在动态包中识别。
- 原始入站留存已经保存根事件，旧查询却把全表行数当作“后续加入行数”；查询显式区分根事件，并继续检查完整根/加入输入结算。
- 旧用例认为keep/replace必须等主模型续轮才发送；按用户明确合同，keep可发送当前合适草稿，replace直接发送合法修改稿。独立的新问题仍由原Work续轮处理，不能假装已回答。

多Scope用例原来允许私聊与群聊任意抢先更新全局可信观察版本，固定的复核次数和“始终drop”替身因此并不确定。现在使用可控barrier：群聊A生成期间加入B/C，进入群聊续轮后再注入私聊，再释放原群Work。替身按其已见输入返回drop/keep，不修改生产决策逻辑。最终严格断言 **14次主请求、9次复核**；第9次来自明确安排的可信版本变化，不是无条件重试。仍验证群聊只发送一次、三个输入各结算一次、私聊不能加入群Work、14个完整历史前缀不变、四次上限及后续交接。

真实业务缺陷位于 `adapters/astrbot/initiative.py:272`：

1. 原始协议入站在异步转换前持久化，`observed_at` 可为浮点秒。
2. SDK首次转换/入队的规范消息时间可为整数秒，并已绑定到 `message_provenance`。
3. Worker恢复旧输入时，原实现用浮点原始观察时间覆盖SDK重新生成的时间。
4. 同一Scope/event的规范输入内容因此变化，`bind_model_input` 正确拒绝，产生 `shared_context_protocol_input_changed`。这不是应该绕过的身份护栏。

修复优先复用同一Scope/event已持久化的 `fishbot_shared_inputs` 来源时间；队列行已经被Journal接纳时，查现有 `bot_shared` Journal的对应原始来源。严格校验Scope/event/原始作者相符；没有既有来源才使用保留的原始观察时间。原始payload、payload SHA、身份摘要及历史均不改写，不使用恢复时刻伪造原始时间。新增队列/Journal两种恢复及错误作者拒绝回归，位于 `tests/unstarted_input_recovery_20261111_test.py`。

### 3. 继承的队列窗口依赖

修改前检查了未提交的 `shared_context.py`，确认其与本次请求归属及旧队列行为有关；连同已有窗口测试，单独提交为 `d96c1b5`，没有覆盖其他会话内容，也不把它冒认为本轮新设计。

`adapters/astrbot/shared_context.py:157` 起：每群背景窗口最多12条，当前激活输入在配额内保留，私聊不按此群窗口截断。排除的**临时队列行**仅在对应窗口被Journal真实接纳后按精确ID删除；失败/仅暂存时不删，不删除独立Work账本及未提交来源。覆盖失败提交、重启后接纳及跨群/私聊隔离。

## 剩余风险与未执行事项

当前修复范围没有留下一项已知、未解决的阻塞性P1。以下限制不能隐藏：

- 生产仍有历史blocked_recovery、blocked_unknown和deferred记录；本次不批量改pending或清理。它们不等于Worker健康接口的当前执行队列，也不能据此宣称所有历史输入已补答。必须按真实Owner/来源/执行证据逐条判断。
- 首次重启前后，一成员的21条 `blocked_unknown,seen=0` 被**既有启动恢复规则**识别为确定未尝试发送的群观察等待，转为deferred。该规则在发布前源码已存在（`bot_pipeline.py:473`），只匹配同Scope/subject/event、waiting/group_waiting、attempted=confirmed=0；不是本次手工批量解锁。真实unknown继续保留。发布脚本没有重放外部操作。
- 后续无副作用观测发现同一成员blocked_recovery从592增至601。逐项只读核对新增9条：均为群消息、addressed_self=0、无@本机器人、且全部在当前共享上下文白名单之外；其中2条引用其他消息，不等于可信引用本机器人。这些记录没有进入pipeline_events、主模型或发送，恢复审计为 `ingress_not_accepted/retry=5`。这是既有原始留存与白名单早退间的 **P2账本分类/无效恢复债务**，有界停止后未无限空转；不把它说成全部恢复成功，也不越权扩大群白名单。本轮不据此改已提交历史或批量结算。另有1条缺原始payload/身份的旧队列进入保守blocked_unknown；缺证据时继续未知，不重放。
- 真实Provider对社交适宜性的判断具有模型不确定性。本轮证明了资料、决策采用及执行边界，没有额外付费模型A/B，也没有以Mock结论证明自然交流质量提高。
- 未主动向真实QQ发送验收消息；确认的是运行版本、身份、既有协议在线、模型配置、持久化与真实发送路径的隔离验证，不能声称逐个Bot完成了生产新逻辑keep/replace/drop的实际外发验收。
- 本轮未做长时间耐久测试，也未对全部历史blocked记录恢复。后续只需观察旧输入重开次数、来源冲突、keep/replace后实际回执、unknown增长及Worker成员异常，避免无证据扩大重构。
