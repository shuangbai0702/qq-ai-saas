## 具体职责与整洁度

`semantic_runtime.py` 使用原 memory_semantic_batches 的退休成员身份，匹配 `_fishbot_source(scope,event_id)`；元数据从真实 SDK current_message_event/Work取得，先移除调用者自带归属。管理员 grant 不等于按时间猜测归属的许可，故移除原生消息表按 created_at 删除的分支。SDK conversations 原有显式管理员 cache reset 语义仍保留。

旧原生 content 没有当前消息 event_id，reply 中的 message_id 属于被引用对象，不能拿正文相似、显示名、时间或相邻 conversation 伪造归属。此类行保留 physical 并报告 `native_history_source_unproven`；既有工具读屏障不返回它们，新批次可正常继续。既有每UMO数量上限可能自然淘汰它们，但没有承诺淘汰期限。人工清理需要可信 rowID→原事件/Work证据。没有恢复 Coverage/Hold，没有第二原文池。

外部动作预留分别落原 `autonomy_actions.external_effects` 与 `tool_effects.budget_reserved`，同一 cycle 行锁提供共享额度边界，周期/day用原账本汇总，不创建第三套发送状态。新增 migration012 是必要的持久化扩展。预留HTTP失联可能后端已提交，因此默认保守占用；真实协议失联也不退款。不能将一次“模型宣称完成”当实际外部回执。

`bot_pipeline.py` 统一等待原因与定向输入判断；已seen、存在执行效果、真实unknown及原事件已有Work均不能成为自动重放许可。`group_actions.py` 精确撤回确定未dispatch的一次attempt，保留新分条合同的逐气泡回执。主动联系沿原预约/联系账本分阶段释放，没有新增预约调度器。

`native_ingress.py` 只是原转换入口的所有权绑定，不存第二份长期原文，不新增恢复循环。正常转换未新增5秒硬超时；部署StopFence看到真实busy可拒绝停机，既有有界部署等待不能无限阻塞。专属与共享Worker都接入；原SDK恢复不再穿过真实入站的重复投递门。

`NodeAgent` 仍是现有调度所有者：新增有界在途集合用于同bot互斥与停机排空，health不能与同bot生命周期写操作交叠；共享成员清理也取得同一生命周期lane。`ProcessHost` 的检查快照仅属于当前health异步上下文，普通命令不能借用它判断进程。维护入口统一检查 `controlIdle`，避免新后台操作在旧busy标志外继续运行。

共享Worker的生命周期仍保守串行：start/stop链可能重新分组、重选全局端口，不能单靠查询时的group_id认为此后始终属于同组。独立机器人、health及heartbeat已分离，进一步缩短共享分配/启动临界区需独立方案；本轮没有把全部操作改成无约束Promise.all。

合理保留 PostgreSQL自主任务/工具账本、SQLite Work、权威Journal、媒体归属：这些状态分别证明业务、执行、已提交wire和原始材料归属，不能为文件更小而合并。也没有全仓格式化、拆大文件或新建第二自主系统。
