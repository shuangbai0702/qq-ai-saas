## 2. 本轮优化效果复核与尚存缺口

### 2.1 "readonlyChanges -57.4%"的真实含义

【已证实】该数字来自**合成控制轨迹**（`.local/h2-replay-20261107/trajectory-benchmark.py`，`actualModelRequests:0`、`actualTokens:null`），不是真实流量，且单位是**字符不是 Token**。报告 §5.4 诚实标注了"未宣称 Token 收益"，但标题数字有被放大引用的风险。

【已证实】我在**真实抓包**（`.local/r4-publish-20261107/private-native-replay.json.gz`，生产请求捕获）上重跑了仓库自带的 A/B 脚本：

| 真实窗口 | 旧 diff 总量 | 新 diff 总量 | 降幅 |
|---|---|---|---|
| 窗口0（35轮私聊） | 58,529 字符 | 57,579 字符 | **1.6%** |
| 窗口35 | 31,793 字符 | 30,161 字符 | **5.1%** |
| 19个真实窗口 maxWire（报告口径） | 6,444,444 | 6,424,000 | **-0.3%** |

字段分解（真实窗口，当前新代码）：稳态 ToolLoop 轮 delta=2 字符（空，最优）；大轮次来自 `<root>` 整包重建（单次 20,341 字符，合法边界：summary 变化后重建基线）、`autonomous_experience`+`execution_experience`（单轮合计最高 8,729）、`recent_messages` 滑窗新内容（4,189）、`tool_context` 计时器/冷却（每轮 ~500-1,500）、`social`/`dialogue`（各 ~500）。

**判定**：H2 修复真实存在且实现正确（滑窗位移类重复确实归零，合成轨迹证明了机制），但**在已测真实流量上量级很小**——因为真实私聊流量里滑窗位移本来就占比低，且 readonlyChanges 本身只占前台 wire 增量的一小部分（原生消息+工具结果才是大头）。57.4% 是"该机制在专门构造的应力轨迹上的字符降幅"，不是实际费用降幅。这不是虚假宣传（报告 §5.4 有免责），但验收叙述容易让人高估收益。

### 2.2 尚存缺口（按体积排序，真实数据）

1. **外层经验回流是前台资料包里最大的可控冗余**：单轮 8.7K 字符（§4 第6类详述）。
2. **`<root>` 整包重建 20K/次**：summary 变化即全量重发 readonly 状态。合法且无法用增量表达，但 timeline/状态越大重建越贵——这是"资料包瘦身"的第二收益点。
3. **计时器类 churn**：`tool_context.lastPoll/cooldowns`、`social.engagement` 每轮变化。单轮几百字符，属于"真实变化"，但模型并不需要每轮知道 meme 冷却还剩几秒。可消除程度：中。
4. D5 子项 P1-2（请求级动作 ID 去重）未实施：影响小（四路投影各有用途）。

## 3. 第一优先级：外层自治的净收益——**建议裁撤持续规划循环，保留任务账本**

### 3.1 生产账本（3 天，PG `autonomy_cycles`，全舰队）

【已证实】`cycles3d=3914`（≈1300/天），结局分布：

| 结局 | 3天次数 | 占比 | 含义 |
|---|---|---|---|
| sleep | 1005 | 25.7% | 决定休息 |
| model_request_unconfirmed | 970 | 24.8% | 模型请求结果未确认（故障） |
| foreground_work_busy | 889 | 22.7% | 被前台占用直接放弃 |
| request_token_budget | 341 | 8.7% | 预算截断 |
| interrupted | 332 | 8.5% | 租约/重启中断 |
| fair_yield | 141 | 3.6% | 公平调度让位 |
| runtime_or_decision_failed | 97 | 2.5% | 决策失败 |
| 其他（stale_internal_work/feedback_changed/mode_changed/invalid_json 等） | ~98 | 2.5% | — |
| **产生真实行动决策（expectedGoalRevision）** | **7** | **0.18%** | ≈ **2.3 次/天（全舰队）** |

【已证实】单次决策调用成本（model-diagnostics，48h 窗口实测）：planning `inputTokens` 37,333-100K+/次、缓存命中 76-88%；orientation ~58K token/次、缓存 59-93%；外层 planning wire 125,527 字符（前缀复用 113,285）。外层决策输入 12.9-15.4 万字符的量级与审计报告一致（sharedContext 全量注入是主因）。

【已证实】故障循环：bot 7356b371 在 36 分钟内 orientation **失败 86 次**（`res:orientation:failed 86`）；d18ad07d 4.6h 内失败 44+9 次。失败的 orientation 也花钱（部分失败请求仍有 inputTokens）。这正是 H4 想治理的 `model_request_unconfirmed`——而 H4 的 Node 侧代码未生效（§1.1）。

【已证实】前台（真正响应用户的请求）在同一窗口：最忙 bot 64 次/8.3h 完成、median wire 162,374 字符、max 458,175；**前台没有任何 usage 记录**（`kind:'usage'` 仅在 `native_internal.py:84` 内层/外层路径发出，前台 provider 管线不记录）——**生产上无法核算前台真实 Token 消耗**【待验证→建议补】。

【已证实】资源：agent 容器 474.7MiB RSS / 10.76% CPU（1.7GiB 限额），主要是协调器轮询+每 bot worker；API 49MiB；PG 85MiB。硬件无压力。

### 3.2 外层实际产出 vs 成本

【已证实】外层每周期的模型调用：planning 每有效周期 1 次 + orientation 条件触发 + execute 按动作。由于 sleep 最短 300s、无新消息也 wake（wakeReason=autonomous-time），**空闲调用是常态**。3 天 3914 周期里 975 次跑了 orientation、约 100 次跑通 planning 到决策，最终 7 次行动。

【已证实】重复建设：主动联络策略在外层 `candidates()`（autonomous_runtime.py:364-391）与 legacy `initiative.candidates()`（initiative.py:62-119）是两份同规则代码；同一动作回执在 ①外层 feedback ②内层 autonomous_experience ③protocol_experience 三处回流（有界但不去重）；外层 shared_context 每周期重读内层同款记忆/摘要/群消息（129-154K 字符的主因）。

【已证实】外层独有、legacy 定时器覆盖不了的能力只有一类：**跨轮委托/任务账本 + 到期唤醒 + 执行回执闭环**（`propose_background_task` → `pipeline_handoffs` → `autonomy_goals`+`autonomy_wakes` → 到期 cycle → planning → `request_reply` 许可 → execute）。此外还有自主签名/空间发布、自主研究推进、疲劳/活动倾向调节——这三种 3 天账本里贡献≈0-2 次。

【已证实】内层**没有任何定时/提醒工具**（inner_tools.py:6-33 全清单：QQ 资料/发消息/群上下文/引用/收藏/执行记忆/B站/研究；grep reminder/alarm 无命中）。"明天早上7点叫我起床"的唯一实现链路在外层 active 模式，且延时是模型把自然语言换算成相对秒数（无绝对时刻工具），"定时器创建成功≠约定履行完成"有防护（pending≠登记提示、notBefore 前拒绝标记完成）但无履约确认。

### 3.3 三方案对比（A/B/C）

| 维度 | A：现状双层 | B：定时激活单内层（legacy sweep 已存在） | C：定时器+事件触发单层（保留 goals/wakes 账本） |
|---|---|---|---|
| 外层模型调用/天（舰队） | ~百-千次 planning/orientation（实测 3天3914 周期、~1300 周期/天，加失败重试） | 0 | 0（仅到期/事件时调内层 1 次 tool-loop） |
| 决策输入 Token | 5-6 万/次，76-93% 缓存 | — | — |
| 实际行动产出 | 2.3 次/天 | 与现在相当（寒暄/主动消息 ≤10/天，owner 判定 ≤48/天） | 与现在相当或更好（委托履约直达，不再被 planning 环节丢弃） |
| 输入重复 | sharedContext 每周期重读 13-15 万字符 | 无 | 无 |
| 代码复杂度 | 外层 951 行 runtime + Node 协调器 + 7 张 PG 表 + 双份联络策略 | 已存在（initiative/companion_schedule） | 账本保留，删 planning/orientation/睡眠调节 |
| 每次行动的真实路径长度 | cycle→orient→plan→execute（3+ 次模型调用，0.18% 周期走通） | sweep→合成事件→内层一次 | wake→内层一次 tool-loop |

【推断】B/C 不会增加内层 Token：内层前台 journal 增量复用已就位（readonly journal + provider 缓存），一次唤醒的内层请求（median 162K 字符、大部分缓存命中）**小于**现在一次 planning 的全价输入。裁撤持续规划后舰队每天可省下约 20-30M 输入 token 的量级（48h 窗口外层输入实测合计 ~10M，含失败重试），同时把"到期做事"的成功率从 0.18%/周期提升为唤醒即执行。

### 3.4 裁撤清单与保留清单

**裁撤**（持续 planning 循环及其全部配套）：orientation 阶段、每周期 planning、sleep/fatigue/idleActivation 调节、外层 candidates()（与 legacy 二选一）、autonomy_cycles 循环记账、budget_exhausted/planning 相关提示词。沉没成本不计。

**保留**（事件驱动）：`pipeline_handoffs`/`autonomy_goals`/`autonomy_wakes` 三张账本与 `propose_background_task` 前台入口；到期/事件唤醒直接驱动内层一次 tool-loop（需要一小段新接线代码——把"wake→内层执行"从 planning 决策链中解耦）；`request_reply` 回复许可与 quiet/预算豁免逻辑；执行回执落 `pipeline_actions`（内层 experience 简报继续可见）。

**迁移障碍**：无硬障碍。需保留的存量数据=未完成的 owner_request/contact_request 目标与未到期 wakes（当前仅个位数）；autonomy_actions 回执历史被 execution-memory JOIN 引用（execution-memory.ts:17-19），保留只读即可。

**明确结论**：外层以现在的"每5分钟全量重新规划"形态**不具备整体净收益**——0.18% 的周期产出行动、每次行动摊上百次 5 万 token 级调用、25% 周期耗在故障上、与内层三处重复回流。**建议裁撤持续规划循环，改为事件驱动单层**（方案C），保留委托/定时账本。若产品明确要"自主研究/自主发空间"这类持续自主动机，也应降频为显式调度（如每日 N 次、按目标触发），而不是常驻轮询。

## 5. 第三优先级：去冗余后的信息保真与模型能力

【已证实】护栏骨架健全：native 前缀字节相等才复用（`same_native_prefix`），SDK 短窗/群轮替换有专用桥（`confirmed_native_window_extension`/`confirmed_group_extension`），重建必须持 35轮检查点铸造的许可，fail-closed（readonly_journal.py:16-19,311-321）。生产两个 ready journal（§9）与"前缀字节零变化"的部署核验相符。

【已证实】说话人/归属链现状：
- 每条真实消息带 `source_event/sender_id/sender_name/mentions/reply_to` 溯源（message_provenance.py:22-36）；原生历史每轮注入 `[QQ消息来源]` JSON（bot_pipeline.py:163-174）。
- D2 受众门：rolling 先过滤后取最新3条+protected 不挤掉；跨 scope 负例有测试（d2_audience 8/8，含 id=52/53 型）；私聊不出原私聊、legacy_unverified 不扩散。
- "过去回复里的称呼不能证明主人"等纠偏规则已写入协议文本（behavior.py:1108）。

【已证实+推断】剩余风险（非本轮引入）：
1. **存量脏数据**：D2 门只管新写入，D9 存量治理仍是 dry-run，旧行的错误归属（如早期把群聊事实写入私聊 facts）仍在库中且会被 recall 命中。这是"把A的话归给B"问题的残留通道。
2. **protected 关键词匹配脆弱**（见 §6）：无"约定/纠正/承诺"字样的一次性约定不受保护，merge 后散文改写可能弱化——语义保真风险点。
3. 折叠视图（experience_view/provenance 截尾6条+计数）是"有损但标注"的设计，未发现把截断当完整的问题；`plainTextChars` 与 `wireChars` 分开记账，图片不冒充文本。

【已证实】模型正常能力回归：中英文/媒体/分条/NO_REPLY/ToolLoop/ACK 夹具全绿（报告 §5.5），本轮未发现因去冗余导致工具选择或主动行为退化的证据。

## 6. 第四优先级：35轮小压缩与大压缩的真实质量

### 6.1 实际提示词清单（逐字核实过组装点）

| 提示词 | 位置 | 触发 | 输入 | 输出限制 |
|---|---|---|---|---|
| 小压缩（insight 版，生产主用） | companion_insights.py:10-19 + memory_reflection.py:587-604 | 每 scope 满 35 轮（memory-defaults.json `summaryRounds:35`，可配 30-200） | 35轮 turns（单条入库已截800字）+pending≤600条+persona前5000字+sent≤3600字+observed_requests（含引用/图片观察，单图观察≤400字）+core_note | summary≤**800**字（`:800` 硬截）；facts/corrections/emotion/interests/motives/effects/relations **各≤2项**，quote 12-40字且逐字命中 |
| 小压缩（无 insight 变体） | memory_reflection.py:12,591 | insight 关闭时 | 同上少 insight | 600字模板 replace 成 800 |
| 大压缩/Big Merge | memory_reflection.py:566-567 | 跨库 smalls≥3 或 bigs>1 且退避到期；每次吃最旧3条 small+全部 big | **全部 big（各≤1500）+3条旧 small+core_note；不含 claims、不含原始轮次** | ≤**1500**字；claims 由 `inherit_claims` 确定性继承（不靠模型） |
| core_note 更新 | memory_reflection.py:51 | 附着在每次小/大压缩 | 现文+本批证据 | ≤300字，来源须为本批材料 |

| 记忆提取 | 与小压缩同一次请求 | — | — | 同 insight 版 |

【已证实】"800/1200"的真实位置：800=小压缩 summary 上限；**1200 不是任何摘要的字数上限**，而是 `semantic_context.py:31` 的查询命中摘要总预算（此时每条还被截 300 字）。1500=大压缩。

### 6.2 质量评价

**小压缩——设计认真，定位正确。【已证实】**提示词明确"只总结已明确说过的事件、偏好、未完话题和纠正，保留QQ ID，不把机器人说的话当用户事实，不保留凭据"；facts 要求第一人称自述且 value 必须在 quote 中；corrections 排除引述他人/代词不清/道歉/复述。这些约束直接针对历史上"归属错配/猜测变事实"两类事故。定位上它确实侧重近期连续性（逐轮原文+引用+图片都在输入里）。

**结构性短板（按风险排序）**：
1. **提取口径极窄**：每 35 轮每类最多 2 项、"宁可漏掉也不要猜"。一次性重要信息（朋友名字、临时约定、行程）落网之外的概率不低；漏掉的只能靠 800 字散文和 claims 层承接。
2. **protected 判定是中文关键词子串匹配**（summary_material.py:214：`约定/纠正/承诺/答应/未解决/还在等/不叫/应该叫/改口/道歉/撤回`）。"说好了周末去""周末一起爬山吧"这类无关键词的真实约定不会被保护，可被后续 merge 挤掉。这是 protected 机制最大的弱点。
3. claims 层（逐字转录，每轮 human+bot 各1条、240/400字截断）是主要保真机制，但**检索与合并都看不见它**：memory_search 只索引散文不索引 claims（memory_search.py:38），大压缩输入不含 claims（memory_reflection.py:566）——claim 里还在的纠正，模型面上可能已经丢了。claims 的"保护"目前主要在数据层闭环，模型利用率不高。

**大压缩——筛选标准正确，但输入面太薄。【已证实】**提示词优先级排序（人物关系变化>重要经历>长期目标>未解决问题和纠正；短期闲聊舍弃）正是长期价值筛选该有的样子。但它只看到"摘要的摘要"（3条小+全部大+core_note 的散文），没有 claims、没有原始轮次——模型改写 1500 字时可以把散文里的纠正/约定弄丢或混并；不同人物相似事件靠"保留来源会话和QQ归属"一句提示词约束，无结构校验。预算挤掉的**非 protected claims 在 merge 时被静默丢弃**（`merge_sources` 的丢弃集未上报）。

**链式变形【已证实+推断】**：protected claims 按值复制不变形（预算内）；普通信息逐代衰减。孤儿轮问题：小压缩时 protected 装不下的轮次照常前移 watermark，此后不再进入任何批次（memory_reflection.py:667,548）——该轮细节从此只存在于 native wire 直到被轮数自然推出，模型面永久不可见。边界场景但真实存在。

**claims v2 复杂度是否值得**：对纠正/称呼/来源归属收益明确（与 memory_blocks 互引、native-only 不签 coverage、core_note 继承）；对一般事实收益有限。不建议再加复杂度，更不值得回退——回退会重新打开"猜测变事实"的门。

### 6.3 对核心问题的直接回答

- **800 字默认通常够用吗？** 够。35轮批次里真正需要进入长期层的是约定/纠错/关系/目标，量小；bulk 细节本就该由 facts/claims 承接。信息密集批次（大量图片、多个新人物、长约定）会有损失，但主要损失点在"每类≤2项"和 protected 关键词，不在 800 字本身。**1200 字没有现存入口，也无必要**——真要扩，扩的应是 protected 判定准确率而非字数。
- **最可能丢失**：>240 字长消息的尾部细节；无 protected 关键词的一次性约定/目标；每类 2 项之外的事实；merge 预算挤掉的普通 statement。
- **最可能伪造**：散文 summary 把机器人玩笑/猜测写成用户事实（提示词有禁令、无机检——claims 可事后对照发现）；big merge 跨会话合并的归属漂移。claims 结构本身几乎不可伪造。
- **自然遗忘可接受吗？** 可接受。遗忘单点在小压缩（`memory_rounds` 删除+`project_history` 永久停发，memory_reflection.py:664-673; summary_material.py:15-29），大压缩只能在小压缩产物上做减法。缓冲层（claims+facts+core_note+图片观察）使"重要约定被静默遗忘"需要同时穿过四层，概率低。**当前压缩体系不是本次整改的短板，不需要重写**。

## 13. 总结：对四个最终问题的回答

**1. FishBot 现在哪里真正浪费了 Token 和计算？**
外层持续规划循环是唯一大头：每 5 分钟级全量重载 13-15 万字符上下文做一次"决定什么都不做"，0.18% 的周期产出行动，外加 25% 周期耗在未确认的故障请求上、活跃 bot 小时级 orientation 失败循环。次级浪费：外层经验三处回流（前台单轮 8.7K 字符）、journal 全量重写、外层 sharedContext 与内层记忆重复读取。前台增量本身（H2 之后）已无明显浪费。

**2. 哪些复杂机制实际上不值得存在？**
外层的 orientation/每周期 planning/睡眠-疲劳调节/双份联络策略；011 检查点铸造（无消费者）；外层与 legacy 并存的主动联络第二实现。它们删掉后模型能力不受损——因为这些机制的产出（每天 2.3 次行动）可以用"账本+到期唤醒+内层一次执行"完全覆盖。

**3. 去除这些机制会不会损害模型的真实能力？**
不会。对话能力全在内层（护栏/记忆/压缩/工具）；外层裁撤清单里的每项要么与内层重复，要么由保留的账本+legacy sweep 覆盖。唯一真实的风格层损失是"自主研究/自主发空间"的持续动机——若产品要它，用显式低频调度实现，不需要常驻规划。真正的能力风险不在裁撤，而在：protected 关键词误判、大压缩散文盲区、D9 存量脏数据——这三个建议按 §11 处理。

**4. 35轮小压缩与大压缩能不能足够可靠地保留有价值的信息？**
能，且有明确的边界。小压缩（逐字 claims 层+800字散文+每类2项+core_note）对约定/纠错/关系/目标的保真链路是认真的，多次压缩后 protected 不变形、普通信息有序衰减，属于设计良好的"自然遗忘"。大压缩筛选标准正确但只看散文，可能丢掉散文里未被 claims 保护的纠正——这是当前体系里唯一值得修的保真缺口。800 字通常够用，1200 无现存入口也无必要；比字数更重要的是 protected 判定的准确率。

**一句话结论**：本轮整改把前台上下文管线和压缩记忆做到了"不需要再动"的状态（验证严格、收益如实但量小）；系统当前真正的杠杆只有两个——**重启 agent 让已测好的 Node 修复生效**，以及**把外层从常驻规划改成事件驱动的任务执行层**。做完这两件事，整体净收益（费用、可靠性、复杂度同向改善）远大于继续打磨增量去重。
