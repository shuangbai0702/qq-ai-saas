# 大肥鱼机制与双平台自动内存策略接入

工作区：`D:\MYCODE\APP\fishbot\qq-ai-saas`。本轮沿用现有平台，没有创建第二套产品。

## 本轮真正接入的行为

1. **群聊近期氛围上下文**：在原有学习、长期记忆和触发判定之外，保存同一 Bot、同一群最近 12 条文本片段，每条最多 180 字，10 分钟过期，每 Bot 最多 128 个群缓存。未触发的消息不调用模型；真正触发时才注入上下文。私聊不进入该缓存，群白名单在观察前校验。使用现有 `socialAwareness` 开关，保留客户已保存的选择。
2. **直接复用内部标签清理**：复制 `zexuanw958-svg/dafeiyu-config-pack` 的清理规则，固定提交 `8c01b0361b8a4baff5be3d2bc67ed55108953086`，保留 MIT 许可证。清理 system_reminder、DSML 和旧工具调用标签。接入模型普通响应、字符串形式的 assistant 历史，以及最终文字发送；保留真正的工具调用对象，不改用户原文。模型最终发送检查仍保留 NO_REPLY、MEME/IMAGE 和 QQ_FACE 的独立规则。
3. **管理动作清理临时学习上下文**：停用表达或清空学习成功后，立即清除对应群的氛围缓存，避免已停用的表达通过另一条注入路径继续影响下一次回复。

来源：该配置包属于此前已核对的高播放量大肥鱼视频关联仓库；群聊上下文机制也参考已有 `group-chat-plus` 源码。它们不能证明不同作者使用同一套人格，不能证明当前实际模型效果已与视频完全相同。

| 机制 | 当前实现与本轮变化 |
|---|---|

| 说话方式学习与使用范围、停用/清空 | 保留现有实现，补齐停用后的临时缓存失效 |
| QQ 自动收集聊天表情包、审核、图片候选、普通图库独立管理 | 保留现有实现；本轮未增加常驻视觉/Embedding 服务 |
| 防止内部工具标签发给群友并污染后续对话 | 本轮复用成功项目清理规则，接入普通响应和发送链路 |

这些机制是程序与 Prompt 配合，不承诺只靠修改人格就能完全复制原作者效果。氛围上下文会增加每次已触发请求的少量输入 Token，最多约 2160 字正文，不是完全零成本。

## 双平台基本能力

正式入口：`ProcessHost.beginInspection → maintainMemory → scripts/runtime_memory.py`。不是实验固定 A/B 账号入口。Agent 接管磁盘中的既有进程记录后也会参与策略；没有新增每 Bot 常驻控制器。

| 平台 | 自动策略 |
|---|---|
| Windows | 对已验证身份的受控 PID，在空闲至少 300 秒后执行一次 EmptyWorkingSet。每次真实活动后重新计算空闲周期，尝试间隔至少 300 秒；一轮最多操作一个实例 |
| Linux | 仅在整机内存压力下、有现成 Swap 且原生接口/权限可用时，对受控 PID 的私有匿名、驻留、未锁定地址建议 PAGEOUT，地址预算 64MiB；若属于可验证独占的叶子 cgroup，补充有界 memory.reclaim |
| 条件不足 | 无 Swap、不支持原生接口、权限拒绝、进程归属变化、保留内存不足时，不强行操作；降级为系统管理，并返回状态 |
| AI 进程公共维护 | 每分钟检查，空闲 5 分钟后释放 SQLite 缓存、Python 可回收对象；Linux 额外尝试自身 allocator 的 malloc_trim。活动模型、学习任务、表情下载任务、消息合并期间跳过 |

实际消息与活跃模型状态由行为层写入无内容的活动记录。共享组记录汇总所有成员的活动，各成员协议实例读取自己 Bot 的活动。没有把 Key、QQ 消息正文写进内存策略文件。

活动恢复是按需自然回页：**正式策略没有新增低 memory.high/memory.max、工作集硬顶或低优先级约束**，所以不需要等待控制器解除限制。实验里的永久 hard32 和需要独立租约守护的软顶策略未默认接入。既有管理员设置的 cgroup 配额保持原来的职责。

保护包括 PID 创建时间、私有目录 argv 校验、原生进程句柄/pidfd、操作和发布前校验当前 process record、原生失败限频、单轮错峰。没有修改宿主 Swap、zswap、sysctl、fstab，也不修改 QQ 登录文件。PAGEOUT 预算不是“实际释放了 64MiB”；EmptyWorkingSet 成功也不是净省同量物理 RAM 的证据。

配置：缺省自动启用。可设 `FISHBOT_MEMORY_POLICY=off` 关闭原生进程回收；AI 正常缓存清理仍保留。代码随 Windows 源码部署和 Linux Docker allowlist 一同交付。管理页运行概览新增 AI/QQ 内存优化状态。

### Linux 条件

现有 AstrBot 固定依赖包含 psutil。实际生产容器若被 seccomp/capability 策略禁止 `process_madvise`，会降级，不使用 `--privileged` 绕过。cgroup 不是专属叶子或包含无法验证归属的进程时，不写 `memory.reclaim`。本轮没有自动申请额外权限或创建 Swap；需要运维先准备适当的后备和授权，再由平台自动选择可用路径。

旧实验保留在 `experiments/qq-memory-virtualization/round3`，没有被新数据覆盖。本轮没有重新宣称“一号完整只需几十 MiB”或 2GB 可售容量。

### 本轮已发现并处理的问题

1. 扩展上下文说明改变了记忆 JSON 标识：保留原稳定标识，将新说明移到前文。没有降低记忆测试强度。
2. 停用学习表达后原句残留临时缓存：由同一个运行时管理入口同步失效对应群缓存，真实 SDK 回归已验证。
3. 共享组全局活动不能写成每成员都永久 busy：成员与组分别计算，新增测试覆盖。
4. 旧进程/旧记录迟到不能操作新 PID：原生句柄和记录双重校验；缺失指标/归属不确定时不操作。
5. 人工 QQ 验收发现启动阶段误报掉线：NapCat 在 generating_qrcode 等进度阶段可能仍带 isOffline，之前会将登录会话提前置为终态 failed。现在显式进度优先于过渡离线标志，保留真正 offline 失败和额外验证；initializing 为 authenticating，不能冒充 online。针对性测试覆盖过渡、扫码、初始化和真实离线。修复已部署，新会话实际达到 waiting_scan/hasQr=true，记录见 `login-after-fix.json`。
6. 随后协议端实际恢复 online，但历史二维码会话仍是 expired：修复 QQPanel，以核实的协议在线状态展示已连接，保留过期历史记录，不要求已在线用户再扫码。直接原生接口核对为 isLogin=true/coreReady=true/ready，真实浏览器验收通过。未为这一纯显示改动再重跑全部后端测试，已重做生产构建、生产启动检查和真实浏览器断言。
