## 3. 确认缺陷与本地修复

### F01 P1：不合格群输入及reaction在过滤前已持久化

- 条件：非群参与白名单输入，或真实`group_msg_emoji_like`通知进入SDK异步转换前的原始接收路径。
- 调用链：OneBot原始事件 → `native_ingress.bind` → 入站留存 → SDK转换 → shared/headless gate → `behavior.execute`。旧实现留存早于有效业务白名单，通知又没有可靠消息恢复身份。
- 修改：[native_ingress.py](../adapters/astrbot/native_ingress.py#L10)统一`admitted`；[shared-worker.py](../adapters/astrbot/shared-worker.py#L143)、[headless.py](../adapters/astrbot/headless.py#L33)和行为入口复用。群必须在`behavior.groupParticipationGroups`中，并与非空`groups`取交集；空业务白名单不表示所有群。私聊仍独立可用。
- 原始可信入口在retain/SDK await前拒绝；转换后继续校验以防配置变化。消息留存只接收真实message，不给notice/request制造第二套恢复池。图片/表情包message不受reaction过滤影响。
- 验证：策略测试、原始留存11项及真实SDK双入口覆盖。生产已有白名单外message、group_increase/upload/reaction债务，证明不是纯理论。
- 风险：之前依靠“空白名单=放行”的配置会停止群服务，这是本轮产品规则的明确变化。旧合法Journal不追溯重写。

### F02 P1：跨Scope版本变化否决无关模型判断

- 条件：群B/私聊B发生人物纠正、约定或关系等全局版本变化，群A/私聊A正在生成或复核草稿。
- 修改：[behavior.py](../adapters/astrbot/behavior.py#L370)当前草稿只依据目标Scope cursor决定是否重新复核及结果是否仍当前。保留同Scope真实输入、配置代际、StopFence、目标身份、权限和最终dispatch检查。
- 没有新建“scoped memory version”账本。原始行的Scope不能可靠代表最近一次纠正的来源；跨Scope纠正/恢复会修改原Scope的派生行，用行Scope凑版本仍会误判。
- 进一步沿实际调用追踪，在[autonomy.py](../adapters/astrbot/autonomy.py#L341)、[companion_schedule.py](../adapters/astrbot/companion_schedule.py#L78)删除群参与/日程/主人辅助判断同类全局记忆否决，保留现有各自会话时钟、anchor、租约和授权条件。
- 跨Scope事实仍可正常持久化、供后续新请求读取；不是冻结记忆。仅有外Scope变化不会打断当前模型决策。
- 验证：真实remember→correct→restore及约定更新；sameScope新输入仍触发判断并能在派发前拒绝过期发送。旧版本上两项自主外Scope纠正测试均失败，修后通过。
- 测试合同修订：`scope-work-runtime`严格期望由14主请求/9复核改为14主请求/8复核；目标群复核2→1，删除的是被明确禁止的外Scope额外调用，输入/回执/上限/前缀断言保留。

### F03 P1：确定未派发的attempt归属不准确

- 修改：[behavior.py](../adapters/astrbot/behavior.py#L341)在真正拥有`pipeline.sending()`的dispatch边界同步捕获attempt，只在该次`dispatch_original`抛`PreDispatchRejected`时回撤该token；外层observed_send不再使用捕获时的当前计数再次退款。
- [bot_pipeline.py](../adapters/astrbot/bot_pipeline.py#L1027)回撤要求本地attempt及数据库CAS仍等于捕获值，且不会把已确认前缀降掉。
- 验证：真实SDK路径5个场景：单次拒发、已有确认前缀、迟到旧拒绝遇新attempt、外层非本次派发错误、真实超时。确定拒发不变unknown；超时仍unknown，部分确认仍partial；不能退款新派发。
- 不增加第三套发送状态；工具账本、Work、真实回执仍承担原有不同职责。没有真实QQ外发。

### F04 P2：waiting激活和输入责任没有正常分离收口

- 修改：[bot_pipeline.py](../adapters/astrbot/bot_pipeline.py#L430)只读规划器，以及`reconcile_waiting`。启动和Scope释放后按现有表证明责任；规划与应用在同一写事务/CAS内，阻止证明后被另一进程加入inbox/input。
- 所有关联输入均已settled：旧激活`superseded / waiting_inputs_settled`。
- 只有settled及blocked_recovery/blocked_unknown责任：旧激活`blocked / waiting_input_blocked`，**输入不变、不获得重放资格**。
- 无输入、无Owner/inbox、无当前Journal引用及未结算模型输出：`blocked / waiting_responsibility_missing`。不能标superseded，否则`bind()`可能把再次投递错误当作已处理。
- runnable输入、当前inbox/Owner、未结算草稿、Journal缺证据：保护，不能根据时间或新消息认定已处理。
- cleanup保留缺责任且没有独立输入去重key的最小事件身份；有blocked输入则沿用输入自身去重保护，不额外永久保存激活。残留的是不带原文的证据缺口key，不是运行中Work或无限重试任务。该类旧key仍需人工核验后收口，不能宣称无任何长期元数据。
- 验证：9项等待测试，含输入不变、unknown保护、缺责任不假结算、重投去重、Journal保护及幂等；31项等待/管线/旧结算组合通过。

### F05 P1：共享背景窗口可遗漏尚未模型化的定向输入

- 修改：[shared_context.py](../adapters/astrbot/shared_context.py#L153)在现有背景窗口之外，保留`pipeline_work_inputs`中可信`addressed_self=1, seen=0`且仍有处理责任的输入。它们也不能被“更晚队列已接纳”的去重捷径抛弃。
- 不把所有旧普通群消息无限加入，不新增队列；只有确实未处理的定向输入突破背景窗口。窗口不承担替模型决定定向输入无需处理的职责。
- 验证：20条背景消息中旧定向输入仍可见；重启/已有后续接纳记录后仍保留；已提交历史前缀不改。真实SDK检查多人Work与明确覆盖结算。

### F06 P1：旧Hold前置严格读取阻断合法35轮

- 修改：[memory_reflection.py](../adapters/astrbot/memory_reflection.py#L1114)删除摘要前对每条旧Hold必须完整恢复的预加载，继续使用原有recapture及语义收集器。
- shared复用现有`collect(...discard_unavailable=True)`；[semantic_collection.py](../adapters/astrbot/semantic_collection.py#L122)的`collect_local`把同Scope旧Hold纳入同一批。完整可信材料正常读，不完整材料提供真实片段及缺失说明。没有作者证据时`sender_ids=[]`，不虚构人物。
- 明确scope/event/作者矛盾、活动Work/owned输入、临时SQLite错误、模型后材料CAS变化仍失败且不提交/提前退休。
- 修前shared/private合法35轮遇孤立Hold，0次模型调用；修后同一次摘要模型请求能看到现存文字、实际作者或明确未知，生成合法Checkpoint。旧Hold直到Journal替换与原有退休成功才清理。
- 验证：8项专项，包含共享/私聊、完整缺失、部分片段、身份冲突、SQLite异常、CAS冲突。未强制生产压缩，没有恢复Coverage/Hold作为新运行机制。

### F07 P2：合法群inbox被年龄/数量截断

- [autonomy.py](../adapters/astrbot/autonomy.py#L241)取消无条件24小时删除及100条截断。inbox本来就是每Scope一行，并受真实群白名单约束；“变老”不是模型处理证据。
- 仍按当前授权和已有参与clock消费/淘汰相应inbox，不把其他输入伪造为已回答。没有新消息时现有inbox仍有合法判断机会，同一event的checked/event合同阻止无进展反复判断。
- 验证：三天前合法inbox不会仅因年龄丢失；自主套件检查独立群窗口、一次判断、冷却、交互失效、预算和取消。

### F08 P2：共享戳一戳处理器不可达；新增显式AI开关

- 实际链路：真实OneBot notify/poke → SDK转换 → shared或headless gate → `chat_rhythm.poke`。修复notice无需message留存即可到现有处理器，其他notice不会一起进入AI。
- `pokeIntoAiContext`默认false：[behavior-defaults.ts](../packages/contracts/behavior-defaults.ts#L40)、配置Zod Schema、回复设置及能力总览一致。API配置沿现有保存/热更新链持久化，无数据库迁移、无第二套配置。
- 关闭：原程序性概率回戳/冷却照常，0个AI Work/消息恢复输入；不计业务轮。
- 开启：只对协议可信、确实戳本机器人的notify/poke，加入简洁`platform_poke`互动说明及`is_user_statement=false`；不复制整份payload，不冒充用户文字。跳过同时程序回戳，模型仍自主判断是否回应。
- 使用现有Scope锁等待/续接，所有权在获得后无await间隙登记，finally释放，避免活跃Scope下bind丢通知或续轮自己等自己。
- 验证：真实SDK转换×shared/dedicated×private/group×开/关共8条路径（1项测试），5项策略及忙Scope测试，TS默认/API序列化/UI开关测试。最后QQ/模型执行边界为替身，不冒充真实QQ成功。notice没有真实稳定message_id，不宣称崩溃窗口内的戳一戳exactly-once恢复。

- 连续性/其他可选认知产品缺失或不合法，按既有接收合同记录，不因为它们不完美永久阻塞合法摘要；真正摘要、身份、事务或CAS失败仍不能退休。

## 8. 尚存风险与发布前条件
